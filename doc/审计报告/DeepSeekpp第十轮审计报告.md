## 一、本轮的核心转向

前九轮一直在做**增量发现**。第十轮换了个问题：

> 已经发现的 55 条 finding，**合起来说明什么**？

单看每条都是 P2/P3。但如果某个子系统攒了 5 条、且是同一根因，那指向的就不是 5 个 bug，而是**一套设计有问题** —— 那种情况逐个修是浪费，应该整体重写。

### 新增 `lib/cluster.py`：双维聚合

```
维度1 子系统（按业务边界归属，非目录）
维度2 根因族（把 kind 归到失效模式）
```

首次运行结果：

### 一个必要的指标修正

第一版阈值是"条数 ≥5 就建议整体重构"，结果 6 个子系统全部中标 —— **等于没建议**。

改成**根因集中度**（主导根因占比）：条数 ≥4 且占比 ≥60% 才算"整体重写"。

修正后只有**自动化调度**一个达标（状态机/事务错序 80%）。这个输出才可用。

## 二、针对高密度区派工单：自动化调度

聚类识别出唯一达标子系统后，派了一张**重构级审查**工单（不是又一轮通读），要求回答：

> 这套状态机的设计缺陷是什么？已有 5 条是否同源？有没有同一根因下的第六、第七个表现？

### 结果：子 agent 报的 4 条，全部是已有 5 条的重复

| 子 agent 报告 | 对应已入库条目 |
|---|---|
| finally 块在删除后 finalize 失败（P1） | = DPP-002（删除不等待终态） |
| nextRunAt 对所有失败统一推进（P2） | = DPP-012（取消仍按失败回写并推进） |
| scanDueAutomations 串行 await（P2） | = DPP-016 |
| deadlineAt 当 completedAt（P1） | = DPP-011（中断恢复用回收时刻当完成时刻） |

**净新增 0 条。**

这个"零产出"本身是有信息的：子 agent 被明确要求找第 6、7 个表现，但找到的全部落回已有 5 条。这反过来**验证了聚类结论** —— 自动化调度的根因单一，且已被这 5 条覆盖。

### 根因判定（本轮最有价值的产出）

子 agent 的 A 部分总结，我复核后认可：

> **这套状态机没有"终态"概念，把"取消/中断"当作普通"失败"处理，且持久化状态与进程内租约之间缺少事务性关联。**

5 条是同一根因的 5 个表现：

| Finding | 表现 | 共同根因 |
|---|---|---|
| DPP-002 | 删除不等待终态 | 删除路径只 abort，不同步等待租约释放 |
| DPP-034 | submitPrompt 无超时 | 执行上下文与超时机制分离 |
| DPP-011 | 中断恢复用回收时刻当完成时刻 | 把"超时判定时刻"当"实际完成时刻" |
| DPP-012 | 取消仍按失败回写并推进 | 对所有非成功结果统一推进 nextRunAt |
| DPP-016 | 串行 await 所有到期任务 | 状态机无并发控制 |

我复核了 `createAutomationRuntimePatch` 的实现（`scheduler.ts:528-556`），确认失败分支（含 cancelled/timeout）**确实统一推进 `nextRunAt`** —— 而 status 判定处（`:235-240`）明明已经区分了 `cancelled`。这是"区分了状态却不区分后续行为"的典型。

**重构要点**（子 agent 给出，我认可）：引入 `claimed → running → finalizing → terminal` 四阶段；租约与存储事务绑定；cancelled/timeout 不推进 nextRunAt；删除等待终态或用软删除+GC；scan 加并发上限；中断恢复用真实时间戳。

## 三、补完剩余零测试模块

第二个子 agent 覆盖剩余零测试模块（约 15 文件）：`core/` 根目录 5 文件、`entrypoints/` 根目录 4 文件、`core/model|theme|browser|background|tool-loop`、`entrypoints/sandbox-offscreen`。

### 净新增 2 条（P3）

**[P3] `core/messaging.ts` 整体是死代码**

```ts
export function sendToBackground(...)      // 3 个导出
export function sendToContentScript(...)
export function onMessage(...)
```

我复核确认：在 `core/` 与 `entrypoints/` 下**零 import**。tests 里出现的 `'core/messaging'` 是 `i18n-background-slice.test.ts` 中的模块名**字符串列表**（用于断言 i18n 覆盖面），不是引用。

真正链路是 `core/messaging/runtime-boundary.ts` + `runtime-command-registry.ts`，带完整 sender 校验。

**[P3] `saveBackgroundConfig` 静默跳过非法配置**

```ts
export async function saveBackgroundConfig(config: BackgroundConfig): Promise<void> {
  const normalized = normalizeBackgroundConfig(config);
  if (!normalized) return;    // ← 无日志、无异常
  await chrome.storage.local.set({ [STORAGE_KEY]: normalized });
}
```

调用方无法区分"保存了空值"与"保存被跳过"。

### ⬇️ 修正一条已有 finding（比新增更有价值）

**DPP-035（messaging 错误映射为 null）从 P2 降为 P3。**

原因：既然 `core/messaging.ts` 是死代码，那么 DPP-035 记录的问题**发生在无人调用的代码路径上**。之前判断"所有经 onMessage 的调用都无法区分失败"—— 这个影响面评估是错的，实际生产链路走的是带 sender 校验的另一套。

这是对已有结论的**自我修正**，其价值高于新增一条 P3。

## 六、局限

**① 聚类依赖手工归属表**

`SUBSYSTEMS` 是手工定义的路径前缀表，可能与实际业务边界有偏差（如 `core/` 根目录文件归入"其他"，本轮有 6 条）。集中度阈值（≥4 条且 ≥60%）也是经验值。

**② 重构级审查的子 agent 未深入**

它跑满 29 turns 就到上限，把已有 5 条重新描述了一遍，没有真正找第 6、7 个表现。所以"根因单一且已覆盖"这个结论**只是一次尝试的结论，不构成证明**。若要在重构前确认，需要人工完整通读 2842 行。

**③ 仍然没跑起来**

`tsc` 卡在依赖缺失，220 个测试因 vitest 缺失一个都跑不了。这是十轮下来最大的空白。

**④ 死代码判定基于静态 grep**

`core/messaging.ts` 零 import 的结论基于 grep，未考虑动态 require 或构建期字符串引用。
