## 一、确证缺陷：D14【P1·high】懒加载单例竞态

`butler/core/aliases.py:118`：

```python
def get_alias_store() -> AliasStore:
    global _alias_store
    if _alias_store is None:              # ← check
        _alias_store = AliasStore()       # ← act（非原子）
    return _alias_store
```

**两次实测**：

| 实验 | 结果 |
|---|---|
| 8 线程并发首调 | 拿到 **2 个不同实例**（竞态成立） |
| 6 线程（放大窗口） | **6 个实例**；期望 6 条别名，**盘上只剩 1 条** |

**后果链条**：多个实例各自 `_load()` → 各持一份 `self.aliases` → 各自 `learn()` → 各自 `_save()` **全量覆盖同一个 aliases.json** ⇒ 后写覆盖先写。

**这把 D4 的性质改变了。** D4 原本的触发条件是"文件损坏"，现在**服务启动后首批并发请求就会丢别名**——HTTP 是并发的，MQTT 触发也是，这个窗口真实存在。

**同型懒单例另有 3 处**（`global _` 共 26 处，`if _X is None:` 共 10 处）：

| 位置 | 后果 |
|---|---|
| `config.py:412` `get_settings()` | 多份 Settings 实例 |
| `decision_store.py:20` `_conn` | **SQLite 多连接**，WAL 下写冲突 |
| `notification_store.py:20` `_conn` | 同上 |

后两处尤其需要一起改：SQLite 在 WAL 下多连接写会撞 `database is locked`。

## 二、CONC-08 判为假阳性（但引出了 D14）

规则报的是 "`_load` 裸写 `self.aliases`，`learn` 持锁"——看起来是锁覆盖不一致。

**核验结论**：`_load()` 只在 `__init__`（第 21 行）被调用，而 `__init__` 只在 `get_alias_store()` 首次调用时执行一次 ⇒ **单线程路径，无并发窗口**。判假阳性。

这和 AutoForge `af_premiere` 那次是同一型：**静态分析看不出调用时机**，分不出"运行期每次都调"和"启动期只调一次"。

**但顺着这条查下去，发现了真正的问题不在锁覆盖，而在单例本身。** 规则报的是"锁没覆盖 `_load`"，真因是"**同一个函数可能创建多个实例，锁是每个实例各自的**"——`_lock` 是类级 `Lock()`，但多实例意味着多把不同的锁，加锁形同虚设。

## 三、工作流迭代

### W65：跨函数属性解析通用化（收口到 `_common.py`）

同一条判据缺口在 doubao-butler 审计里出现了三次：

| 轮次 | 表现 |
|---|---|
| W54（第三轮） | 写盘委托：`learn()` 调 `self._save()`，`dumps` 在 `_save` 里 |
| W61（第五轮） | 函数内 import 同名函数，规则按名字字面判递归 |
| W62（第六轮） | `timeout` 在被调的 `_ha_call` 里 |

**根因相同：静态规则的视野局限在单个 FunctionDef 内。** 第六轮我记下"该做通用化改造，而不是每次单独补"，本轮落地：

```python
module_func_index(tree)   # 模块内 函数名 -> 节点列表
called_names(fn)          # 函数体内调用过的名字
attr_reaches(fn, pred, func_idx, depth=2)   # 本函数或它调用的模块内函数满足 pred
```

`errorhandling_defects.py` 的本地 `_timeout_reaches` 已替换为调用通用实现。

**实现时踩到的坑（值得记）**：`attr_reaches` 自身递归必须有 `seen` 防环——互相调用的函数（A→B→A）会让**找 bug 的工具自己先 RecursionError**。

### W65 落地时我犯的错

重构时按区间删除本地 helper，**把区间内的 `LONG_LIVED_CALL` 常量一起删了** ⇒ NameError ⇒ `check_timeout_cleanup` **整条规则 0 命中**。

发现方式是"命中从 3 变 0，我第一反应不是'规则变好了'而是'刚刚删了东西'"。这是本项目**第十八次**"工具静默失效"，失效方向照例是"命中变少"。

**教训已写进代码注释**：按区间删除代码前必须确认区间内没有别的东西，删完立刻跑门禁。

### W66：扫描范围收口

`doc/ask/src/` 是 **AutoForge 的代码快照**（4 个 `af_*.py`），是随仓库附带的参考资料，**不是本项目代码**，却贡献了 82 条命中（high 7）。

新增 `py_files()` 统一入口（在 `_common.py`）：

- 跳过通用非源码目录（test/docs/doc/vendor/node_modules/build...）
- 支持项目根下 `audit-exclude.txt` 声明额外排除前缀

**实测过滤效果**：366 个 .py → **311 个**（剔除 doc 5 / tests 43 / vendor 7）。

这和 `_chain()` 被复制 10 份是**同一个结构性问题**：24 个分析器各自 `rglob("*.py")`，任何一处忘记跳过就前功尽弃。统一入口已提供，但**尚未替换全部 24 处**——本轮只验证了能力本身，替换工作留给后续轮次（每次替换都要过门禁）。

## 七、本轮最该记住的一条

**规则报的现象和真因可能不在同一个点上，但顺着规则查下去往往能找到真因。**

CONC-08 报的是"`_load` 裸写、锁覆盖不一致"——这是假阳性。但正是这次核验让我去读 `get_alias_store()`，发现了 D14。**锁本身没问题，问题是锁属于实例，而实例可能有多个。**

反过来也成立：如果当时直接判"规则误报"就翻篇，D14 不会有。这提示分诊时**不要只判"命中对不对"，还要问"这条命中指向的代码周边有没有别的问题"**——规则指错了位置，但指对了区域。
