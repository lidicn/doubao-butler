## 1. 工作流迭代

### 1.1 混合聚焦（本轮核心改进）

第八轮的问题是：纯按危险信号排序，core 名单被 `app.py`、`dialog.py` 这些**已读烂的文件**占据，而 V23 恰恰藏在从未读过的 `mcp/server.py`。

改为**未读文件权重 ×1.6**：

```python
def key(r):
    rel = relpath(r["path"], repo)
    return -r["score"] * (1.6 if rel not in read else 1.0)
```

这是"探索 vs 利用"的权衡——信号分高 = 利用（已知危险区），未读 = 探索（盲区）。效果立竿见影：

```
★ butler/mcp/server.py           79.09   ← 从第 2 升到第 1
★ butler/api/skill_routes.py     76.11   ← 从第 3 升到第 2
  butler/app.py                  83.71   ← 已读，降到第 3
```

第 2、3 名（V23 所在）现在能稳定进入 core，不会被已读文件挤掉。

### 1.2 冷启动优化

- 正则预编译（220 文件 × 10 模式，不预编译会重复编译数千次）
- worker 上限从 8 压到 4——**实测 `cpu_count=2` 时 workers=8 反而更慢**（进程创建开销 > 并行收益）
- 文件数 < 30 时直接单进程

### 1.3 更正上一条虚假性能声明

上一轮我写"冷启动 16.5s"。重新测量后：**首次约 3.2s，热态 2.5s**。

原 16.5s 是 `mp.Pool` 首次创建 + 沙箱文件缓存未预热的**一次性**开销，且我误把它当成了常态值。**这条已更正**——连续两轮出现性能数字夸大了，说明我对"测量什么"还不够严谨。

## 2. 三条经核实的负面结论

### 2.1 `skill_routes.py`：52 个端点守卫覆盖完整

| 项 | 结果 |
|---|---|
| 函数总数 | 56 |
| 带 `guard(request)` | **53** |
| 无 guard 的 3 个 | `_runner`(L17)、`repo_recent`(L870)、`routes`(L1006) —— **全部是内部 helper，非端点** |

**无未授权访问风险。** 三个无 guard 的函数经逐一确认都是被同文件内其他函数同步调用的辅助函数，不出现在路由注册表中。

### 2.2 `skill_natural_create` 的 LLM 调用：有超时兜底，无限流但可接受

疑点：`await llm.chat(...)` 无 `asyncio.wait_for` 包裹，全文件 `timeout=` 计数为 **0**。

核查结果：

- `llm.chat` → `self._raw()` → `httpx.AsyncClient(timeout=self.s.llm_timeout)`，`llm_timeout` 默认 **30s**（`config.py:115`）
- `chat_with_tools` 另有 `time_budget=60.0` 的循环前检查

**结论：单次请求有 30s 硬超时，不会无限挂起。** 但自然语言创建技能是**多轮 ReAct**，最坏 8 轮 × 30s = 240s，且该端点**无限流**。

定 **P3**：影响是"单次调用可能占住一个连接 4 分钟"，不是缺陷。建议后续加端点级限流，但不阻塞修复优先级。

### 2.3 `validate_skill` 在 async 内同步调用：实测无影响

疑点：`skills_save`(L52) 在 `async def` 里直接调同步的 `validate_skill`（151 行，含 for 循环和正则），未包 `asyncio.to_thread`。

**实测：单次 `validate_skill` 耗时 0.004 ms，且 `skills/schema.py` 内无任何 IO 调用**（`open`/`httpx`/`subprocess` 计数为 0）。

**结论：纯 CPU 且微秒级，阻塞事件循环的时长可忽略。** 同为未包裹的 `_runner()`、`repo_recent` 也同理（前者只是 `getattr`，后者是 SQLite 查询——这个略重，但 `skill_runs` 已在 asyncio.to_thread 里调用它）。

定 **P3**，不列为缺陷。

## 5. 诚实的能力边界

1. **覆盖率仍只有 ~10%**：八轮下来逐行读过约 4,173 / 41,431 行。core 名单里仍有大量未读文件。
2. **完整 lifespan、真实 MQTT、SQLite 并发——九轮均未覆盖。** 这是最大的盲区：`_run_coro` 这类缺陷在静态分析下能推出来，但**并发类缺陷（P0-2 SQLite 跨线程）只有真跑才证得实**。
3. **"未发现"不等于"不存在"**：本轮零新增是在两个文件、1701 行的范围内成立，不能外推到全仓。
4. **静态分析的天然上限**：本轮用的仍是 AST + 正则。要突破当前产出递减，需要换方法——真跑起来（integration 测试、并发压测）或属性测试（hypothesis 随机输入打边界）。

## 6. 建议下一步

**继续用同一套静态工作流，边际收益已经很低了。** 建议二选一：

- **A. 转向运行时验证**：把 lifespan 跑起来（真实 MQTT + SQLite 并发），专攻 P0-2 这条九轮未证实的核心缺陷。这是当前**风险最高、证据最弱**的一条。
- **B. 换检测引擎**：属性测试 / 不变量运行时断言，突破静态分析的上限。

不建议继续做的：再扩大静态扫描范围——本轮已证明"高信号区 ≠ 高缺陷区"，继续扫只是在已排除了风险的地方重复投入。
