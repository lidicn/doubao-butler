## 1. 风险总览

### 1.1 分级统计

| 级别 | 含义 | 数量 | 编号区间 |
|---|---|---|---|
| 🔴 **S0** | **服务无法启动，或核心功能 100% 失效** | **5** | R2-01 ~ R2-05 |
| 🟠 **S1** | 单条链路永久失效 / 会造成真实数据丢失 | **10** | R2-06 ~ R2-15 |
| 🟡 **S2** | 阻塞、挂起、静默降级、状态错乱 | **36** | R2-16 ~ R2-51 |
| ⚪ **S3** | 前端可用性与健壮性 | **9** | R2-52 ~ R2-60 |
| | **合计** | **60** | 另有 36 条已核实为阴性（N-01 ~ N-36） |

### 1.2 十句话结论

1. **当前这棵树 `import butler.app` 直接失败**（`ModuleNotFoundError`），因为 `butler/tts/nowvoice_client.py` 不存在——启动链 `app.py:85 → manager.py:18 → nowvoice_tts.py:13` 断裂。（V-1 实测）
2. **用户建的所有 cron 定时任务 100% 不执行**：`sync_job` 在 APScheduler 的线程池里调 `asyncio.get_event_loop()`，必然 `RuntimeError`，只留一行 apscheduler 日志。（V-2 实测）
3. **决策层心跳 job 被 `next_run_time=None` 钉死，永不触发**，而 `decision_cfg.enabled` 默认就是 `True`。（V-3 实测）
4. **TTS 第 10 次播报后永久静音**：`PushGuard.tts_pop()` 与 `reset()` 全仓**各 0 个调用者**，队列只进不出，过载闩锁每次调用都续期 300s。
5. **前端"指令中心"整页失效**：全文件唯一的 `x-data` 是空的 `<body>`，464 处都写 `$store.app.`，唯独该页用裸标识符 ⇒ 全部 `ReferenceError`。
6. **永远无法登出**：`@click="$store.app.logout()"` 调用的方法在被加载的 JS 里不存在（它只存在于两个未被引用的死副本里）。
7. **`data/config.json` 一旦解析失败，下一次改任何设置就会把全部家人档案清空**——`_load_cfg()` 吞异常返回 `{}`，`_save_cfg()` 非原子覆写。
8. **豆包 webhook 的去重 hash 在处理之前就落表**，处理中途抛 500 后，上游重试命中 duplicate 直接返回 `ok:true` ⇒ **指令永久丢失且上游以为成功**。
9. **9 处定位条件恒为 False**（`get_snapshot` 不存在，实为 `snapshot`），8 处调用方全部被 `except: logger.debug` 吞掉。
10. **容器无 `TZ`，同时存在三套时间语义**（显式 Asia/Shanghai / 朴素 `datetime.now()` / 硬编码 `+8`）⇒ "每日""6-10 点晨起窗口"等条件偏移 8 小时。

### 1.3 本轮最重要的元观察

第一轮的结论是"**降级得太安静**"。本轮补充第二条：

> **这套代码里，"写好了的代码"和"接上了线的代码"是两回事。**
>
> `PushGuard` 的队列、熔断、审计写得很完整，但出队函数零调用；`CronTaskExecutor` 的调度逻辑写得很完整，但 job func 在线程池里必然抛错；`ConfigReloader` 写出来了但全仓无调用点；`store/db.py:close()` 写出来了但除 `app.py:763` 外无人调用；`self_evolve.analyze_llm_traces` 写出来了，调用方却 import 一个不存在的 `analyze_candidates`。
>
> **本轮 60 条发现里，至少 9 条是"实现完成但接线断裂"**——它们不会在 code review 里被发现，因为代码本身读起来是对的。这需要一类新的检测手段：**调用图连通性检查**，而不只是代码审查。

### 🔴 R2-02 用户创建的 cron 定时任务 **100% 不执行**（`sync_job` 线程池必然抛错）

**状态：V-2 实测复现 ✅**

**代码**（`butler/core/cron_task.py:670-689`）：

```python
async def job_func():
    await self.execute_task(skill)

# 用线程安全的方式调度协程
def sync_job():
    loop = asyncio.get_event_loop()                 # :675  ← 灾难点
    asyncio.run_coroutine_threadsafe(job_func(), loop)

job = self.scheduler.add_job(sync_job, "cron", id=f"cron_task_{skill_id}", ...)
```

**机理**（三段证据链）：

1. `add_job(sync_job, ...)` 传的是**普通函数**，不是协程。
2. 项目用 `AsyncIOScheduler`（`app.py:517`）⇒ executor 是 `AsyncIOExecutor`。其实现为：
   ```python
   # apscheduler/executors/asyncio.py
   if iscoroutinefunction_partial(job.func):
       f = self._eventloop.create_task(coro)
   else:
       f = self._eventloop.run_in_executor(None, run_job, ...)   # ← 走默认线程池
   ```
   已实测该源码。`sync_job` 不是协程函数 ⇒ **在 `asyncio_N` 线程池线程里执行**。
3. 线程池线程没有事件循环 ⇒ `asyncio.get_event_loop()` 抛 `RuntimeError`。异常被 `apscheduler.executors.base.run_job` 的 `except` 捕获，只调 `self._logger.error('Error running job %s', ...)`。

**实测**（原样复刻该函数，interval 1s，跑 2.6s）：

```
ran = []
ERROR:apscheduler.executors.default:Job "sync_job (trigger: interval[0:00:01]) raised an exception"
RuntimeError: There is no current event loop in thread 'asyncio_0'.
```

**触发场景**：任一 `brain.type == "cron_task"` 且 `status == "enabled"` 的技能到达 cron 时间。`POST /api/triggers/{id}/run` 手动触发走 `health_api.py:120 job.func()` 同样抛。

**后果**：

- **用户建的定时任务一次都不会跑**——这是产品的主要功能之一。
- 无 `mark_error`、无 registry 记录、`/api/triggers/health` **不报错**（见 R2-25 的假绿机制）。
- 唯一痕迹是 apscheduler 自己的一行 `ERROR`，**没有 traceback 输出到业务日志**（`_run_job_error` 只 log logger，`run_job` 内部捕获）。
- 与第一轮的 P0-5（18 个内置任务 + `sched.start()` 共用一个 try）叠加：内置任务用的是 `reg.wrap_scheduler_job` + `run_coroutine_threadsafe`（`app.py:518`），**那条路是对的**；坏的是 `CronTaskExecutor` 这条**独立的、后加的**路径。

**修复**：把 `sync_job` 改为 `async def`（apscheduler 3.10.4 的 `iscoroutinefunction_partial` 分支会直接 `create_task`），或改用与 `app.py:518` 相同的 `reg.wrap_scheduler_job` 模式（先把 `_main_loop` 保存好）。

**附加**：`cron_task.py:175` 的 `test_api` 里有**同样一行** `loop = asyncio.get_event_loop()`，但它先判 `loop.is_running()` 再开线程——那一处的失败模式不同，见 R2-16。

### 🔴 R2-03 决策层心跳 job 被 `next_run_time=None` 钉死，**永不触发**

**状态：V-3 实测复现 ✅**

**代码**（`butler/app.py:560-567`）：

```python
_hb = reg.wrap_scheduler_job("sched:decision_heartbeat",
        lambda: asyncio.run_coroutine_threadsafe(_heartbeat_tick(rt), _main_loop))
reg.register("sched:decision_heartbeat", "scheduler", "决策层心跳",
             expected_interval_sec=decision_cfg.interval_minutes * 60, ...)
sched.add_job(
    _hb, "interval", minutes=decision_cfg.interval_minutes,
    id="decision_heartbeat",
    next_run_time=None,        # ← :567
)
```

**机理**：apscheduler 的 `Job._modify` 把 `next_run_time=None` 写入 job；`MemoryJobStore.get_due_jobs` 对 `timestamp is None` 直接 `continue`；`get_next_fire_time` 同样跳过 ⇒ **job 挂在 store 里但永不被调度**。

**实测**（interval 1s）：

```
hits with next_run_time=None -> 0
hits without               -> 2
```

**触发场景**：默认路径。`decision_cfg.enabled` 默认 `True`（`decision/config.py:70`），`interval_minutes` 参与 job 注册。`app.py:531` 的 `table_retention` 在 `retention_days<=0` 时也用同样写法不注册——那处是有意的；**这一处不是**。

**后果**：

- 决策层 `heartbeat` 事件**完全不发** ⇒ 依赖 heartbeat 的 trigger 规则链路静默失效。
- `health_api.py:112` 的"手动执行一次" `modify_job(next_run_time=None)` 对该 job 也是 no-op（因为已经是 None）。
- 更隐蔽：`reg.register(...)` 已把它登记进 registry，`expected_interval_sec` 有值 ⇒ **`/api/triggers/health` 把它当活的来算 staleness**，产生一条永远修不好的假告警（与 R2-13、R2-25 同族）。

**修复**：删掉 `:567` 的 `next_run_time=None`。若本意是"先不跑、等条件满足"，应使用 `sched.pause_job()` 或根本不要 `add_job`。

> **同类排查建议**：全树 grep `next_run_time=None`。目前命中 `app.py:567`（本条）与 `health_api.py:112`（有意的 pause 语义）。前者是 bug，后者是用 API 的"意外刹车"达成 pause——**这是个危险的惯用法**，见 R2-02 修复后的第一轮 P2-3 一并处理。

### 🔴 R2-04 TTS 第 10 次播报后**永久静音**：`tts_pop()` 与 `reset()` 各 0 个调用者

**状态：代码取证 ✅（`tts_pop` 全仓命中数 = 1 = 仅定义处；`reset()` 全仓命中数 = 1 = 仅定义处）**

**四段证据**：

1. **入队**（`guard/push_guard.py:242-332`，`check_tts`）：
   - `:310` `self._tts_queue.append(item)`（或 `:308` insert）
   - `:313` `while len(self._tts_queue) > TTS_QUEUE_MAX:` 把长度**裁剪到恰好 10**
   - `:325-327` `if len(self._tts_queue) >= TTS_QUEUE_MAX:` → `self._tts_overload_until = now + TTS_OVERLOAD_PAUSE`（`TTS_QUEUE_MAX=10`、`TTS_OVERLOAD_PAUSE=300`，`:58-59`）
2. **出队**（`:334-340` `def tts_pop`）：**全仓 0 个调用者**（`grep tts_pop` 唯一命中即定义处）
3. **闩锁生效**（`:260-267`）：
   ```python
   if now < self._tts_overload_until:
       if PRIORITY_BYPASS_CIRCUIT.get(priority, False): return PASS   # 只有 critical
       return PushDecision(action=DECISION_DROP, reason=f"tts overload ({remaining}s)")
   ```
   而 `api/tts_routes.py:267` 传入的 priority 只有 `"warning"`/`"info"` ⇒ **不可穿透**
4. **落点**（`tts_routes.py:269-271`）：
   ```python
   if tts_decision.action == "drop":
       return ok({"spoken": False, "reason": "push_guard_drop", "detail": ...})
   ```

**自续期机理**：`tts_pop` 永不调用 ⇒ 队列长度停在 10 ⇒ 每一次新的 `check_tts` 都重新执行 `:326` 把 `_tts_overload_until` 推到 `now+300`。闩锁**每 5 分钟自我续期一次，永不到期**。

**唯一出口**：`push_guard.py:381` 的 `reset()` 会清 `_tts_overload_until = 0`，但**全仓 0 个调用者**（无路由、无重启钩子）。

**注意 `tts_unlock` 是被调用的**（`tts_routes.py:278,289`），但它只设 `self._tts_lock = False`——而 `_tts_lock` 只有 `tts_pop` 会设 `True`，所以它**恒为 no-op**。这是个重要的假线索：读代码会以为"出队/释放是接好的"。

**触发场景**：对 `POST /api/tts/speak` 发起第 10 次调用（PWA / Node-RED 主动播报常用此端点）。

**后果**：此后**所有非 critical 播报返回 `{"spoken": false, "reason": "push_guard_drop"}`**，直到进程重启。稳态是"每 5 分钟最多通过 1 条，且立刻重新闩锁"（因为第 11 条到第 N 条都会再次满足 `len >= 10`）。设备控制通知、早安简报、技能输出的语音播报**全部静默失败**，而返回体是 `ok:true`（HTTP 200）⇒ 调用方以为成功。

**附加**：`push_guard.py:10-15,83` 的注释声称"状态持久化到 SQLite"，实际只有审计表 `_init_db:93-119`；队列与闩锁是**纯内存**，重启即清零——这既是缺陷（重启成为唯一恢复手段），也解释了为什么现场"偶尔会自己好"。

**修复**：`tts_routes` 在播报完成后调用 `pg.tts_pop()`（并在 `finally` 里 `tts_unlock()`）；或直接把 `:325` 的 `>=` 改为按**时间窗内入队速率**判断，并给 `reset()` 接一个运维端点。

**模式**：

```python
_conn = c       # 先缓存
_init(c)        # 后初始化 —— 抛异常时它已经返回给所有人了
```

```python
    c = sqlite3.connect(...)
    with _lock: _conn = c   # :29-30
    _init(_conn)            # :31  ← 锁外执行 DDL
```

双重检查在锁外 ⇒ 两线程可同时进分支，各建一个连接，**后一个覆盖前一个，前一个泄漏**；`_init` 在锁外 ⇒ 两个连接并发 `ALTER TABLE ADD COLUMN target` ⇒ 第二个抛 `duplicate column name` ⇒ 叠加本条。`task_store.get_conn()` 则**完全没有锁**。

## 9. 结语

**第一轮的结论是"降级得太安静"。本轮的结论是：这套系统的故障面，主要不在"算法写错了"，而在"线没接上"。**

三条最有力的证据：

1. **`butler/tts/nowvoice_client.py` 根本不存在**，而 `app.py:85 → manager.py:18 → nowvoice_tts.py:13` 三段都是无保护的顶层 import ⇒ **`import butler.app` 直接失败**。这不是一个隐蔽的 bug，是一个**文件丢了**——而没有任何流程会在启动前发现它。
2. **`PushGuard` 写了完整的队列、熔断、审计、SQLite 持久化（注释里宣称的），但出队函数 `tts_pop()` 与恢复函数 `reset()` 各 0 个调用者** ⇒ 第 10 次播报后永久静音。读这段代码的人会以为它是接好的，因为**唯一被调用的 `tts_unlock()` 恰恰是个恒为 no-op 的假线索**。
3. **`sync_job` 在 apscheduler 的线程池里调 `asyncio.get_event_loop()`** ⇒ 用户建的定时任务 100% 不执行，而健康面板显示全绿（因为 `wrap_scheduler_job` 把"派发成功"当"执行成功"记账）。**功能完全没跑，系统却认为自己一切正常。**

这三条有一个共同属性：**它们都不会被 code review 发现**。因为：

- 第一条——代码看起来完全正常，缺的是别的文件。
- 第二条——每个函数单独看都正确，缺的是调用关系。
- 第三条——本地手写一段同步代码测不出问题，问题在 apscheduler 的**执行器分发语义**里。

**所以本轮最重要的一句话建议是：**

> 这个项目的下一步不是"修这 40 个 bug"，而是**建立三条能在 10 秒内发现它们的检查**：
> ① `python -c "import butler.app"`（拦 R2-01 类）
> ② 调用图连通性差集（拦 R2-04/06/11/12/13/33 类，共 9 条）
> ③ 真的跑 `pytest`（已有 192 个测试函数，包括一张能钉住 `sync_job` 形状的回归卡，**但从来没执行过**）
>
> 第一轮说"每个 P0 都能被一条 CI 检查拦住"。本轮把这句话变成了可执行的三条命令。
