async def _login(request: Request):
    try:
        body = await request.json()
    except Exception:

## 五、DP 那次 401 到底哪儿不对（逐条，能证的先说）

被审对象：`E:\NAS\DeskPilot\doc\DEV日志\回执-DP-20260921-B0.md`，模板原文在其 §「curl 命令模板（真值已 REDACTED）」（我 09:44Z 读到该文件 3,084 B）。他们的 T4 两步是：
```bash
curl -s -c cookie.txt -X POST -H "Content-Type: application/json" -d '{"user":"…","password":"…"}' http://192.168.2.200:8095/api/login
curl -s -o /dev/null -w '%{http_code}' -b cookie.txt http://192.168.2.200:8095/api/status
```

**P1（可证，是他们探针的真缺陷）：第一步没有状态码。**
第二条挂了 `-o /dev/null -w '%{http_code}'`，**第一条没挂**（`-s` 只压进度条，不改输出流），也没有 `ls -l cookie.txt` / `grep -c butler_auth cookie.txt`。⇒ **他们的读数里不存在"登录成功过"这件事的任何证据**。而 `Set-Cookie` 只在 200 分支发（`O:app.py:136-139`：`if not tok: return err("用户名或密码错误", 401)`，`429` 那条同理），登录一失败 jar 就是空的 ⇒ 第二步**退化成与 T1（无凭据）完全同形的请求**。他们的 T1 与 T4 读数一模一样（401×4）不是巧合，是这个形状下的必然。
⇒ **所以：T4 的 401 是一次 0 分母判定，它既不能证明 cookie 会话有效，也不能证明它无效。** 他们自己在注里也留了"或登录本身返回了非 200"，但没有把它落成读数。

**P2（可证，形状风险，不成立为因）：SameSite / Path / HttpOnly 都不会挡 curl。**
`M:app.py:139` 只显式给了 `httponly` 与 `max_age`，其余按 Starlette 默认 = `Path=/`、`SameSite=Lax`、无 `Secure`、无 `Domain`（host-only）。curl 的 `-b cookie.txt` **不看 SameSite/HttpOnly**（jar 里 `#HttpOnly_` 前缀照样回带），`Path=/` 覆盖 `/api/status`，`Secure` 未置所以 http 明文也发。⇒ **他们注里猜的"SameSite/Path/Domain 导致 jar 未回传"这条不成立**（这是把浏览器语义套到了 curl 上）。
⚠ 但 `HttpOnly` 有一条真实后果值得入账：**`document.cookie` 读不到它** ⇒ 任何"前端 JS 自己取 cookie 值拼头"的写法都不可能成立，这也从反面再钉一次 (a) 不成立。

**P3（候选，未验）：`-d` 的字段名与 `Content-Type` 对得上，但登录失败还有第二个入口 —— 429 自锁。**
`is_login_locked()`（`M:deps.py:262-268`，阈值 `:140-141` = **同 IP 5 次失败 / 锁 15 分钟**）在 `O:app.py:132-133` 被**先于口令校验**调用，返回的是 429 且**没有 `Set-Cookie`**。⇒ 一个探针连打 4 次 POST `/api/login`（他们 T4 就是 4 连采）时，如果前面有任何一次凭证不对，**它自己就能把这台源 IP 推进锁定，之后每次必然无 cookie**。这条不需要现网读数就成立为"风险"，但要定它为"因"还缺 P1 那条状态码。

**P4（候选，未验）：jar 是相对路径 `cookie.txt`。**
