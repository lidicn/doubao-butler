### 排除法（四条各留一把尺）

1. 持锁 pid == `docker inspect .State.Pid`（1910704 前 / 2770209 后），`/proc/locks` 落在 `-shm` inode 偏移 `120`（`WAL_WRITE_LOCK`）⇒ **外部持锁者出局**（候选 2 死，候选 1 活）。
2. 容器 13 线程，`D` 态 0，主线程 `do_epoll_wait` ⇒ **I/O 卡死在半个 WAL frame 上**出局。
3. WAL 尾帧解析：最后一帧是 COMMIT ⇒ 悬住那笔写从未落 WAL，页留在连接自己的缓存 ⇒ 与「事务未提交」同形，且解释了为何 `-wal` 可以整小时不动。
4. 全仓 18 处 `sqlite3.connect`，**10 条指向同一个 `butler.db`**、同进程；`store/db` 单例自己是受害者（`trigger_run persist failed` 走它）⇒ 持锁者是另外 9 条之一。全仓 **0 处显式 `BEGIN` / `isolation_level`** ⇒ 只可能是 python 隐式事务被漏掉的 `commit()` 悬住。

静态面（AST 两把尺互对）：**86 处写站点、`rollback` 出现 0 次**——「异常落在 execute 与 commit 之间 ⇒ 锁永不再放」是结构性的。三处启动补列（`add_column_if_absent`）都紧跟 `commit()`，已排除；DDL/`executescript` 会不会悬事务，用探针量过（probe46，NAS py3.11.2/sqlite3.40.1 与容器 py3.11.16/sqlite3.46.1 两套口径同结论）：`executescript_create / execute_create / alter_no_commit / executescript_dml / pragma_only` 全 `in_transaction=False` 且第二条连接 `BEGIN IMMEDIATE=OK`，唯一能悬住的是「未提交的 DML」（C 组：`in_transaction=True` + 第二条连接 BUSY）。**⇒ 本档此前把候选 1 说成「机制仍未定」的那格，现在是「机制已定、肇事行未定」。**
