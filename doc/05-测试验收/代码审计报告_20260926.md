## 1. 风险总览

### 1.1 严重度分布

| 严重度 | 数量 | 定义 |
|---|---|---|
| 🔴 **P0 严重** | 10 | 可直接导致数据泄露、权限完全失守、功能永久失效或宿主失守 |
| 🟠 **P1 高危** | 19 | 显著削弱纵深防御，或造成可利用的信息泄露 / 稳定性风险 |
| 🟡 **P2 中危** | 74 | 局部缺陷、可维护性问题，或需要额外前置条件才可利用 |
| ⚪ **P3 低危** | 14 | 代码卫生、可访问性、文档漂移等改进项 |
| ✅ **正面发现** | 14 | 值得保持并推广的做法 |

### 1.2 十句话结论

1. **管理员口令以明文形式硬编码在 13 个前端 JS 文件中**，而 `static/` 是无鉴权静态挂载 → 任何能访问 `:8095` 的人 `curl` 一下就拿到全站管理员凭证。
2. 这个凭证之所以能直接用，是因为 `deps.py:254` 的 `ALLOW_PASSWORD_AS_BEARER` **默认为 `true`**——登录口令本身就是有效 Bearer，绕过登录页、绕过锁定、绕过审计。
3. 口令本身是 5 字符供应商默认值，且**用户名与口令同值**。
4. `app.py:316` 用了 `os.environ` 但**模块顶层没有 `import os`** → 百度 TTS 自诞生起就从未初始化成功过，且只在启动时留一行 warning。
5. `dialog.py:389` 用了 `self.rt.ha`，但 `DialogManager.__init__` **从未给 `self.rt` 赋值** → HA 设备控制经 simple_rules 路径必然抛 `AttributeError`，被吞掉后对用户回答"刚才出了点问题"。
6. `requirements.txt` **缺 `aiohttp`**，而 5 个模块在 import 它 → 小爱语音唤醒、HA 事件流、AF ask 桥、百度 TTS、每日 LLM 简报，**五条链路在容器里全部静默死亡**。
7. 18 个定时任务的注册 + `sched.start()` 被包在**同一个 `try`** 里 → 任意一处抛异常，整个调度器不启动、`rt.scheduler` 永为 `None`、一个任务都不跑，而日志只有一行 "scheduler unavailable"。
8. LLM 创建的技能 `approval` **默认就是 `approved`**，`create_draft` 不覆盖它 → 沙箱与审批门在最主要的技能创建路径上**完全失效**；叠加 `tool_sequence` 的 `brain.steps` 不做校验，LLM 可自造任意工具调用序列。
9. `docker_compose_up` 把 LLM 给的字符串直接拼进 `docker compose -f <宿主路径>/docker-compose.yml up -d` → **宿主 root 代码执行原语**。目前被一个"漏写 `await`"的 bug 意外掩盖——**谁按测试卡的建议补上 `await`，谁就打开了这个洞**。
10. 质量体系整体是**人工的、非强制的**：`gates.sh` 不跑 pytest、不扫密钥；无 CI、无 pre-commit；`pytest.ini` 声明的覆盖率门禁因缺 `pytest-cov` **根本无法启动**。

### 🔴 P0-1 管理口令明文硬编码在 13 个前端 JS 中，叠加「口令即 Bearer」默认开启

**位置**

| 文件 | 行号 |
|---|---|

**已复验**：全树 `Bearer <值>` 正则扫描共 32 处命中，去重后**唯一取值**为长度 12 的 `Bearer a***n`（即 5 字符口令），与 `.env:9` 的 `BUTLER_WEB_PASSWORD` 一致。

**为什么这一条是 P0 而非 P1**——三个条件同时成立，任意一个不成立都能挡住它：

1. **口令值本身**是 5 字符供应商默认值，`.env:8` 的 `BUTLER_WEB_USER` 与之同值（`doc/生态链/凭据台账-20260921.md:45` 原文："用户名与口令同值"）。
2. **`butler/static/` 是无鉴权静态挂载**：`app.py:234` `Mount("/", StaticFiles(STATIC_DIR, html=True))`，**没有** `guard()` 包装。
3. **`ALLOW_PASSWORD_AS_BEARER` 默认 `true`**：`butler/api/deps.py:254`

   ```python
   allow_pw_bearer = os.environ.get("ALLOW_PASSWORD_AS_BEARER", "true").lower() != "false"
   ```

   `.env` / `docker-compose.yml` / `.env.example` **均未设置该变量** → 生产走默认值 `true`。

**利用链**：`curl http://<host>:8095/js/app.js | grep Bearer` → 拿到口令 → `Authorization: Bearer <口令>` 直打任意 226 个受保护端点。**完全绕过**：登录表单、5 次/15 分钟登录锁定（`deps.py:262-268`，只挂在 `POST /api/login` 上）、会话表与 7 天过期、`butler_auth` cookie。`deps.py:243` 的 `bearer_locked()` 只在 20 次失败/60 秒后才刹车，**正确凭证不计数**。

**次生问题**：`deps.py:254` 只认字面量 `"false"`。写 `ALLOW_PASSWORD_AS_BEARER=0` / `=no` / `=off` / `=False `（带尾空格）**都不会关闭它**。项目其他所有布尔开关都走 `config.py:31-37` 的 `_env_bool`（接受 `1/0/true/false/yes/no/on/off`），**唯独这个绕过 helper 且不在 `Settings` 上**——一个纯手写的、与其他 40 个开关行为不一致的解析。

**修复建议（按优先级）**

1. **立即**：前端全部改为只用 cookie 会话，删除所有 `Authorization` 头。
2. **立即**：`ALLOW_PASSWORD_AS_BEARER=false` 写入 `.env`（必须用字面量 `false`），并把 `deps.py:254` 改为走 `_env_bool`。
3. **立即**：轮换 `BUTLER_WEB_PASSWORD`。`doc/口令轮换执行规范-v1.md` 与 `_投递/口令轮换单-20260921.md` 已备好 20 字符新值与 23 处替换点，但**盘面证据显示轮换未落地**：`.env:9` 仍是 5 字符。
4. 删除 `butler/static/index.html:691` 的鉴权示例展示。
5. 加一条 CI 规则：`static/**` 与 `dashboard_pwa/**` 中出现 `Bearer ` 字面量即失败。

> **扫描方法论警告（重要）**：本次审计的首轮关键词扫描**漏掉了全部 13 处**，因为常规启发式是 `Bearer [A-Za-z0-9]{8,}`，5 字符口令不匹配长度下限。**任何带长度下限的密钥扫描器都会漏掉这个 bug。** 建议扫描规则改为 `Bearer\s+\S+`（不设长度下限）+ 值去重。

### 🔴 P0-2 `app.py` 使用 `os.environ` 但未导入 `os` → 百度 TTS 永久静默失效

**位置**：`butler/app.py:316-317`

```python
try:
    from butler.core.tts_baidu import BaiduTTS
    rt.baidu_tts = BaiduTTS(
        api_key=os.environ.get("BAIDU_TTS_API_KEY", ""),        # ← line 316
        secret_key=os.environ.get("BAIDU_TTS_SECRET_KEY", ""),  # ← line 317
    )
    logger.info("baidu tts initialized")
except Exception as e:
    logger.warning("baidu tts init failed: %s", e)
    rt.baidu_tts = None
```

**已复验**：`app.py` 全部模块级 import 逐行列出（第 2–16 行 + 18–88 行的 `butler.*` 块）——**没有 `import os`**。全文件唯一一处 `os` 绑定是第 432 行的 `import os as _os`（函数局部，且在使用点之后 116 行才执行）。

**后果链**：`NameError: name 'os' is not defined` → 被 313 行的 `try` 捕获 → 321 行打一条 warning → 322 行 `rt.baidu_tts = None`。**百度 TTS 自这段代码落地起就从未成功初始化过。** 唯一证据是启动时一行 `baidu tts init failed: name 'os' is not defined`。

**二次隐藏**：即使修好这行，容器里**依然起不来**。`butler/core/tts_baidu.py:11` `import aiohttp`，而 `aiohttp` 不在 `requirements.txt`（已复验）→ `ModuleNotFoundError` 在 `os` 那一行**之前**就抛出。**只修 P0-2 不足以恢复百度 TTS，必须同时修 P0-4。**

**同类扫描结论**：AST 级未定义名扫描覆盖 `app.py` / `dialog.py` / `agent.py` / `cron_task.py` / `triggers/engine.py`，未定义名共 4 处，详见 P0-2、P0-3 与 P2-1（`repo.py:155` 的 `sqlite3`）、P2-4。

**修复**：`app.py` 顶部加 `import os`；`app.py:432` 的 `import os as _os` 改为复用模块级 `os`；把 `except Exception` 收窄到只捕获 `ImportError`/`OSError`，让 `NameError` 这种编码错误在启动时**炸出来**而不是被降级为 warning。

**位置**：`butler/core/dialog.py:389-390`

**已复验**：全文件 `self.rt` 只出现在 389、390 两行。`DialogManager.__init__`（`dialog.py:41-73`）**从未给 `self.rt` 赋值**；该类其余 6 处拿 runtime 用的都是模块函数 `rt = get_runtime()` 的局部惯用法（197、215、245、453、592、636 行）。

**失败模式**（这是本条的全部要害）

**修复（结构性）**——把单个大 `try` 拆成三层：

```python
sched = AsyncIOScheduler(timezone="Asia/Shanghai")
for job in ALL_JOBS:              # 每个作业独立注册
    try:
        reg.register(...); sched.add_job(...)
    except Exception as e:
        logger.error("job %s registration failed", job.id, exc_info=True)
        rt.startup_degraded.append(f"job:{job.id}")   # 降级可见
try:
    sched.start()
except Exception as e:
    logger.error("scheduler start FAILED", exc_info=True)   # 必须是 error，不是 warning
    rt.startup_degraded.append("scheduler:not_started")
rt._sched = rt.scheduler = agent.scheduler = sched
```

`sess.start()` 失败必须是 `logger.error` 且必须让 `/api/health` 反映——**它不是一个"可选功能"**。

**代价估算**（中文回复，40 字 → 39 bigram → 约 600-900 B JSON/行）：

| 场景 | 窗口内行数 | 每次调用解析量 | 结论 |
|---|---|---|---|
| 20 次/天 | 140 | ~120 KB，~140 次集合运算 | 可忽略 |
| 200 次/天（活跃家庭 + 主动 + 技能） | 1,400 | ~1.1 MB，**每次开口都在工作线程上解析** | 可接受但浪费 |
| 1,000 次/天（失控的 trigger 或 job storm） | 7,000 | ~6 MB/次 ⇒ 单次 `is_duplicate` 耗时到秒级 | **不可用** |

**修复**：`recent_fingerprints` 加 `LIMIT 500`；或按 `text_hash` 前缀分桶后再做 Jaccard；相似度循环加提前退出（长度差超阈值即跳过）。

## 11. 结语

**这个项目的服务端 Python 层质量明显高于它的运维与前端层。**

具体地说：`config.py` 的"必需密钥缺键即启动失败"设计（正面 11）、`deps.py` 的 fail-closed 判定顺序与正确的会话存储（正面 1、2）、`newapi.py` 与全部 store 的彻底参数化（正面 5）、`notify_routes.py` 头像上传的四层校验（正面 4）、主 WebUI 的 279 个 `x-text` 零 HTML sink（正面 8）、以及 191 个模块里 `eval`/`exec`/`pickle`/`shell=True` 全部为零（正面 6）——这些都是**有经验的人写出来的代码**。

**但整个系统的外围（部署、密钥管理、前端鉴权、可观测性、CI）是手工的、一次性的、且在日志上看不见的。** 四个最严重的问题——P0-1（口令进前端）、P0-4（缺依赖导致 5 条链路静默死亡）、P0-5（调度器单点）、P0-6（审批门默认放行）——**每一个都可以被一条 CI 检查或一次部署后冒烟测试拦住**，而它们全部通过了人工 review 走到了今天。

**最值得记住的一条元教训**：这个项目里最危险的缺陷**不是"写错了"，而是"降级得太安静"**。`NameError` 被 `except Exception` 变成一行 warning；`AttributeError` 被吞掉后管家对用户说"刚才出了点问题"；`ImportError` 让 5 条功能链路集体消失而日志只有 `No module named 'aiohttp'`；调度器整体瘫痪被写成 `scheduler unavailable`；健康面板对什么都不做的作业报绿。

**建议的第一条工程原则**：把这个代码库的原则从"永不崩溃退出"（`README.md:72`）改成 **"永不静默降级"**——任何 `except Exception: logger.warning(...)` 都必须在 `/api/health` 上留一个可见的痕迹。**降级不是不能有，但不能只有日志。**
