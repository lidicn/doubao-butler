# MiMo 辅助快速重构指南 —— DB tools.py 拆分

**创建时间**: 2026-09-23
**适用项目**: doubao-butler (DB)
**参考经验**: Memory Agent (MA) 已用 MiMo 完成身份融合、行为洞察框架等模块重构

---

## 一、为什么用 MiMo 重构

MiMo UltraSpeed 的优势：
- **速度快**：58k token 代码生成约 108 秒，是普通模型的 3-5 倍
- **代码质量高**：生成的代码一次通过率高（MA 经验：身份融合模块一次通过）
- **适合"出参考方案"**：让 MiMo 出设计稿/参考代码，我们学习吸收后自己落地，而不是直接抄

**不适合 MiMo 的场景**：
- 心脏模块（如 dialog.py）—— 改不好就崩，需要人工逐行把控
- 还在快速迭代的模块 —— 重构完马上又要改
- 概念混乱但不影响运行的模块 —— 命名问题优先级低

## 二、MA 验证过的工作流

### 步骤 1：写前置需求稿（关键！）

MiMo 新对话没有记忆，必须把所有上下文一次性给全。需求稿格式：

```markdown
# 重构目标：<模块名>

## 1. 现有代码（完整内联）
<把要重构的文件完整贴进来，不要省略>

## 2. 项目上下文
- 技术栈：<Python/Node/...>
- 框架：<FastAPI/...>
- 目录结构：<关键目录说明>
- 依赖关系：<这个模块被谁引用，引用了谁>

## 3. 重构目标
- <目标1>
- <目标2>

## 4. 边界定义（必须明确）
- 保留什么：<接口签名/外部依赖/配置项>
- 删除什么：<死代码/重复函数>
- 不碰什么：<心脏模块/数据 schema>

## 5. 拆分方案（如果是拆分）
- 新文件结构：<目录树>
- 每个文件的职责：<一句话>
- 导出方式：<__init__.py 统一导出 / 显式导入>

## 6. 测试要求
- 单元测试：<哪些函数需要测试>
- 集成测试：<哪些链路需要验证>
- 回归验证：<怎么确认没破坏现有功能>

## 7. 输出要求
- 每个文件单独代码块
- 包含完整的 import 语句
- 包含 docstring 和类型注解
- 不要省略任何函数体
```

### 步骤 2：贴进 MiMo 新对话

- **必须新开对话** —— MiMo 对话有 token 上限，旧对话上下文会挤占生成空间
- 一次只给一个重构任务 —— 贪多会导致输出不完整（MA 验证过：一个对话塞两个设计 = 两个都半成品）
- 需求稿控制在 MiMo 输入上限内 —— 如果代码太长，先压缩（去空行/去注释/合并行），或者分两次给

### 步骤 3：提取 MiMo 输出

**MA 踩过的坑**：
- ❌ 自动提取脚本（油猴/JS）在 MiMo 页面报 `SyntaxError: Invalid or unexpected token` —— MiMo 页面有反作弊机制
- ✅ **手动提取**：一页页复制代码块，虽然慢但可靠
- ✅ 提取后先存到临时文件，再逐文件 review

### 步骤 4：学习吸收，不要直接抄

MiMo 出的是**参考代码**，不是最终代码。必须：
1. 逐文件 review —— 确认逻辑正确、没有幻觉
2. 适配项目规范 —— 命名风格、错误处理、日志格式
3. 保留原有接口 —— 外部调用方不能断
4. 补充测试 —— MiMo 出的测试可能不够，需要补

### 步骤 5：逐步迁移，每阶段验证

- 不要一次性全量替换 —— 风险太高
- 先建新文件，再改引用，最后删旧文件
- 每完成一个阶段跑一次测试
- MA 经验：行为洞察重构分了 3 个 Phase，每个 Phase 都验证后才继续

## 三、DB tools.py 拆分具体方案

### 现状

| 文件 | 行数 | 问题 |
|---|---|---|
| `core/tools.py` | 1941 | 最大的 god class，全是简单工具函数堆一起 |
| `tools.py`（根目录） | 1050 | 与 core/tools.py 功能重叠 |

**合计约 3000 行**，预计合并去重后可砍掉 800-1000 行死代码。

### 拆分目标

```
butler/tools/
├── __init__.py          # 统一导出（保持向后兼容）
├── devices.py           # HA 设备控制（灯/空调/电视/风扇）
├── weather.py           # 天气查询（彩云）
├── query.py             # 简单查询（时间/日历/提醒）
├── deskpilot.py         # DeskPilot 对接
└── registry.py          # 工具注册表（LLM function calling schema）
```

### 前置需求稿模板（直接用）

```markdown
# 重构目标：butler tools.py 按域拆分

## 1. 现有代码（完整内联）

### core/tools.py（1941 行）
<完整贴入>

### tools.py（根目录，1050 行）
<完整贴入>

## 2. 项目上下文
- 技术栈：Python 3.11+
- 框架：doubao-butler 自研框架
- 目录结构：butler/ 是主包，core/ 是核心模块
- 依赖关系：
  - tools.py 被 dialog.py、skills/、agent/ 引用
  - core/tools.py 被 core/ 内其他模块引用
  - 两份文件功能重叠，需要合并去重
- 外部依赖：Home Assistant API、彩云天气 API、DeskPilot API

## 3. 重构目标
1. 把 core/tools.py 1941 行按域拆成 6 个文件
2. 删除根目录 tools.py（1050 行），功能合并到新位置
3. 合并重复函数，砍掉死代码
4. 保持所有外部接口不变（__init__.py 统一导出）

## 4. 边界定义
- 保留：所有工具函数的签名和返回值格式
- 保留：LLM function calling schema（registry.py）
- 删除：两份文件中重复的函数
- 删除：已废弃未使用的函数
- 不碰：dialog.py（心脏模块）
- 不碰：数据 schema 和配置文件

## 5. 拆分方案

### 新文件结构
```
butler/tools/
├── __init__.py          # 统一导出，保持 from butler.tools import xxx 兼容
├── devices.py           # HA 设备控制（灯/空调/电视/风扇/窗帘）
├── weather.py           # 天气查询（彩云 API）
├── query.py             # 简单查询（时间/日期/日历/提醒/倒计时）
├── deskpilot.py         # DeskPilot 对接（远程桌面控制）
└── registry.py          # 工具注册表（LLM function calling schema 生成）
```

### 每个文件的职责
- devices.py：所有与 HA 设备交互的函数（开关/调温/换台/风速）
- weather.py：天气查询、空气质量、生活指数
- query.py：时间查询、日期计算、日历事件、提醒事项
- deskpilot.py：DeskPilot API 封装（远程执行/截图/文件操作）
- registry.py：把所有工具函数注册成 LLM function calling schema
- __init__.py：从各子模块 re-export，保持向后兼容

## 6. 测试要求
- 单元测试：每个工具函数至少 1 条 happy path + 1 条 error path
- 集成测试：HA 设备控制链路（mock HA API）
- 回归验证：
  1. `from butler.tools import <所有原导出名>` 全部成功
  2. `python -c "import butler.tools"` 无 ImportError
  3. 现有测试套件全部通过
  4. 根目录 tools.py 删除后无引用断裂

## 7. 输出要求
- 每个文件单独代码块，标注文件名
- 包含完整的 import 语句（包括相对导入）
- 包含 docstring 和类型注解
- 不要省略任何函数体
- __init__.py 必须列出所有 re-export 的名称
- registry.py 必须包含完整的 function calling schema 生成逻辑
```

## 四、MA 踩过的坑（DB 避坑）

| 坑 | 现象 | 解决 |
|---|---|---|
| 一个对话塞两个任务 | 两个都半成品，输出截断 | 一次只给一个重构任务 |
| 需求稿太长 | MiMo 输入超限，报错 | 先压缩代码（去空行/注释），或分两次给 |
| 直接抄 MiMo 代码 | 有幻觉、不匹配项目规范 | 逐文件 review，适配后再落地 |
| 一次性全量替换 | 破坏现有功能，回滚困难 | 先建新文件，再改引用，最后删旧文件 |
| 自动提取脚本 | MiMo 页面报 SyntaxError | 手动复制代码块，可靠但慢 |
| 不写测试 | 重构后不知道有没有破坏 | 每阶段跑测试，FAIL→PASS 出证 |

## 五、执行节奏建议

### Phase 1：建新文件 + 合并去重（MiMo 出参考）
- 写前置需求稿 → MiMo 出 6 个新文件的参考代码
- 手动提取 → 逐文件 review → 适配项目规范
- 新文件放到 `butler/tools/`，**不删旧文件**
- 验证：`import butler.tools.devices` 等全部成功

### Phase 2：改引用 + 删旧文件
- 把所有 `from core.tools import xxx` 改成 `from butler.tools import xxx`
- 把所有 `from tools import xxx` 改成 `from butler.tools import xxx`
- 确认无引用断裂后，删除 `core/tools.py` 和根目录 `tools.py`
- 验证：现有测试套件全部通过

### Phase 3：补测试 + 清理
- 给新拆分的模块补单元测试
- 清理 __init__.py 中不需要的导出
- 跑全量回归测试
- 验证：覆盖率不低于重构前

## 六、如何判断 MiMo 输出质量

MA 经验：MiMo 生成的代码**一次通过率约 70-80%**，剩下的需要人工修。

**快速检查清单**：
1. ✅ import 语句完整吗？有没有遗漏的相对导入？
2. ✅ 函数签名和原文件一致吗？（参数名/默认值/返回类型）
3. ✅ 有没有幻觉函数？（MiMo 可能编造不存在的依赖）
4. ✅ 错误处理一致吗？（异常类型/日志格式/返回值）
5. ✅ 配置项读取方式一致吗？（config.xxx / env var）
6. ✅ 有没有引入新的外部依赖？（需要 pip install 的）

**如果以上 6 条都过，基本可以直接用。**

## 七、MiMo 输入上限技巧

MiMo 对话框有输入字符上限（DB 实测：约 N 个 0）。如果代码太长：

1. **压缩代码**：
   - 去掉空行
   - 去掉注释（MiMo 能从函数名推断用途）
   - 合并短行
   - 用 `;` 合并简单语句

2. **分两次给**：
   - 第一次给 core/tools.py
   - 第二次给根目录 tools.py + 拆分要求
   - MiMo 会在同一会话内记住上下文

3. **只给关键部分**：
   - 函数签名 + docstring（不给函数体）
   - 让 MiMo 根据签名重新实现
   - 适合"重写"而不是"迁移"的场景
