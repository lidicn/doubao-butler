## 二、任务-模型匹配指南

### 2.1 按任务复杂度选择

| 任务类型 | 推荐模型 | 理由 |
|---|---|---|
| **架构设计/技术选型** | `power-chat` > `architect-chat` | 需要全局视野和深度推理 |
| **代码审查/安全审计** | `power-chat` > `reviewer-chat` | 漏了安全漏洞就是事故 |
| **核心 API 开发** | `backend-dev-chat` | 中等能力足够，性价比高 |
| **前端 UI 开发** | `frontend-dev-chat` | 样式调整不需要太强推理 |
| **Bug 修复（简单）** | `backend-dev-chat` | 定位+修复，中等能力够用 |
| **Bug 修复（复杂）** | `power-chat` > `reviewer-chat` | 根因分析需要强推理 |
| **测试用例编写** | `tester-chat` | 格式活，便宜模型够用 |
| **文档撰写** | `docs-chat` | 格式化工作，不需要强模型 |
| **代码注释生成** | `docs-chat` | 简单重复工作 |
| **CI/CD 配置** | `devops-chat` | 标准化工作流 |

---

### 2.2 按任务紧急度选择

| 紧急程度 | 推荐模型 | 理由 |
|---|---|---|
| **紧急（生产事故）** | `power-chat` | 速度优先，确保正确 |
| **较急（当天完成）** | `backend-dev-chat` / `frontend-dev-chat` | 平衡速度与质量 |
| **不紧急（一周内）** | `tester-chat` / `docs-chat` | 成本优先，慢慢做 |

---

### 2.3 按上下文长度选择

| 上下文长度 | 推荐模型 | 理由 |
|---|---|---|
| < 8K tokens | 任意模型 | 都够用 |
| 8K - 32K tokens | 中端/高端模型 | 低端模型长上下文差 |
| > 32K tokens | `power-chat` / `pm-chat` | 强模型长上下文能力好 |

## 五、使用规范

### 5.1 自动选择 vs 手动指定

**默认行为**：系统根据任务类型自动选择最合适的模型

**手动指定**：如果对任务有特殊判断，可以手动指定模型

**示例**：
```python
# 自动选择（默认）
agent.run_task("修复登录 Bug")

# 手动指定用强模型
agent.run_task("修复登录 Bug", model="power-chat")

# 手动指定用便宜模型
agent.run_task("生成 API 文档", model="docs-chat")
```

---

### 5.2 升级与降级

**什么时候升级**：
- 中端模型输出质量不达标 → 升级到高端
- 低端模型搞不定 → 升级到中端

**什么时候降级**：
- 高端模型输出太啰嗦 → 降级到中端
- 任务比预期简单 → 降级到低端

---

### 5.3 并发控制

| 模型级别 | 建议并发数 |
|---|---|
| DSH power-chat | ≤ 2 |
| FFL 高端（kimi-k3） | ≤ 2 |
| FFL 中端（deepseek-v4-flash） | ≤ 4 |
| FFL 低端（agnes-2.5-flash） | ≤ 8 |

**总并发**：不超过 16 个 Agent

## 七、FAQ

### Q1：为什么不全部用最强的模型？
A：成本不划算。80% 的任务用中端模型就能搞定，用最强的是浪费。而且最强的模型并发有限，全用会排队。

### Q2：怎么判断任务该用哪个级别？
A：问自己三个问题：
1. 这个任务做错了后果严重吗？（严重 → 升级）
2. 这个任务需要深度推理吗？（需要 → 升级）
3. 这个任务是重复劳动吗？（是 → 降级）

### Q3：DSH power-chat 和 FFL kimi-k3 哪个强？
A：各有千秋。power-chat 综合能力更强，kimi-k3 代码能力不错。核心任务优先用 power-chat，有备份方案用 kimi-k3。

### Q4：模型输出质量不稳定怎么办？
A：1) 检查是不是用错了模型 2) 升级到更高一级 3) 优化提示词 4) 重试一次
