# P0-10 容器安全加固计划

> 目标：把豆包管家容器的爆炸半径从「整台 NAS root」降到「只能操作白名单内的几个容器」

## 现状

| 项目 | 当前配置 | 风险 |
|---|---|---|
| 运行用户 | root（Dockerfile 无 USER） | 容器逃逸即 root |
| docker.sock | 直挂 `/var/run/docker.sock` | 容器内 RCE = 宿主 root |
| one-api.db | 读写挂载 | 全生态 LLM 凭证可篡改 |
| /nas/books | 全量挂载 | 家庭资料泄露面 |
| 安全加固 | 无 cap_drop / read_only / pids_limit | 缺少纵深防御 |

## 分阶段修复

### 阶段 1：docker.sock → 受限代理（最高优先级）

**做什么**
- 新增 `docker-socket-proxy` 容器，只放行 3 个操作：
  - `GET /containers/json`（查看容器列表）
  - `GET /containers/{id}/logs`（查看日志）
  - `POST /containers/{id}/restart`（重启容器）
- 禁止：create / build / delete / exec / networks / volumes / images
- 豆包管家的 `DOCKER_HOST` 指向代理而非直挂 socket
- 移除 `docker.sock` 和 `/usr/bin/docker` 挂载

**风险**
- `docker_compose_up` 工具会失效（需要 create/build，代理不允许）
- 但该工具已有白名单限制，实际运维很少用

**验证**
- `docker ps` 正常
- `docker restart doubao-butler` 正常（但管家自己重启自己会断，正常）
- `docker compose up` 返回 403

### 阶段 2：one-api.db 改只读 + 代码改 HTTP API

**做什么**
- one-api.db 挂载改 `:ro`
- `set_model_allocation` 从直写 SQLite 改为调 new-api HTTP 管理接口
- 确认 new-api 有对应的管理 API 和 token

**风险**
- new-api 可能没有模型分配的 HTTP 接口 → 需要调研
- 如果没有，保留读写挂载但加 advisory lock

### 阶段 3：非 root 用户 + 基础加固

**做什么**
- Dockerfile 加 `RUN useradd -r -u 10001 butler && USER butler`
- compose 加：
  - `cap_drop: [ALL]`
  - `security_opt: [no-new-privileges:true]`
  - `pids_limit: 512`
- 容器内 `chown -R 10001:10001 /app/tts /app/data`

**风险**
- bind mount 的 `/app/butler` 属主是 root，非 root 用户读没问题但写不了
- 但代码是 bind mount 的，运行时不需要写 `/app/butler`
- TTS 缓存和 SQLite 需要写权限，提前 chown

### 阶段 4：read_only 根文件系统

**做什么**
- compose 加 `read_only: true`
- 加 `tmpfs: [/tmp, /app/tts, /run]`
- 确认所有写路径都在 tmpfs 或 bind mount 里

**风险**
- 某些库可能在意外位置写临时文件
- 需要全面排查写路径

### 阶段 5：/nas/books 挂载收敛

**做什么**
- 确认哪些功能实际需要访问 /nas/books（audiobook？）
- 如果只需要特定子目录，改成精确挂载
- 如果不需要，直接移除

## 当前安全姿态

- 容器内 RCE → 非 root 用户（uid 10001），无任何 capabilities
- 根文件系统只读，无法篡改系统文件
- docker 操作只能通过代理（ps/logs/restart），拿不到宿主 root
- /nas/books 只读，家庭资料不可篡改
- one-api.db 仍为读写（唯一剩余风险点，需 new-api 侧配合）
