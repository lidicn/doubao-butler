## 0. 一句话结论

> 分层方向正确（大脑/感知/记忆/表达/编排），但存在**一个核心结构缺口：对话工具系统（硬编码 TOOL_SCHEMAS）与技能引擎系统（动态 skills）两套平行、互不相通**；

## 2. 核心缺口（按严重度排序）

### 2.1 【最大】对话工具系统与技能引擎系统两套平行、互不相通

- **对话**：`TOOL_SCHEMAS` 硬编码 9 个工具（control_device / analyze_camera / query_memory …），LLM 在对话中直接调用，**不经技能引擎**。
- **技能**：`skill/{id}/run` 动态引擎（JSON 配置可热增删），带安全阀 + 审计 + 角色续聊，但**只能被 NR/HTTP/MQTT 外部触发，对话触不到**。

后果：
1. 对话里"监控一下客厅"走硬编码 `analyze_camera`，**绕过了技能引擎的冷却/熔断/审计/角色续聊**——同一种能力存在两套实现、两套策略；
2. 技能系统新增的能力，对话永远用不上（LLM 不知道技能的存在）；
3. 技能的安全阀在"用户直接跟管家说"这条最高频的链路上完全失效——`control_device` 对话里可以任意控制 HA 设备，无冷却、无审批、无限流，只靠 LLM 判断。

修复方向（一个文件即可闭环）：
- 启动时枚举 `data/skills/*.json` → 动态生成 OpenAI function schema（name=技能 id，description=技能 prompt 摘要，parameters=ctx.payload 约定）→ 挂进 `TOOL_SCHEMAS` → `dispatch_tool` 收到技能名时转调 `runner.run()`（复用全部安全阀/审计/角色路由）。
- 硬编码工具中与技能重复的（analyze_camera ↔ camera_vlm 引擎、query_memory ↔ 记忆技能）**退役到技能系统**，TOOL_SCHEMAS 只保留技能不覆盖的原子工具。

### 2.2 引擎 = 任意代码，无沙箱隔离

- 插件引擎 `engine.py` 在 butler 进程内 `asyncio` 执行；出错/恶意引擎可拖垮整个容器（NAS 规范里"崩溃→churn→死机"是真实血泪）。
- **"让 agent 通过 MCP 建立新引擎"之前，必须先解决引擎隔离**：子进程/独立容器执行 + 超时 kill + 资源限制 + dry_run 不碰设备。autoflow 的"DSL → 编译 → 虚拟试跑 → 审批"是现成参照。
- 折中路线（推荐先做）：引擎执行加"看门狗"（asyncio.wait_for 超时 + 异常吞掉不崩进程）已具备一半；补齐"单引擎崩溃隔离"即可开放 agent 建引擎。

### 2.3 身份与能力边界缺失（全局单钥匙）

- 所有 `/api/*` 一个 `Bearer <redacted>`；泄漏 = 全屋可触发、可控制、可改配置。
- autoflow 已示范：身份码（af_）+ 按身份记账 + 一键吊销 + 三面权限（用户/专家/开发者）+ approve 只在 WebUI。
- butler 应对齐：技能级权限（谁/哪个角色/哪条来源可触发哪个技能）、敏感技能（设备控制、建 flow）需二次确认、操作审计已部分存在（skill_runs）但无"按身份追责"。

### 2.4 降级矩阵只写在文档里，没进代码

- 调研报告写了"ma 挂→退化 TV 人脸+HA 传感器；LLM 挂→ma /api/llm/ask；TV 挂→小爱→Bark"，但运行时没有显式状态与路由。
- 建议：每个技能声明 `fallbacks`（依赖不可用时的降级行为），runner 在依赖调用失败时按声明降级并在 `meta` 里标注降级路径（已有 `tv_offline` 降级 Bark 的先例，推广到所有依赖）。

### 2.5 技能结果没有记忆回流闭环

- ma 的记忆写回强制 `source_refs`（event:/insight:/activity: 前缀，防幻觉设计）。
- 技能产出（监控发现、食物热量、日程洞察）目前只进 `skill_runs`，没有自动转成 ma 的 insight/event 沉淀——**"管家看到的"和"管家记住的"是断开的**。
- 建议：引擎协议增加可选 `memory_hint`（内容 + 类型），runner 成功后按角色策略决定是否写回 ma（且先走 staging 需晋升，复用 ma 已有机制）。

## 3. 你问的 MCP：要，但要分三个方向

| 方向 | 做法 | 优先级 |
|---|---|---|
| **内部：技能→对话工具** | 见 §2.1，这不是 MCP，是系统内的 function calling 映射 | **P0** |
| **对外服务端：agent 建技能/引擎** | butler 暴露 /mcp（用户面：查/触发）+ /mcp-admin（管理面：建/改技能，需审批）；**引擎代码走沙箱**（§2.2） | P1（先沙箱后开放） |
| **对外客户端：接 autoflow** | autoflow 已暴露 /mcp（Streamable HTTP + af_ 身份码），butler 对话里"说一句话建 flow"= 工具 `autoflow_resolve_entity` / `autoflow_submit`，结果走 autoflow 审批闸，**butler 不持有 HA 令牌** | P1 |

**关键判断**：豆包/workbuddy/opencode 通过 MCP 建技能的价值是"技能创建自动化"，但**创建≠直接生效**——必须"LLM 提案 → schema 校验 → dry_run 试跑 → 审批 → 上线"。autoflow 的审批闸模型（AI 永远不能自己批准自己）应原样搬到 butler 的技能管理面。

## 4. Node-RED：保留，不脱离；但把"写 flow"从人手里交出去

**为什么不脱离**：
1. NR 是沉淀多年的设备适配资产（311 function / 138 xiaomi / 94 tts 节点），小爱/HA/Bark 链路全在里面，重写成本高且引入新 bug（X08A 直连循环问题就是"直连绕开 NR"的教训）；
2. NR 擅长事件汇聚、多协议 IO、可视化调试——但ler 不该也不擅长做这些；
3. 调研报告已定边界（NR=事件总线+设备适配，但ler=决策），方向正确。

**NR 真正的问题**：flow 不可版本化/不可测试/堆到 311 个 function 难维护——这不是"脱离 NR"能解决的，而是"flow 生成方式"的问题。autoflow 正是为此存在（DSL→编译→虚拟试跑→快照→一键下线）。

**结论**：三层各司其职——**autoflow 建 flow、NR 跑 flow、butler 决策表达**。不要脱离 NR；要防止的只是"NR 里堆对话判断逻辑"（职责漂移，应回流但ler）。

## 5. 最想增加 / 最值得移除

### 最想增加（按价值排序）
1. **技能系统→对话工具融合**（§2.1）：让"跟管家说一句话"能触达全部技能能力，且走同一套安全阀。
2. **技能自愈闭环**：运行失败 → 记录 → LLM 分析 → 生成修改建议（技能 JSON/引擎）→ 审批 → 上线。autoflow 已提"上报缺陷/自愈技能"概念，直接借鉴。
3. **MCP 管理面对外**（含引擎沙箱）：外部 agent 提案新技能，审批后生效。

### 最值得移除
1. **`/api/hello` 兼容端点及一切"旧路径 + 标准路径"并存的技术债**：随 NR flow 迁移完成后退役，避免两套系统长期并存。
2. **硬编码 TOOL_SCHEMAS 中与技能重复的工具**（analyze_camera、query_memory 等）：能力收敛到技能系统，TOOL_SCHEMAS 只留原子工具。
3. **无效辅助调用**（如 `player_set_loop {"loop_type":0}`——X08A 实测无效且字段名都错了）：删除，避免误导后续维护者。
4. **未验证的角色音色**：WebUI 试跑能发现"不响"的音色，应从角色配置清理，缩小排查面。

## 7. Node-RED「豆包管家 tab」实地评审（2026-09-05 补充）

> 依据：登录 NR（192.168.2.200:1990）导出 `flows.json`（783KB，1025 项）逐节点分析 + butler 源码对照。

### 7.1 豆包管家 tab（d5a38c4777f84f35）真实职责：不是编排层，是「过渡期 LLM 网关 + 人设打招呼」

31 个节点，实测内容：

| 职责 | 节点 | 现状 |
|---|---|---|
| LLM 网关 | `/llm/chat`、`/llm/image`、`/llm/vision` HTTP in → doubao2api:9090 | 纯转发 |
| 人设打招呼中枢 | `中枢编排` function（33 行）：PERSONAS（大佬/凯文/爱美丽）+ 时间感知 + `flow.get(key)` 会话历史（每 scenario+user 内存 6 条） | 手写死代码 |
| 消费方 | 仅 2 处 http request：书房专注基准 flow、arcface 人脸打招呼 | 量很小 |

**关键事实**：
1. **这不是编排层**——真正的设备/场景编排在 NR 其他 90+ tab（智能调度核心 45、书房 93、客厅 42…）。
2. **当前 NR 与 butler 完全隔离**：全 flow 检索 `:8095` 命中 0，NR 的「管家大脑」直连豆包，与 butler 平行、互不感知。
3. **butler 已具备等价且更强的能力**：
   - `/v1/chat/completions` OpenAI 兼容端点（openai_routes.py，注释「butler 既是大脑，也是对外的 openai 兼容 LLM，原计划 A3」）；
   - 角色系统（roles/store.py + roles/*.json）→ 比 NR 手写 PERSONAS 完整；
   - 会话持久化（role_state.json + 豆包云端 conversation_id）→ 比 NR 6 条内存历史强（跨重启、可续聊）；
   - `/api/wakeup`（注释「NR 耳朵转发 {role, room, message, member}」，就是给 NR 用的对话入口）；
   - 技能系统 `POST /api/skill/{id}/run`（熔断 429）+ MQTT `butler/trigger/+`、`butler/speak/out`（统一发声出口，NR 转小爱/Bark）。

### 7.2 结论：不是「NR tab vs butler 容器」二选一，而是「大脑归 butler，编排归 NR」

- **该收编到 butler**（豆包管家 tab 的职责）：
  1. `/llm/chat` → butler `/v1/chat/completions`（OpenAI 兼容）；
  2. 人设打招呼（arcface、书房专注）→ butler `/api/wakeup`（角色唤醒）或技能触发；
  3. 会话历史 → butler role_state + 豆包云端。
  - 收编后该 tab 可缩为纯转发甚至删除。
- **该保留在 NR**（真正的编排地盘，勿搬）：设备事件汇聚（HA/小爱/摄像头/TV）、TTS/发声路由（butler/speak/out 转小爱/Bark）、场景联动与定时调度（智能调度核心等 tab）。butler 是 Python 决策容器，做设备适配/可视编排不是其强项。
- **前置缺口（唯一代码改动）**：butler `/v1/chat/completions` 目前走完整 agent 管线（`agent.run` 可能触发 TTS/设备副作用）。对「NR 场景内部静默调 LLM 拿文本」需加**纯透传模式**（不跑 agent 管线、不触发输出），否则书房专注 flow 调 butler 会触发管家发声。
- **迁移节奏（勿一夜删）**：双跑期 → 逐消费者切 URL（arcface、书房专注）→ 切换完删豆包管家 tab（或保留 /llm/vision、/llm/image 纯网关兜底）→ 其余 90+ tab 不动。

### 8.3 trigger 规则层设计（与 skills 平级）

**数据模型**（`data/triggers/*.json`）：

```json
{
  "id": "morning_greet_lidicn",
  "name": "早上看到lidicn开电视+打招呼+播报",
  "version": 1,
  "enabled": true,
  "event": "face_detected",
  "conditions": {
    "time_range": "07:00-08:00",
    "member": "lidicn"
  },
  "role": "butler",
  "actions": [
    {"skill": "tv_turn_on", "params": {"room": "{{event.room}}"}},
    {"skill": "tv_switch_channel", "params": {"channel": "CCTV-1"}},
    {"skill": "greet", "params": {"member": "lidicn"}},
    {"skill": "daily_dev_summary"},
    {"skill": "today_schedule"}
  ],
  "cooldown_sec": 300,
  "priority": 10
}
```

**事件类型**：`face_detected` / `voice_wake` / `button_pressed` / `device_state` / `scheduled` / `skill_completed`

**条件**：`time_range`（HH:MM-HH:MM）、`member`、`room`、后续扩展 `custom`

**动作链**：actions 数组，顺序执行，支持 `{{event.xxx}}` 参数模板渲染

**引擎职责**：订阅 MQTT 事件 → 匹配 enabled trigger（事件类型+条件）→ 冷却检查 → 按 priority 排序 → 依次 `runner.run()` 执行动作 → 输出由技能自身 output 字段决定

### 8.4 三个必须补的关键能力

1. **角色-触发绑定**：trigger 带 `role` 字段，触发时唤醒对应角色（健康专家只在客厅+食物热量按钮）
2. **动作链多技能编排**：actions 数组顺序执行，参数从事件传递（`{{event.room}}`）
3. **全屋成员定位**：大脑触发到点后遍历所有摄像头/TV 人脸 → 找到成员所在房间 → 该房间小爱播报；找不到走 Bark

### 8.5 NR 定位与分工原则

- **NR 保留**：小爱 TTS 调用、HA 服务调用、发声路由（butler/speak/out → 小爱/Bark）、TTS 队列互斥、**复杂设备事件编排**（多设备联动、协议转换）
- **NR 移除**：MVP 耳朵 flow（butler 已直连小爱）、简单触发 flow（按钮→调 butler→播报，收进 trigger 层）
- **分工原则**：**简单触发（单事件→单技能）在 butler 内完成；复杂设备事件（多设备联动、协议转换）交 NR 豆包管家 tab**
- **设备自动化**（电脑开机→开灯）：走 autoflow 生成 NR flow，不走 trigger 层

### 8.6 自我编排

用户通过对话说需求 → deepseek 生成 trigger JSON → schema 校验 → dry_run 模拟匹配 → 保存 → 热加载。**不需要 ACP/autoflow**，因为 trigger JSON 比 NR flow 简单一个数量级。autoflow 只在设备级自动化场景调用。
