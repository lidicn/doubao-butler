## 二、核心结论：三层分工（按「延迟 + 权威」切）

| 层 | 归属 | 职责 | 为什么在这 |
|---|---|---|---|
| **实时反应层** | **豆包管家** | 规则引擎匹配（毫秒级）→ 立即推送 / 联动自动化 / 更新实时位置 | 管家有 `xiaomi_ear` HA websocket，秒级；MA **没有**实时事件流（MA 是批量轮询 HA MariaDB + 人脸推送，见 §三事实） |
| **权威记忆 + 发现层** | **MA** | 从 `behavior_events` 得出 **canonical 行为状态**（工作/睡觉/移动）；**挖掘新模式**（LLM 自进化 = MA v0.8 记忆研究员扩展）；沉淀长期习惯 | MA 有 30+ 天行为历史、Chroma 向量库、记忆研究员、预聚合洞察引擎 |
| **身份层** | **MA** | `ma/presence`（ArcFace 人脸）是"**谁**"的唯一权威源 | 人脸只在 MA；管家不该重造身份，否则出现矛盾"谁在哪" |

**防重复铁律**（方案 C 的核心）：
- 管家规则引擎产出的是 **易逝的"实时活动假设"**（为即时反应，可错、可覆盖）；
- MA 产出的是 **持久的"行为真相 + 长期模式"**（为记忆与学习，权威）；
- **同一份事件流，两种用途；MA 对"行为真相"拥有权威，管家对"实时反应"拥有权威。**
- 管家**不得**自建行为推断 / 时间规律学习 / 人脸识别，全部消费 MA 接口（`ma/presence` / `member-schedule` / `behaviors`）。

## 三、事实基线（为什么 MA 不做实时反应）

MA 当前对 HA 事件的获取方式（已查证源码）：

- `ha_db.py` —— **轮询** HA 的 MariaDB recorder（批量/定时，非实时流）；
- `trigger_collection` 工具 —— 手动/定时触发采集；
- `POST /api/events/face` —— TV ArcFace 人脸**推送**（这是 MA 唯一的"实时"通道，且只含人脸，不含设备状态流）。

**结论**：MA 没有 HA 状态变化的 websocket 监听。因此"毫秒级实时反应"天然属于管家（它有 `xiaomi_ear`）。MA 的识别是**批量/增量**粒度（分钟级），适合做 authoritative 行为与模式，不适合做实时联动触发器。这正是三层分工的技术根基。

## 五、你的三个场景：双层映射

你提的三个"连环操作推断意图"例子，在三层模型里**两层各做一遍、用途不同**：

### 场景 1：书房使用电脑
```
事件序列（5 分钟窗口）：书房门开 → 关 → 灯亮 → 空调开 → 电脑开
```
- **管家（实时层）**：命中规则 → 立即更新"凯文在书房工作"实时状态 → 不打扰 / 可选联动。
- **MA（权威层）**：从 `behavior_events` 识别同序列 → 写 canonical 行为状态（书房/工作）→ 喂记忆研究员，长期学出"凯文 工作日常驻书房"。
- **身份**："凯文"来自 `ma/presence`（人脸），管家区域状态只回答"书房有人"，不回答"谁"。

### 场景 2：人员移动轨迹
```
事件序列（10 分钟窗口）：起居室人体 → 客厅人体 → 厨房人体 → 卫生间人体
```
- **管家**：实时更新"用户当前在卫生间"位置（PIR 序列 + 去抖）。
- **MA**：记录 canonical 移动轨迹（起居室→客厅→厨房→卫生间），作为行为序列沉淀；长期可学"凯文 睡前路线"。
- **注意**：PIR 只答"有人"不答"谁"；轨迹归属某人需结合 `ma/presence` 最近身份。

### 场景 3：入睡
```
事件序列（21:00 后）：卧室门关 → 灯亮 → 空调开 → 灯灭
```
- **管家**：命中规则 → 主动动作（关客厅灯、调空调温度）。
- **MA**：识别 canonical "入睡"状态 → 长期学出就寝习惯（时间/时长）→ 写入 `member-schedule` 作为管家融合先验（"lidicn 工作日通常 22:30 睡"→ 提高卧室作息基础分）。

## 六、回答你的三个核心疑问

### 6.1 「如何理解用户意图？」
严格区分两层概念：
- **活动识别（在干嘛）**：书房工作 / 睡觉 / 移动 —— 由**规则 + 序列模式**得出，确定性强。
- **意图（为什么 / 接下来要什么）**：
  - *实时意图*（当前目标）= 管家用 **MA 先验 + 区域状态**推断的"大概率下一步"（如"关卧室灯 → 大概率要睡"），用于主动提醒/联动；
  - *长期意图（习惯）* = MA 从**重复活动序列**学到的稳定模式，回灌管家做先验置信。

> 即："意图"是**活动层之上的一层标签**，不是凭空推断；活动是意图的入口，MA 负责把活动沉淀成意图（习惯）。

### 6.2 「连环操作能否识别意图？」
能，这就是**时序序列模式匹配（ordered sequence pattern）**。你描述的"门开→关→灯亮→空调开→电脑开"是**有序事件序列**：`A→B→C→D 在窗口 W 内按序发生`。

技术上比布尔状态判断多两步（建议在 v1.7 规则引擎里落实）：
1. **时序顺序敏感**：开灯在关门之前 vs 之后，含义不同；
2. **滑动窗口 + 去抖**：PIR 会连触发，需 debounce；
3. **多传感器融合**：单靠 PIR 只能说"有人"，结合门磁 + 灯 + 人脸才能定位到"凯文在书房"。

规则定义建议升级为**有序条件**（v1.7 现有 `conditions` 已带 `after_prev_min`，方向正确，确认支持"顺序 + 窗口"即可）。

### 6.3 「传感器如何确定'谁'？」
- **PIR / 人在传感器**：只答"某区域有人"，**答不出是谁**；
- **门磁 / 灯 / 空调**：只答设备状态，**不答身份**；
- **ArcFace 人脸**：唯一能答"谁"，且只在 **MA**（经 `ma/presence`）。

**结论**："凯文在书房工作" = **MA 的 identity（人脸）+ 管家的 zone 状态（门/灯/电脑）** 融合。身份归一必须归 MA，管家不得重造人脸识别（方案 C 开放问题 1 已确认 TV 单路上报 MA）。
