# 豆包管家 (doubao-butler) — 项目设计文档

> 版本：v1.2
> 日期：2026-09-08
> 状态：待确认
> 定位：拟人化家庭 AI 管家，基于人脸识别 + 多模态场景理解 + 记忆系统，实现主动对话与个性化交互

---

## 1. 项目定位

### 1.1 是什么

豆包管家是一个运行在 NAS Docker 上的拟人化家庭 AI 管家服务。它：
- 通过 TV 端人脸识别知道"谁在客厅"
- 通过 memory-agent VLM 多模态知道"客厅发生了什么"
- 通过记忆系统知道"用户喜欢什么、讨厌什么、之前聊过什么"
- 通过 TTS 语音在电视上主动打招呼、提醒、聊天
- 支持小爱音箱语音触发、人体传感器主动唤醒

### 1.2 不是什么

- 不是通用聊天机器人（不回答百科问题，只做家庭场景交互）
- 不是 memory-agent 的一部分（独立部署，隐私隔离）
- 不是 Node-RED 流程（复杂对话状态管理不适合 Node-RED）

### 1.3 核心价值

| 价值 | 说明 |
|------|------|
| **拟人化** | 有名字、有性格、有记忆，不像机器 |
| **主动式** | 不是等用户问，而是主动打招呼、提醒、关心 |
| **场景感知** | 知道当前客厅情况，对话有上下文 |
| **个性化** | 对不同家庭成员有不同的称呼、话题、语气 |
| **不重复** | 记忆系统防止每天说同样的话 |

## 3. 核心模块设计

### 3.1 唤醒引擎 (WakeupEngine)

#### 3.1.1 唤醒方式

| 唤醒方式 | 触发条件 | 优先级 | 说明 |
|---------|---------|--------|------|
| **人脸识别** | TV 端识别到新的人进入客厅 | 高 | 立即打招呼 |
| **人体传感器** | 客厅人体传感器检测到有人，且 30 秒内无对话 | 中 | 主动关心 |
| **定时唤醒** | 特定时间点（早上 8 点、晚上 10 点） | 中 | 播报日程/提醒 |
| **小爱音箱** | 用户说"小爱同学，叫豆包管家" | 高 | 启动对话模式 |
| **场景触发** | memory-agent 检测到特定场景（如客厅很乱） | 低 | 委婉提醒 |

#### 3.1.2 唤醒策略

- **冷却机制**：两次主动对话间隔至少 10 分钟（防止打扰）
- **场景判断**：
  - 电视在播放视频 → 不主动说话（只在用户暂停时）
  - 深夜（23:00-07:00）→ 不主动说话
  - 多人在客厅 → 简短问候，不展开对话
- **用户偏好**：用户可以设置"免打扰时段"、"主动对话频率"

### 3.2 对话管理器 (DialogManager)

#### 3.2.1 对话状态

```
IDLE（空闲）
  │
  ├─ 唤醒事件 → LISTENING（监听中，等待用户说话）
  │                │
  │                ├─ 用户说话 → THINKING（思考中，生成回复）
  │                │                │
  │                │                └─ 回复生成 → SPEAKING（说话中）
  │                │                                  │
  │                │                                  └─ 说完 → WAITING（等待回应，5秒）
  │                │                                                    │
  │                │                                                    ├─ 用户回应 → THINKING
  │                │                                                    └─ 无回应 → IDLE
  │                │
  │                └─ 超时（10秒无说话）→ IDLE
  │
  └─ 主动对话触发 → SPEAKING（直接说话，说完后进入 WAITING）
```

#### 3.2.2 上下文管理

- **短期上下文**：当前对话的最近 10 轮（内存）
- **中期上下文**：今天的对话摘要（SQLite）
- **长期记忆**：用户偏好、重要事件、习惯（ChromaDB 向量）
- **场景上下文**：当前客厅情况（从 memory-agent 获取）

#### 3.2.3 人格设定

```
你是"小豆"，一个亲切、幽默、有点唠叨的家庭 AI 管家。
- 对 lidicn 称呼"豪哥"，语气像老朋友，可以开玩笑
- 对 Kevin 称呼"小凯"，语气像大哥哥，关心学习和健康
- 对小女孩称呼"小公主"，语气温柔，鼓励为主
- 不要太正式，用口语化表达
- 不要重复说同样的话（记忆系统会记录）
- 不要主动聊沉重话题（工作压力、健康问题等），除非用户提起
- 提醒要委婉，不要说教
```

### 3.3 记忆系统 (MemorySystem)

#### 3.3.1 记忆类型

| 类型 | 存储 | 用途 | 保留期 |
|------|------|------|--------|
| **对话历史** | SQLite | 上下文、防重复 | 30 天 |
| **用户偏好** | SQLite + ChromaDB | 个性化回复 | 永久 |
| **场景记忆** | SQLite | 什么场景说过什么话 | 7 天 |
| **重要事件** | ChromaDB | 生日、纪念日、重要约定 | 永久 |
| **防重复哈希** | SQLite | 防止 7 天内说同样的话 | 7 天 |

#### 3.3.2 防重复机制

每次生成回复前：
1. 计算回复内容的语义哈希（embedding）
2. 在 ChromaDB 中搜索最近 7 天的相似回复
3. 如果相似度 > 0.85 → 重新生成（换个说法或换个话题）
4. 最多重试 3 次，仍重复则跳过本次主动对话

#### 3.3.3 用户偏好学习

- 显式学习：用户说"我不喜欢..."、"我喜欢..." → 直接记录
- 隐式学习：用户对某话题回应积极 → 增加该话题权重；回应消极 → 减少
- 定期整理：每周生成用户偏好摘要，供对话生成使用

### 3.4 TTS 语音模块

#### 3.4.1 语音生成

- **方案 A（推荐）**：edge-tts（微软免费 TTS，音质好，支持中文多种音色）
- **方案 B**：豆包 TTS API（需付费，音质更好，支持情感）
- **方案 C**：本地 Piper TTS（离线，音质一般）

#### 3.4.2 播放方式

| 播放设备 | 方式 | 延迟 | 适用场景 |
|---------|------|------|---------|
| **电视扬声器** | TV 端 APK 接收音频流，AudioTrack 播放 | 低（<1s） | 客厅主动对话 |
| **小爱音箱** | TTS 文本 → 小爱 TTS API → 小爱播放 | 中（2-3s） | 全屋广播 |
| **手机推送** | Bark 推送文字 + 语音链接 | 高 | 重要提醒（用户不在家） |

#### 3.4.3 TV 端播放协议

doubao-butler 生成 MP3 音频文件后：
1. 上传到 NAS 静态文件服务（或 TV 端可访问的 HTTP 地址）
2. 调用 TV 端 API：`POST http://192.168.2.238:8080/api/tts/play`
   ```json
   {"url": "http://192.168.2.200:8090/tts/xxx.mp3", "volume": 80}
   ```
3. TV 端 APK 用 MediaPlayer 播放

**TV 端需要新增**：`/api/tts/play` 端点，接收音频 URL 并播放。

## 4. 外部 API 集成

### 4.1 TV 端人脸识别

```
GET http://192.168.2.238:8080/api/scan/latest
Response:
{
  "faces": 1,
  "persons": [
    {"name": "Kevin", "similarity": 0.923, "age": 13, "gender": 0, "state": "stable"}
  ],
  "fused": [...]
}
```

**使用场景**：
- 唤醒时：知道谁在客厅，用对应称呼打招呼
- 对话中：知道谁在说话，个性化回复
- 离开时：知道人走了，结束对话

### 4.2 memory-agent VLM 场景分析

```
POST http://192.168.2.200:8086/api/vision/analyze
Body: {"room": "客厅", "force": true, "wait": true}
Response:
{
  "ok": true,
  "persons": [
    {"identity": "Kevin", "action": "坐在沙发上玩手机", "posture": "坐", "confidence": 0.9}
  ],
  "scene": "客厅，一人坐在沙发上玩手机",
  "snapshot_quality": "good"
}
```

**使用场景**：
- 主动对话前：获取当前场景，让对话有上下文
- 提醒触发：检测到特定场景（客厅很乱、有人久坐不动）
- 对话中：用户问"我在干嘛"时回答

### 4.3 memory-agent 行为记录

```
GET http://192.168.2.200:8086/api/behaviors?room=客厅&limit=10
Response:
{
  "count": 10,
  "events": [
    {"ts": 1725264000, "room": "客厅", "persons": [...], "scene": "...", ...}
  ]
}
```

**使用场景**：
- 记忆系统：读取历史行为，了解用户习惯
- 对话中："你今天看了 3 小时电视，注意休息"
- 统计：用户活动规律

### 4.4 Home Assistant 传感器

```
GET http://192.168.2.200:8123/api/states/binary_sensor.living_room_motion
Headers: Authorization: Bearer <ha_token>
```

**使用场景**：
- 唤醒引擎：人体传感器触发主动对话
- 场景判断：电视是否在播放、灯是否开着
- 设备控制：对话中控制设备（"帮我关灯"）

### 4.5 doubao2api LLM

```
POST http://192.168.2.200:9090/v1/chat/completions
Body:
{
  "model": "doubao",
  "messages": [
    {"role": "system", "content": "<人格设定 + 上下文 + 记忆>"},
    {"role": "user", "content": "<用户说话或主动对话触发>"}
  ],
  "temperature": 0.7,
  "max_tokens": 200
}
```

## 5. 典型场景示例

### 5.1 场景一：Kevin 放学回家

```
触发：TV 人脸识别到 Kevin（新进入客厅）
唤醒引擎：检测到新人，立即打招呼
对话管理器：
  上下文：Kevin，13岁，男生，下午 17:30
  记忆：Kevin 今天还没说过话；昨天提醒过写作业
  生成回复："小凯回来啦，今天学校怎么样？作业多不多？"
TTS：生成语音，电视播放
等待回应：
  Kevin："还行，作业不多"
  生成回复："那就好，先休息一下，吃完饭再写？对了，你妈说今天晚上吃红烧肉"
```

### 5.2 场景二：客厅很乱，委婉提醒

```
触发：memory-agent VLM 分析到"客厅茶几上有很多可乐瓶和零食袋"
唤醒引擎：场景触发，低优先级，检查是否适合提醒
  - 电视没在播放 ✅
  - 不是深夜 ✅
  - 距离上次提醒 > 2 小时 ✅
  - lidicn 在客厅 ✅
对话管理器：
  上下文：lidicn，客厅很乱，晚上 21:00
  记忆：上周提醒过一次打扫，用户说"明天收拾"但没收拾
  防重复：上次说"茶几有点乱，要不要收拾一下" → 换说法
  生成回复："豪哥，茶几上的可乐瓶都快堆成山了，要不要我帮你叫个保洁？还是你自己动手？"
TTS：电视播放
```

### 5.3 场景三：久坐提醒

```
触发：人体传感器检测到 lidicn 在电竞沙发上连续 2 小时
唤醒引擎：定时检查，触发健康提醒
  - 电视在播放 → 等待暂停（不打扰）
  - 用户暂停视频 → 立即提醒
对话管理器：
  上下文：lidicn，久坐 2 小时，电竞沙发
  记忆：用户有颈椎问题（之前提过）
  生成回复："豪哥，你都坐了 2 小时了，起来活动活动吧，颈椎还要不要了？去倒杯水喝"
TTS：电视播放
```

### 5.4 场景四：早上播报

```
触发：定时唤醒，早上 8:00
唤醒引擎：检查是否适合播报
  - 客厅有人 ✅
  - 不是免打扰时段 ✅
对话管理器：
  上下文：早上 8:00，lidicn 在客厅
  记忆：读取今天的日程、天气
  生成回复："豪哥早上好，今天深圳 28 度，多云，适合出门。你今天上午 10 点有个会，别忘了。早餐吃了没？"
TTS：电视播放
```

## 8. 风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| LLM 回复质量不稳定 | 对话不自然 | 优化 system prompt，增加场景模板，人工审核关键回复 |
| TTS 延迟高 | 对话不流畅 | 预生成常见回复音频，流式 TTS，本地缓存 |
| 主动对话打扰用户 | 用户反感 | 严格的冷却机制、免打扰时段、场景判断、用户可调节频率 |
| 记忆系统误判 | 重复或遗忘 | 多层记忆（短期/中期/长期），定期整理，用户可编辑 |
| 隐私安全 | 敏感信息泄露 | 本地存储，不上云，用户可清除记忆，敏感话题不记录 |
| TV 端播放失败 | 听不到声音 | 降级到小爱音箱，再降级到手机推送 |

## 12. 规划：角色唤醒词唤醒房间专属角色（Phase 6）

> v1.1 新增。前置依赖已就绪：技能层（skills）+ 多角色（roles：presence_rooms 排他、
> per-role conversation_id、角色音色）+ 设备登记表（devices：绑定房间/实体/兜底）。
> 本节只补齐「语音入口 → 角色路由」这一段。

### 12.1 目标

- 说「小爱同学，叫晓月」→ 晓月在客厅应答（晓月只能出现在厨房/客厅）
- 为 lidicn / Kevin / Emily 每人房间配置**专属私人助理角色**：
  - 人设基于该成员画像页 profile（口味/作息/课表）
  - **不离开房间**（presence_rooms = 该房间），**只能被该房间的小爱唤醒**，也只从该房间设备出声
  - 专职处理个人事务（日程、提醒、陪伴聊天）

### 12.2 唤醒链路（关键认知：难点在语音入口，不在管家）

```
小爱音箱（训练计划/自定义指令，每个角色注册一组唤醒短语）
   │  「小爱同学，叫晓月」命中训练计划
   ▼
Node-RED / HA 自动化（拿到：唤醒短语 + 来源音箱实体 → 房间）
   │  POST butler API 或 MQTT butler/event/voice
   ▼
butler RoleWakeupRouter（新增，~1 天）
   │  唤醒词 → 角色；校验来源房间 ∈ role.presence_rooms
   ▼
该角色的对话线程（per-role conversation_id 已实现）+ 角色音色输出（已实现）
```

小爱侧需人工配置一次：为每个角色在米家/小爱训练计划注册唤醒短语，
动作选「调用 HA/NR webhook」，把原文与设备实体传给管家。

### 12.3 数据模型扩展

`Role`（data/roles/{id}.json）新增字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `wake_words` | list[str] | 唤醒词列表，如 `["晓月","月亮"]`；空=不可语音唤醒 |
| `bound_rooms` | list[str] | 专属绑定房间（私人助理用）；空=不绑定 |
| `scope` | str | `family`（家庭角色，可被任意已允许房间唤醒）/ `private`（私人助理，仅 bound_rooms 内设备可唤醒） |

`Device`（data/devices.json）新增字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `play_mode` | str | `notify_text`（小爱自带 TTS，稳定）/ `tts_speak`（edge-tts 音色，经 HA tts.speak） |
| `ha_tts_entity` | str | tts_speak 模式使用的 `tts.*` 实体（如 `tts.edgetts_zh_cn_xiaoyineural`）与 `media_player.*` 目标 |

### 12.4 路由规则（RoleWakeupRouter）

1. 唤醒词 → 角色查表；未命中 → 路由到来源房间的专属角色，再退主角色
2. 校验：来源房间必须 ∈ `role.presence_rooms`，且 `private` 角色只接受 `bound_rooms` 内设备唤醒；
   不满足时播报拒绝语（"我只能待在房间，来找我呀"），不越房应答
3. 活跃互斥：沿用全局输出锁 + 角色排他——同一时刻一个角色只在一个房间；
   唤醒新角色前需当前角色先结束对话（或编排层先发结束事件）
4. 对话线程按角色隔离（per-role conversation_id），互不串上下文

## 13. 已知问题与修复计划

### 13.1 小爱 edge-tts 循环播放（已定位，待修）

- **现象**：HA `tts.speak`（edge-tts）推小爱后同一句反复播放，需说"停止播放"才停
- **原因**：小爱（MICO）media_player 把 TTS 音频 URL 当歌单播放，处于循环模式或拿不到音频时长
- **缓解**（按成本排序）：
  1. 播放前 `media_player.repeat_set: off`（大概率直接解决）
  2. 改 `media_player.play_media`（music）+ 按音频时长定时 `media_stop` 兜底
  3. 退回 `notify execute_text_directive`（小爱自带 TTS，无循环但非 edge 音色）——即现有 `notify_text` 默认通道
- **落地**：Device 增加 `play_mode`（§12.3），edge-tts 音色走 `tts_speak` 通道并内置防循环逻辑

## 14. 轻量 Agent 框架（自研，v1.1，2026-09-08 决策）

### 14.1 决策

- **自研轻量 ReAct Agent，不引入开源 Agent 框架**。理由：管家是垂直系统（固定工具集、短任务、单家庭、深度耦合 MQTT/HA/TVPilot/MA/豆包App/技能系统），缺的是"观察→验证→重试闭环"，而非框架；引入重框架（LangChain/CrewAI/AutoGen）会放大 NAS 依赖风险与过度工程成本。
- TVPilot（原 zap-tv，品牌升级）为 LLM 的"手"，v0.2 工具层已就绪，管家侧开始 Phase 1 联调。
- **模板体系统一**：操作模板/经验的存储、检索、执行、版本、沙箱一律归**豆包管家技能系统**（TVPilot 不再做模板引擎，见交接单 `E:\NAS\TVPilot\doc\豆包管家_对接路线变更_20260908.md`）。

### 14.2 现状（已具备的 Agent 基元）

| 基元 | 位置 | 状态 |
|------|------|------|
| ReAct 工具循环 | `integrations/llm.py::chat_with_tools`（max_iter=5，tool 结果回灌） | ✅ 已有，需升级为"可观察" |
| 技能/模板体系 | `skills/`（7 引擎 + 创建/沙箱/隔离/版本） | ✅ 作为模板统一承载 |
| 主动行为 | `decision/engine.py` 心跳 | ✅ |
| 规则层 | `triggers/engine.py` | ✅ |
| 多 Agent 协作 | `agent_collab.py`（delegate_task 已修假异步，asyncio.Event 真等待） | ✅ 已修 |
| 换台回执闭环 | `tv.py` async zap + request_id | ✅ 9-7 上线 |

**缺失（本次补齐）**：工具调用后**状态观察与验证**、**多步失败恢复**、**模板复用流程**。

### 14.3 目标：可观察 ReAct 闭环

```
用户指令
  │
  ▼
[Thought] 规划多步
  │
  ▼
[Action]  调用 TVPilot 工具（screenshot/keyevent/tap/launch_app/zap/foreground/current）
  │
  ▼
[Observation] 验证结果
   ├─ 结构化状态优先：foreground / current / health（快、省 token）
   ├─ 关键节点截图：screenshot?fmt=json&width=480（启动后/输入后/最终验证）
   └─ 失败必截图（排查）
  │
  ├─ 成功 → 下一步 / 完成（沉淀为技能模板）
  └─ 失败 → 错误码重试矩阵 → 换路径 → 仍失败报错
```

**错误码重试矩阵**：`tv_unreachable`→重连×3；`app_not_responding`→等2s×2；`wrong_foreground`→重 launch；`operation_timeout`→×1；`invalid_parameter`→不重试直接报错；`mytv_api_error`→检查后×1。

**安全阀**：步数/时间预算上限；逃生通道（`keyevent KEYCODE_HOME`）；失败最终回退"回桌面 + 报错给用户"，不做无限重试。

**可观测性**：ReAct 轨迹（thought/action/observation/cost_ms/错误码）全量落库，可回放复盘；TVPilot 侧操作+截图 JSONL 存档（已发交接单）。

### 14.4 与 TVPilot 的集成

- **通信**：HTTP 主通道（同步工具调用）；MQTT 仅状态推送 + 回执（换台 request_id 闭环）。
- **工具清单**：screenshot / foreground / keyevent / tap / swipe / input_text / launch_app / wait / zap / current / channels / health（v0.2 全就绪）。
- **观察策略**：结构化优先、截图兜底；多模态账号后期扩容，不阻塞。
- **P0 阻塞项**：`input_text` 中文输入（ADB 原生不支持，电影名是中文）——已列入交接单要求 TVPilot 解决。

### 14.5 明确不做（对齐图3 判定）

- ❌ 长期目标追踪（家庭任务都是短任务）
- ❌ 自主探索新工具（工具集固定）
- ❌ 情感/人格（角色人设已在 roles/persona 层，不归 agent 框架）
- ❌ 多 Agent 协作编排任务（agent_collab 仅用于角色调度/委派，不做通用编排）
