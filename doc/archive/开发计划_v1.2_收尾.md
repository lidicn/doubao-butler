## 二、T1：Bark Tailscale 修复（详细）

### 问题
- Bark 服务器：`100.114.216.94:18273`（NAS Tailscale IP）
- 当前连不通：`Connect call failed ('100.114.216.94', 18273)`
- 局域网 IP `192.168.2.200:18273` 可能可用，但手机在外网时需要 Tailscale

### 排查步骤
1. SSH 到 NAS，检查 Bark 容器是否运行：`docker ps | grep bark`
2. 检查 Bark 容器端口映射：`docker port bark` 或 `docker inspect bark | grep Port`
3. 检查 Tailscale 状态：`tailscale status`（NAS 上）
4. 从 NAS 本地测试：`curl http://127.0.0.1:18273/tmLBKcC47VWTW95fYmB5x7/`
5. 从局域网测试：`curl http://192.168.2.200:18273/tmLBKcC47VWTW95fYmB5x7/`
6. 从 Tailscale 测试：`curl http://100.114.216.94:18273/tmLBKcC47VWTW95fYmB5x7/`

### 可能原因与修复
- Bark 容器只监听 127.0.0.1 → 修改 docker-compose 端口映射为 `0.0.0.0:18273:8080`
- Tailscale 防火墙拦截 → NAS 上 `sudo ufw allow 18273` 或 Tailscale ACL 放行
- Tailscale IP 变更 → 检查 `tailscale ip -4`，更新管家配置
- Bark 容器崩溃 → `docker restart bark`

### 验收标准
- 从管家容器内 `curl http://100.114.216.94:18273/{key}/测试` 返回 200
- 手机 Bark app 收到推送

## 三、T2/T3：TP/DP 适配统一指令中心（详细）

### 背景
统一指令中心 API 已就绪（`/api/commands`），但 TP/DP 还不会主动拉取指令。需要开工单让他们实现：
1. 启动时/定时轮询 `GET /api/commands/pull/{TP|DP}`（拉取 pending 状态指令）
2. 接手指令：`POST /api/commands/{id}/accept`
3. 完成指令：`POST /api/commands/{id}/complete`（body: {result: "完成说明"}）
4. 失败指令：`POST /api/commands/{id}/fail`（body: {error: "错误信息"}）
5. 轮询间隔：30 秒（可配），紧急指令优先

### 工单内容（PM 下发）
- 标题：适配统一指令中心（拉取+状态上报）
- 描述：实现指令轮询拉取和状态上报，接入管家看板
- 优先级：P1
- 验收标准：
  1. PM 在看板创建指令（target=TP/DP）
  2. TP/DP 在 30 秒内拉取并 accept
  3. TP/DP 完成后 complete，看板状态更新
  4. 失败时 fail，看板显示错误信息
  5. 轮询不影响正常功能（异步后台线程）

## 六、T6-T11：客厅 Vibe Coding 决策系统（管家侧）

### 背景
小甜菜 v1.0 成为电视端决策终端，PM 需要决策时通过广播唤醒小甜菜弹窗，lidicn 用遥控器选择 A/B/C 或语音回复。管家侧需要实现：
1. 决策数据存储（decision_store）
2. 接收小甜菜选择上报的 API
3. 接收小甜菜语音转发的 API
4. 查询待处理决策的 API（小甜菜重启后恢复）
5. PM 侧创建决策并发送广播的工具
6. 决策超时检测（后台线程+Bark 推送）

### T6：decision_store 决策数据存储

**数据模型**（SQLite，复用现有 db 连接）：
```sql
CREATE TABLE decisions (
  id TEXT PRIMARY KEY,          -- 业务 ID：DEC-YYYYMMDD-XXXX
  question TEXT NOT NULL,        -- 决策问题
  options TEXT NOT NULL,         -- JSON: [{"key":"A","text":"..."},...]
  priority INTEGER DEFAULT 1,    -- 0=紧急 1=一般 2=低
  status TEXT DEFAULT 'pending', -- pending/accepted/selected/timeout/cancelled/user_left
  selected_option TEXT,          -- 用户选择的 A/B/C
  selected_note TEXT,            -- 用户备注
  selected_user TEXT,            -- 选择时的用户（lidicn/kevin/emily）
  timeout_sec INTEGER DEFAULT 300,
  created_at TEXT,
  updated_at TEXT,
  selected_at TEXT,
  expire_at TEXT                  -- created_at + timeout_sec
);

CREATE TABLE decision_events (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  decision_id TEXT,
  event_type TEXT,  -- created/broadcast_sent/selected/timeout/cancelled/user_left/voice_received
  detail TEXT,      -- JSON 详情
  created_at TEXT
);
```

**核心方法**：
- `create_decision(question, options, priority, timeout_sec)` → 返回 decision_id
- `get_decision(decision_id)` → 决策详情+events
- `list_decisions(status=None, limit=20)` → 决策列表
- `update_status(decision_id, status, **kwargs)` → 更新状态+记录 event
- `get_pending_decisions()` → status=pending 且未过期的决策
- `check_timeouts()` → 扫描过期决策，标记 timeout+Bark 推送（后台线程调用）

### T7：POST /api/vibe/decision/{id}/select

**请求**：
```json
{
  "option": "A",
  "note": "先做截图优化",
  "user": "lidicn"
}
```

**处理逻辑**：
1. 查找 decision，不存在返回 404
2. 校验 option 在 options 范围内
3. 更新 status=selected，记录 selected_option/note/user/selected_at
4. 记录 event: selected
5. 如果 PM 正在等待此决策（ReAct 循环中），通过事件机制通知
6. 返回 `{ok: true}`

### T8：POST /api/vibe/voice_input

**请求**：
```json
{
  "user": "lidicn",
  "text": "选A，先做截图优化",
  "has_pending_decision": true,
  "decision_id": "DEC-20260909-001",
  "timestamp": "2026-09-09T20:30:00"
}
```

**处理逻辑**：
1. 记录 event: voice_received（decision_id 关联或独立记录）
2. 如果 has_pending_decision 且 decision_id 有效：
   - 解析文本中的选择（正则匹配 "选A"/"A"/"第一个" 等）
   - 如果解析到明确选择 → 调用 T7 的 select 逻辑
   - 如果解析不到（纯文字说明）→ 保存为 selected_note，status 仍 pending，通知 PM 查看
3. 如果没有 pending_decision：
   - 作为普通消息存入 message_store（PWA 对话系统已有）
   - 通知 PM 有新消息（通过 PM 消息管道转发到豆包对话）
4. 返回 `{ok: true, action: "selected"|"note_saved"|"message_forwarded"}`

### T9：GET /api/vibe/decision/pending

**响应**：
```json
{
  "decisions": [
    {
      "id": "DEC-20260909-001",
      "question": "先做截图优化还是客户端UI？",
      "options": [{"key":"A","text":"截图优化"},...],
      "priority": 1,
      "status": "pending",
      "created_at": "2026-09-09T20:00:00",
      "expire_at": "2026-09-09T20:05:00",
      "remaining_sec": 120
    }
  ],
  "count": 1
}
```

**用途**：小甜菜 DecisionActivity 启动时查询，如果有 pending 决策且 decision_id 匹配当前广播，直接恢复显示；如果小甜菜被杀重启，也能查到未完成的决策。

### T10：PM 侧决策请求工具（create_decision + 广播发送）

**工具定义**（tools.py 新增 `create_vibe_decision`）：
```
工具名：create_vibe_decision
参数：
  - question (str, required): 决策问题
  - options (list[str], required): 选项列表，如 ["A:截图优化", "B:客户端UI", "C:并行"]
  - priority (int, optional): 0=紧急 1=一般 2=低，默认 1
  - timeout_sec (int, optional): 超时秒数，默认 300

执行逻辑：
1. decision_store.create_decision() → 生成 decision_id
2. 构造广播 Intent extras
3. 调用 TVPilot API 发送 ADB 广播（或直接 SSH 到电视执行 adb shell am broadcast）
   - 待 TP 提供"发送广播"API 端点；临时方案：SSH 到电视直接 adb shell am broadcast
4. 如果 priority=0（紧急），同时 Bark 推送手机
5. 返回 decision_id + 广播发送结果

ReAct 中的使用：
- PM 在管理 TP/DP 时遇到需要 lidicn 决策的事项
- 调用 create_vibe_decision 工具
- 工具返回后，ReAct 进入"等待决策"状态（暂停当前任务，记录 decision_id）
- 小甜菜上报选择后（T7/T8），通过事件机制唤醒 ReAct 继续执行
```

**临时广播方案**（TP 广播 API 就绪前）：
```python
# 通过 SSH 到电视直接执行 adb broadcast
ssh lidicn@192.168.2.200 "adb -s 192.168.2.238:5555 shell am broadcast \
  -a com.xiaotiancai.action.SHOW_DECISION \
  --es decision_id 'DEC-xxx' \
  --es question '...' \
  --es options 'A:...|B:...|C:...' \
  --ei priority 1 \
  --ei timeout_sec 300"
```

### T11：决策超时检测（后台线程）

**实现**：
- 后台线程每 30 秒扫描 decisions 表
- 查找 status=pending 且 expire_at < now 的决策
- 对每个超时决策：
  1. 更新 status=timeout
  2. 记录 event: timeout
  3. Bark 推送手机："决策超时未处理：{question}"
  4. 如果 PM ReAct 正在等待，通知其超时（可选择默认选项或标记失败）
- 同时检测 user_left 状态（小甜菜上报 lidicn 离开时更新）

**与现有后台任务的关系**：复用管家现有的后台线程机制（如果有），或新增一个轻量级定时器。
