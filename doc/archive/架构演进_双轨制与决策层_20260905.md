## 一、关键技术发现（真机验证）

### 1.1 doubao2api 真实能力

| 能力 | 状态 | 验证方式 |
|---|---|---|
| 纯文本 keep_conversation | ✅ 可用 | 创建对话返回 conversation_id=38440225923606274，第二次复用同一 id，上下文保留（"你叫测试用户"跨轮记住） |
| 视觉 keep_conversation | ✅ 可用 | role_state.json 中 gu_anheng 已有 conversation_id |
| function calling（推断式） | ✅ 可用 | `DOUBAO_CODE_EXECUTOR=on` 已开启；传入 tools+"打开客厅灯"→返回 `tool_calls: ha_light_on` |
| 中文意图匹配（family_fallback） | ✅ 默认 on | tool_call.py 内置 HA/记忆体中文别名（灯/空调/电视/人/房间等） |
| webhook/回调 | ❌ 不存在 | 源码无 webhook/callback |
| 拉取对话消息 | ❌ 不存在 | 只有 /v1/chat/completions（发消息），无"获取对话历史"端点 |

### 1.2 根本性限制：单向通信

doubao2api 是**单向**服务：模拟网页版豆包"发消息→收回复"。用户在豆包app（手机/电脑/网页）里回复某个对话时，消息**直接发给豆包服务器，不经过 doubao2api**。

```
butler ──发消息──→ doubao2api ──模拟网页──→ 豆包服务器 ──→ 豆包app（可见）
                                                          ↑
用户在豆包app回复 ────────────────────────────────────────┘（butler 收不到）
```

**结论**：
- ✅ butler 主动说的话 → 出现在豆包app各角色对话（可行）
- ❌ 用户在豆包app回复 → butler 收到并执行（当前不可行）

双向通信的两条可能路径（均不推荐短期做）：
1. 逆向豆包 API 轮询对话消息（脆弱、有封号风险）
2. 等豆包官方智能体平台开放 webhook

## 二、架构决策

### 2.1 豆包app定位：多角色通知展示窗口（单向）

豆包app不是交互入口，而是**通知展示层**：
- 每个角色（豆包管家/健康专家/小理/小凯/小艾/安防）在豆包app里有一个独立对话
- butler 的主动消息（提醒、打招呼、技能结果、决策层行动）推送到对应角色对话
- 用户在手机豆包app里能看到所有角色的主动通知
- 用户主动跟管家说话 → 走小爱音箱（全屋耳朵 v0.2 已完成）

### 2.2 不做 PWA 对话页面

原计划 PWA 加对话功能，现取消。理由：
- 豆包app通知通道已覆盖"手机端查看管家消息"的核心需求
- PWA 对话需要独立维护前端，且与小爱音箱语音交互重叠
- 如未来豆包app双向通信打通，PWA 对话更无必要

### 2.3 不新建"设备总管"角色

"设备总管"的三个职责拆解：
| 原设备总管职责 | 归属 |
|---|---|
| 操作智能家居设备（开灯/开空调） | butler 角色已有 HA 工具 |
| 学习用户习惯 | 决策层（v0.9）长期分析 |
| 主动询问+创建自动化 | 决策层 `suggest_automation` 行动 + autoflow（v0.8） |

新建独立角色增加角色路由复杂度，且与 butler 职责重叠。**不做**。

### 2.4 决策层/心跳（v0.9）

决策层不是独立"层"，而是 trigger 引擎的一种新事件类型 `heartbeat` + 一个 `decision` 引擎。复用现有动作链、冷却、互斥机制。

**与 trigger 层的区别**：
- trigger 层 = 事件 → 确定性规则匹配（用户显式设定）
- 决策层 = 定时扫描多源数据 → LLM 推理 → 主动行动（无显式指令）

## 三、心跳具体定义

### 3.1 周期与触发

- **周期**：10 分钟（可配，APScheduler cron `*/10 * * * *`）
- **触发**：APScheduler → `handle_event("heartbeat", {})` → 匹配 `heartbeat_decision` trigger → `decision` 引擎

### 3.2 数据聚合（每次心跳）

```
时间上下文：当前时间/日期/星期/天气
设备状态：各房间灯/空调/电视/门窗（HA API 实时）
视觉事件：最近 30 分钟各房间人员出现（MA analyze_camera）
对话历史：最近 10 条 dialog_turns（SQLite）
今日活动：已执行的技能/提醒（skill_runs）
```

聚合为一段文字摘要，传给 deepseek。

### 3.3 推理与行动

```
数据摘要 → deepseek prompt：
  "基于以上家庭状态，是否需要主动行动？
   若需要，输出 JSON：{action, room, text, reason, confidence}"
```

**行动白名单**（LLM 只能选这些）：

| action | 说明 | 风险 |
|---|---|---|
| `speak` | 指定房间小爱播报 | 低 |
| `notify` | Bark/TV 通知 | 低 |
| `reminder` | 设置提醒 | 低 |
| `suggest_automation` | 建议创建自动化，需用户确认 | 中 |

**禁止**：
- ✗ 直接操作设备（灯/空调/门锁/燃气）——必须走 trigger 规则或用户确认
- ✗ 任意工具调用——心跳不接 tools，只接白名单行动

### 3.4 安全边界

| 规则 | 说明 |
|---|---|
| 同类行动冷却 | 30 分钟内不重复（如"睡过头"只叫一次） |
| 夜间静默 | 23:00-07:00 只允许 notify，不允许 speak |
| 置信度阈值 | confidence < 0.6 只 notify 不 speak |
| JSON schema 校验 | LLM 输出必须经校验，非法输出丢弃 |
| 行动结果推送 | 决策行动同步推送到豆包app对应角色对话（v0.5 通道） |

### 3.5 场景验证

**"睡过头"场景**：
- 7:10 心跳 → 客厅灯关 + 主卧空调开 + 7:00 后无视觉事件
- LLM 推理：`{action: "speak", room: "主卧室", text: "大佬，7点10分了，该起床了", reason: "可能睡过头", confidence: 0.7}`
- confidence ≥ 0.6 → speak 放行 → 主卧小爱播报
- 同步推送到豆包app"豆包管家"对话

**"习惯发现"场景**：
- 每日 23:00 心跳（长期分析任务）→ 分析过去 7 天设备使用模式
- 发现"开电脑→80% 概率同时开显示器挂灯"
- LLM 推理：`{action: "suggest_automation", text: "发现你开电脑时常开显示器挂灯，需要帮你创建自动化吗？"}`
- 用户确认 → autoflow 创建自动化

## 四、双轨制说明

### 4.1 为什么叫"双轨"

| 轨道 | 职责 | 模型 | 出现在豆包app？ |
|---|---|---|---|
| 轨道1：展示层 | 豆包app对话展示 | doubao2api（豆包大模型） | ✅ |
| 轨道2：推理执行层 | 实际推理+工具调用 | deepseek（new-api）+ butler tools | ❌ |

### 4.2 工作流程（主动推送）

```
butler 产生主动消息（提醒/打招呼/技能结果）
  │
  ├─→ 小爱音箱播报（现有通道）
  │
  └─→ doubao2api chat(keep_conversation=True, conversation_id=角色ID)
       └─→ 豆包app对应角色对话出现该消息
```

### 4.3 工具调用路径（用户主动交互，走小爱音箱）

```
用户对小爱说"打开电视CCTV1"
  → butler /api/wakeup → deepseek + tools → ha_action 执行
  → 结果小爱播报
  → （可选）同步推送到豆包app豆包管家对话
```

注意：用户主动交互走 deepseek（原生 function calling，可靠），不走 doubao2api 的推断式 tools。doubao2api 的 tools 仅作为未来备选。

## 八、已排除的方案

| 方案 | 排除原因 |
|---|---|
| PWA 对话页面 | 豆包app通知通道已覆盖；维护成本高 |
| 设备总管独立角色 | 职责与 butler/决策层/autoflow 重叠 |
| 豆包app双向交互（轮询） | 逆向 API 脆弱，有封号风险 |
| 决策层直接操作设备 | 安全风险；必须经用户确认或 trigger 规则 |
| 新建数据库存决策数据 | SQLite butler.db 已够用；加 decision_runs 表即可 |
