# 路线图 v1.7 · 主动感知

## 版本主题
从"被动响应"升级为"主动管家"——豆包管家不仅能回答问题，还能主动感知家庭状态变化、推断用户意图、在合适时机主动提醒。

## 架构决策：方案 B（豆包管家主导感知层）

**核心原则**：豆包管家做"感知+执行+推送"，MA 做"记忆+分析"。

```
HA websocket
    ↓
豆包管家（实时中枢）
├── 事件队列（滑动窗口）
├── 规则引擎（毫秒级匹配）
├── 状态推断（位置/活动/谁在家）
├── 主动推送（微信/Bark/TTS）
├── agent_traces（对话记录）
│
├──→ 事件流喂给 MA（POST /api/events）
│       ↓
│   Memory Agent（记忆层）
│   ├── 长期记忆存储
│   ├── 凌晨分析（调豆包管家 API 查事件流+当前状态）
│   └── 发现新模式 → 返回豆包管家规则引擎
│
└──→ WebUI 展示所有状态
```

### 为什么不让 MA 主导感知层
- MA 是记忆服务（批量处理），不是实时事件引擎
- 推送通道（微信/Bark/TTS）都在豆包管家
- 故障隔离：MA 挂了不影响实时感知
- 现有基础设施在豆包管家（xiaomi_ear/agent_traces/推送通道）

### MA 对接 API（豆包管家提供）
MA 在做记忆分析时调用：
- `GET /api/events/recent?minutes=60` — 最近N分钟事件流
- `GET /api/state/current` — 当前家庭状态（谁在家、各房间状态）
- `POST /api/events` — 豆包管家写事件流到 MA

## 里程碑

### M1：事件流监听（核心基础）

- [ ] WebUI 实时事件流查看器

### M2：规则引擎（确定性场景识别）
预定义场景模板，按事件序列匹配：

| 场景 | 触发条件 | 推断结果 | 主动动作 |
|---|---|---|---|
| 进入书房工作 | 书房门开→关→灯亮→空调开 | 用户在书房工作 | 不打扰 |
| 人员移动轨迹 | 起居室→客厅→厨房→卫生间人体感应 | 用户当前在卫生间 | 更新位置 |
| 入睡 | 卧室门关→灯亮→空调开→灯灭（21:00后） | 用户已入睡 | 关客厅灯、调空调 |
| 离家 | 大门开→关→所有灯灭 | 用户外出 | 开启安防模式 |
| 回家 | 大门开→玄关灯亮 | 用户回家 | 开客厅灯、调空调 |
| 凯文玩Xbox | HDMI3开+凯文人脸识别+晚20:00后 | 凯文在玩游戏 | 21:00提醒收工 |
| 早晨起床 | 主卧灯亮（工作日6:30-7:30） | 用户起床 | 开电视切CCTV-1 |

规则定义格式：
```json
{
  "name": "入睡",
  "conditions": [
    {"entity": "door.bedroom", "state": "off", "within_min": 5},
    {"entity": "light.bedroom", "state": "on", "after_prev_min": 2},
    {"entity": "climate.bedroom", "state": "on", "after_prev_min": 2},
    {"entity": "light.bedroom", "state": "off", "after_prev_min": 5}
  ],
  "time_window": "21:00-23:59",
  "infer": "user_asleep",
  "action": "turn_off_living_room_light"
}
```

## 技术要点

### 事件格式
```json
{
  "ts": 1726156800,
  "entity_id": "binary_sensor.study_door",
  "state": "on",
  "room": "study",
  "type": "door"
}
```

### 滑动窗口
- 维护最近10分钟的事件队列（内存）
- 每次新事件进来，检查是否匹配已知场景模板
- 匹配到就更新用户状态
- 事件同时写入 SQLite（持久化，供 MA 凌晨拉取）
