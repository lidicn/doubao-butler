# 技能引擎 · 编排层对接文档

面向 Node-RED / Home Assistant 自动化的对接说明。管家只做「执行 + 安全阀」，
**触发时机、限流、免打扰归编排层**。

- 服务地址：`http://192.168.2.200:8095`
- 鉴权：所有 `/api/*`（除 `/api/health`）需 `Authorization: Bearer <redacted>`
  （`BUTLER_WEB_PASSWORD`，默认 `admin`）

---

## 1. 通道选型：HTTP 入 + MQTT 出

| 方向 | 通道 | 用途 |
|---|---|---|
| 入（主） | `POST /api/skill/{id}/run` | 编排层首选，**同步拿结果**（成功/失败/熔断/文本） |
| 入（兼容） | MQTT `butler/trigger/{id}` | memory-agent 等无 HTTP 场景 |
| 出（统一） | MQTT `butler/skill/{id}/done` | 编排层订阅做后续动作 |

为什么不用全 MQTT：

1. MQTT 是 fire-and-forget，编排层发完拿不到结果，要自己订阅 correlation 主题做配对；
2. MQTT 的 retained / QoS1 离线堆积会在管家重启后**补触发一串旧请求**——正好击中
   「编排层出问题不断触发 hello」这个要防的场景；HTTP 天然无此问题；
3. HTTP 一个 curl 就能测，MQTT 要 pub/sub 两端对着看。

## 2. HTTP 接口契约

### 2.1 `POST /api/skill/{skill_id}/run`（主入口）

请求体可选，任意 JSON 会作为 `ctx.payload` 透传给引擎：

```bash
curl -X POST http://192.168.2.200:8095/api/skill/hello/run \
  -H "Authorization: Bearer <redacted>" \
  -H "Content-Type: application/json" -d '{}'
```

响应：

```json
{
  "ok": true,
  "skill_id": "hello",
  "text": "晚上好，Kevin，作业写完了吗？",
  "status": "ok",
  "error": "",
  "dry_run": false,
  "meta": {
    "duration_ms": 1840,
    "role": "butler",
    "tv_online": true,
    "person": "Kevin",
    "dispatched": [
      {"device": "tv_living", "type": "tv", "ok": true},
      {"device": "xiao_living", "type": "xiaomi", "ok": true, "detail": "ok"}
    ]
  }
}
```

统一响应外壳：`{"ok": bool, "data": {...}}`；出错时 `{"ok": false, "error": "..."}`。

### 2.2 状态码与 `status` 取值

| HTTP | `status` | 含义 | 编排层建议 |
|---|---|---|---|
| 200 | `ok` | 执行成功并已输出 | 正常 |
| 200 | `dry` | 试跑（dry_run），未推送 | 仅预览 |
| 200 | `dedup` | 内容与近期重复，被去重跳过 | 忽略 |
| 200 | `tv_offline` | 电视离线，已降级 Bark | 可提示 |
| 200 | `error` | 引擎执行失败 | 记日志，别重试轰炸 |
| 400 | `not_found` | 技能不存在 | 检查 id |
| 400 | `disabled` | 技能未启用 | 先启用 |
| 400 | `engine_missing` | 引擎未加载 | 检查插件目录 |
| **429** | `breaker` | **熔断冷却中**，带 `retry_after` | **必须退避，别重试** |
| 400 | `daily_limit` | 当日硬上限到顶 | 当天别再触发 |
| 503 | — | runner 未就绪 | 稍后重试 |

> 关键：收到 **429** 表示管家已认定触发过密，编排层应立即停止重试并按
> `retry_after` 秒退避，否则会持续拉长冷却（指数退避）。

### 2.3 其它接口

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/api/skill/{id}/test` | WebUI 试跑：`dry_run=true`，**不推送**，disabled 也能跑 |
| GET | `/api/skill/{id}/runs?limit=50` | 运行历史（时间/来源/状态/耗时/结果） |
| GET | `/api/skills` | 技能列表 + `breaker` 状态 + `engines` 清单 |
| POST | `/api/skills` | 新建/更新技能（按 id upsert，经 schema 校验） |
| DELETE | `/api/skills/{id}` | 删除技能 |
| POST | `/api/hello` | **兼容端点**：内部转 `hello` 技能，响应含 `tv_online/person/nickname/scene/greeting/analyze_ok/status`，现有 NR flow 无需改动 |

### 2.4 试跑（推荐上线前先跑）

```bash
curl -X POST http://192.168.2.200:8095/api/skill/hello/test \
  -H "Authorization: Bearer <redacted>"
```

## 3. MQTT 通道

### 3.1 触发入口（兼容）：`butler/trigger/{skill_id}`

载荷为 JSON，会作为 `ctx.payload` 透传；`source` 记为 `mqtt`。

```bash
mosquitto_pub -h 192.168.2.200 -t butler/trigger/hello -m '{"room":"客厅"}'
```

### 3.2 结果出口：`butler/skill/{skill_id}/done`

每次运行结束广播（含失败/熔断），`status` 与 HTTP 的语义一致。

```bash
mosquitto_sub -h 192.168.2.200 -t 'butler/skill/+/done' -v
```

### 3.3 统一发声出口：`butler/speak/out`

供编排层把文本转到小爱 / Bark 等外部通道。

## 4. 安全阀（管家内置，编排层不用重复做）

| 机制 | 参数 | 行为 |
|---|---|---|
| 滑动窗口熔断 | 60s 内 ≥5 次 | 触发冷却，返回 429 + `retry_after` |
| 冷却退避 | 基准 300s，×2 递增（上限 ×2⁵） | 反复触发会越冷却越久 |
| 每日硬上限 | 技能 `limits.per_day` | 到顶返回 `daily_limit` |
| 全局并发 | VLM 信号量 = 1 | 视觉请求排队，避免并发打爆 |
| 内容去重 | 技能 `brain.dedup=true` | bigram 相似度过高则跳过（`dedup`） |
| 输出互斥 | 全局输出锁 | 占用中按 `on_busy: queue\|drop` 处理 |

查看实时状态：`GET /api/skills` → `breaker[id] = {window_hits, window_max, cooldown_remaining, tripped}`。

## 5. 角色（Persona）与设备路由

技能通过 `role` 字段归属角色，角色决定**音色**和**从哪个设备出声**：

```json
{
  "id": "food-calorie", "role": "xiaoyue", "enabled": false,
  "brain": {"engine": "camera_vlm", "mode": "live_vlm", "prompt": "..."},
  "output": [{"type": "tv_notify", "tts": true}],
  "limits": {"per_day": 10}, "on_busy": "drop"
}
```

- 默认角色：`butler`（主角色，全屋，TV + 客厅小爱）、`xiaoyue`（厨房/客厅，仅客厅小爱PRO右）
- 角色定义：`data/roles/{id}.json`；设备定义：`data/devices.json`
- 分发规则：角色配了 `output_devices` 就以**角色设备为准**（tv=音频 URL 播放；xiaomi=HA 文本推送）；
  否则回退技能 `output` 类型（兼容旧技能）
- 设备全不可用 → 按角色 `fallback`：`silent` / `tv` / `bark`

相关 API：`GET|POST /api/roles`、`DELETE /api/roles/{id}`、`POST /api/roles/{id}/try`（音色+设备试跑）、
`GET|POST /api/devices`、`DELETE /api/devices/{id}`。

## 6. 用户插件引擎

内置引擎与用户插件**同协议**：

1. 复制模板：
   ```bash
   docker exec doubao-butler cp -r /app/butler/skills/engines/_template_ /app/data/plugins/my_engine
   ```
2. 改 `data/plugins/my_engine/manifest.json` 的 `id`/`name`，改写 `engine.py`
3. `docker restart doubao-butler`，WebUI「技能」页引擎下拉可见（`_` 前缀目录会被跳过，即模板本身）

引擎协议：

```python
async def run(self, ctx) -> SkillResult
# ctx.skill / ctx.rt / ctx.role / ctx.source / ctx.dry_run / ctx.payload
# 输出推送由 runner 按角色 output_devices 统一分发，引擎只需产出 SkillResult.text
```

### 7.2 订阅 done 事件做后续编排

再加一个 `mqtt in` 节点：

- 主题：`butler/skill/+/done`
- 输出：JSON，接 `switch` 按 `payload.status` 分流（如 `ok` → 开灯 / `error` →  Bark 告警）

### 7.3 典型编排建议

- 触发时机（回家/门磁/时间段）与免打扰（深夜/午睡）放在编排层；
- 用 `inject` + `traffic`/`delay` 节点做编排层自己的限流；
- **收到 429 必须停止重试**，否则管家冷却会指数拉长。

## 8. 排错手册

| 现象 | 排查 |
|---|---|
| 某角色/技能不出声 | WebUI「角色」页点「试跑」，看 `dispatched` 里每个设备的 `ok`；或 `POST /api/roles/{id}/try` |
| 某个音色不响 | `POST /api/tts/voices` 会逐一合成并返回 `{voice, ok, bytes, error}`，直接定位非法/无音频的音色 |
| 一直 429 | `GET /api/skills` 看 `breaker` 的 `cooldown_remaining`，等冷却；排查编排层是否在疯狂重试 |
| 引擎没出现在下拉 | 看容器日志 `docker logs doubao-butler \| grep engine`，插件目录/类名错误会被跳过 |
| 看不到运行记录 | `GET /api/skill/{id}/runs?limit=50`；或查表 `skill_runs` |
| 电视不播 | 检查 `tv/livingroom/status` 是否 online；离线时按角色 `fallback` 降级 |

常用命令：

```bash
docker logs -f doubao-butler --tail 100
curl -s -H "Authorization: Bearer <redacted>" http://192.168.2.200:8095/api/skills | head -c 800
```
