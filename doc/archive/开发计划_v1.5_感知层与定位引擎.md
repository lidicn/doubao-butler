> 创建：2026-09-09 | 修订：2026-09-10（MA 协同分工对齐）
> 版本：v1.5
> 核心理念：用户定位是家庭自动化的第一性原理。不知道用户在哪，再聪明的决策也会推错地方。
> 架构决策（2026-09-10 与 MA 对齐）：**分层分工** —— MA 做"识别和记忆"（视觉/ArcFace/作息规律/行为推断），管家做"融合和决策"（实时定位融合+决策执行）。HA 采数据 → 管家融合推理 → 管家决策执行。NR 不参与。

## 一、背景与问题

### 1.1 当前痛点
- 通知推错房间：用户在书房，通知推送到了卫生间音箱
- TTS 播错设备：不知道用户在哪个房间，只能固定播书房或全屋
- 技能触发不精准：人在传感器只知道"有人"，不知道"是谁"，无法做个性化响应
- 决策层"盲目"：没有准确的用户位置，再聪明的决策也会执行在错误的地方

### 1.2 现有感知资源（比想象的更丰富）

| 信号源 | 覆盖 | 能识别"是谁" | 置信度 | 延迟 | 数据源 |
|---|---|---|---|---|---|
| 人在传感器 | 全屋覆盖（每区域≥1个） | ❌ | 高 | 秒级 | HA binary_sensor.xxx_occupancy |
| ArcFace（客厅TV端） | 客厅 | ✅ | 高 | 5-10秒 | TVPilot arcface apk → MA 识别 → MQTT `ma/presence`（管家订阅，不直接监听 TV） |
| 米家摄像头×3 | 客厅/书房/起居室 | ❌（需VLM分析） | 中 | 10秒+ | HA camera.xxx |
| ESP32 + iOS通知 | 书房 | ✅（lidicn） | 高 | 实时 | ESP32 → MQTT/HTTP 上报 |
| Kevin米兔手表 | 全屋（HA定位） | ✅ | 高 | 分钟级 | HA device_tracker.kevin |
| Emily小天才手表 | 待确认接入 | ✅ | 待确认 | 待确认 | 待确认 |
| 小米BE7000路由 | 全屋（被动监听） | ❌（设备在线） | 中 | 分钟级 | tcpdump ARP/DHCP（P2） |

### 1.3 架构决策：为什么融合推理放在管家？

| 维度 | HA | NR | 豆包管家 |
|---|---|---|---|
| 复杂推理能力 | ❌ template/automation 笨拙 | ❌ 无状态流程 | ✅ Python 灵活表达 |
| 状态持久化 | ✅ 实体状态 | ❌ 无状态 | ✅ runtime + SQLite |
| 与决策层耦合 | ❌ 跨进程 | ❌ 跨进程 | ✅ 同进程，延迟最低 |
| LLM 增强 | ❌ | ❌ | ✅ 可自然语言查询"Kevin在哪？" |
| 数据采集 | ✅ 已有大量实体 | ✅ 简单管道 | ❌ 不适合 |

**结论**：HA 做数据采集层（已有 device_tracker/person/binary_sensor），管家做融合推理层（Python 复杂算法+与决策紧耦合），NR 不参与。

## 二、P0-1 多源融合定位引擎（核心，3天）

### 2.1 模块结构

```

├── __init__.py          # PresenceEngine 主类
├── sources.py           # 信号源适配器（HA/ArcFace/ESP32/手表）
├── fusion.py            # 加权置信度融合算法
```

### 2.2 数据模型

```python

    "last_seen": "2026-09-09T21:00:00",  # 最后确认时间

# 房间状态
RoomState = {

    "users": ["kevin", "emily"],     # 推断在该房间的用户
    "unknown_person": False,          # 是否有无法识别的人
    "last_motion": "2026-09-09T21:00:00"
}
```

### 2.3 融合算法：加权置信度

**信号权重定义**：

| 信号类型 | 权重 | 说明 |
|---|---|---|
| arcface_recognized | 1.0 | ArcFace 直接识别到用户 |
| esp32_ios_notification | 0.95 | ESP32 检测到 lidicn iPhone 通知 |
| watch_location | 0.85 | 手表定位在某区域 |
| router_device_online | 0.5 | 路由器检测到设备在线（辅助） |
| occupancy_sensor | 0.3 | 人在传感器触发（只知道有人，不知道是谁） |

**融合公式**：

```
对于每个用户 u 和每个房间 r：
  score(u, r) = Σ (weight(signal) * match(signal, u, r))
  confidence(u, r) = sigmoid(score(u, r) - threshold)

最终位置 = argmax_r confidence(u, r)
如果 max confidence < 0.6 → 位置未知
```

### 2.4 身份排除推理

当人在传感器触发但无法识别身份时，使用排除法：

```
已知：
  - lidicn 在书房（ESP32，置信度 0.95）
  - kevin 在学校（手表定位，置信度 0.9）
  - emily 位置未知

事件：客厅人在传感器触发

推理：
  - 不可能是 lidicn（在书房）
  - 不可能是 kevin（在学校）
  - 推断是 emily 或访客（置信度 0.6）
  - 如果 emily 手表也在客厅 → 确认是 emily（置信度提升到 0.85）
```

### 2.5 时间规律学习（弱信号）

基于历史数据学习用户日常规律，作为低置信度先验：

```
规律示例：
  - 工作日 9:00-18:00 → lidicn 通常在书房（先验置信度 0.4）
  - 周末 20:00-22:00 → 全家通常在客厅（先验置信度 0.3）
  - 22:00 后 → kevin/emily 通常在卧室（先验置信度 0.4）

当强信号缺失时，用规律作为先验补充。
```

### 2.6 信号源适配器

**HA 适配器**（sources.py）：
- 定时拉取（每 10 秒）：HA `/api/states` 过滤 binary_sensor.*_occupancy、device_tracker.*、person.*
- 事件订阅：HA WebSocket 订阅 state_changed 事件（实时推送，比轮询更及时）

**ArcFace 适配器**：
- 监听 TVPilot 上报的 face_detected 事件（通过 webhook 或 MQTT）
- 事件格式：`{"user": "lidicn", "room": "客厅", "confidence": 0.9, "ts": "..."}`

**ESP32 适配器**：
- 监听 ESP32 上报的 iOS 通知事件（HTTP/MQTT）
- 事件格式：`{"user": "lidicn", "room": "书房", "event": "notification_received", "ts": "..."}`

## 三、P0-2 房间级 TTS 路由（1天）

### 3.1 功能说明

基于定位引擎，TTS/技能播报自动选择用户所在房间的小爱音箱：

- **单用户**：播报到该用户所在房间的音箱
- **多用户在不同房间**：分别播报（如果消息是给所有人的）
- **指定用户**：播报到该用户所在房间
- **置信度 < 60%**：回退默认音箱（书房）+ 在消息中询问"你在哪个房间？"
- **全屋广播**：保留 `room=all` 选项，强制所有音箱播报

### 3.2 实现方案

修改 `tts_routes.py` 的 `_speak_to_device`：

```python
async def _speak_to_device(text, role, room=None, device_id=None, ...):
    # 如果指定了 device_id，直接用（兼容现有调用）
    if device_id:
        return await _speak_to_entity(text, device_id, ...)

    # 如果指定了 room，用该房间的音箱
    if room:
        return await _speak_to_room(text, room, ...)

    # 基于角色定位：找到角色对应用户所在房间
    presence = rt.presence.get_user_presence(role_to_user(role))
    if presence and presence.confidence >= 0.6:
        return await _speak_to_room(text, presence.room, ...)

    # 置信度不足，回退默认音箱
    return await _speak_to_room(text, "书房", ...)
```

配置每个房间对应的小爱音箱 entity_id：

## 四、P0-3 决策请示机制（2天）

### 4.1 功能说明

管家在遇到需要用户决策的情况时，推送 A/B/C 选项到 Bark/看板，用户选择后回调执行。

**使用场景**：
- TP/DP 开发遇到技术选型，需要 PM 决策
- 设备巡检发现异常，询问是否自动修复
- 防沉迷触发，询问是否强制停止
- 小甜菜 Vibe coding 场景：lidicn 在电竞沙发，电视端弹出决策选项

### 4.2 数据模型

```python
DecisionRequest = {
    "id": "dec_20260909_001",
    "title": "TVPilot 编译环境选择",
    "description": "ArcFace 编译需要 Android SDK，选哪个方案？",
    "options": [
        {"key": "A", "label": "使用 TP 现有编译环境", "description": "复用，零成本"},
        {"key": "B", "label": "新建独立编译环境", "description": "隔离，但需要配置"},
        {"key": "C", "label": "延迟决策", "description": "先记录，稍后处理"}
    ],
    "status": "pending",  # pending / approved / rejected / timeout
    "selected": None,     # 用户选择的 option key
    "callback_url": "http://tp:8080/api/decision/dec_001",  # 回调地址
    "channel": ["bark", "dashboard", "tv"],  # 推送渠道
    "created_at": "...",
    "expires_at": "...",  # 过期时间（默认24小时）
}
```

### 4.3 API 设计

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/decisions` | 创建决策请求（TP/DP/管家技能调用） |
| GET | `/api/decisions` | 决策列表（待处理/已处理/已过期） |
| GET | `/api/decisions/{id}` | 决策详情 |

### 4.4 推送渠道

**Bark 推送**：
- 标题：决策请求标题
- 正文：描述 + 选项列表
- URL：看板决策页面链接（用户点击后打开看板选择）
- level：timeSensitive（时间敏感）
- group：decision

**看板 PWA**：
- 新增"决策"Tab，显示待处理决策列表
- 每个决策卡片显示标题/描述/选项按钮
- 用户点击选项后调用 `/api/decisions/{id}/respond`

**电视端（小甜菜，P2）**：
- lidicn 在电竞沙发时（ArcFace 检测），小甜菜弹出决策选项
- 遥控器选择 A/B/C
- Edge 语音提醒"有新的决策需要处理"

### 4.5 回调机制

用户选择后，管家：
1. 更新决策状态为 approved，记录 selected
2. 调用 callback_url（如果有），POST `{"decision_id": "...", "selected": "A", "label": "..."}`
3. Bark 推送确认"已选择 A，已通知相关方"
4. 如果回调失败，重试 3 次，仍失败则标记为"回调失败，需手动通知"

## 四点五、P0-4 MA ma/presence MQTT 信号源对接（1天）

### 4.5.1 背景

memory-agent v0.4 已实现 MQTT 实时推送，其中 `ma/presence` 主题发布成员在场快照（来自 ArcFace 视觉识别）。这是管家定位引擎的**最强信号源**（权重 1.0），比从 HA 人在传感器推断准确得多——ArcFace 能直接识别"是谁在客厅"，而人在传感器只知道"客厅有人"。

### 4.5.2 MA 推送格式

**主题**：`ma/presence`（retain，默认 60s 周期，内容变化才发）

**载荷**：
```json
{
  "members": [
    {"name": "lidicn", "member_id": "lidicn", "room": "客厅",
     "via": "arcface", "confidence": 0.95, "last_seen": 1789000000,
     "trigger": "face_detected"}
  ],
  "total": 1,
  "ts": "2026-09-10T10:00:00"
}
```

### 4.5.3 实现方案

在 `butler/presence/sources.py` 新增 `MaPresenceSource` 类：

1. **订阅 MQTT**：复用管家已有的 MQTT 客户端（`rt.mqtt`），订阅 `ma/presence` 主题
2. **解析载荷**：收到消息后解析 JSON，提取每个成员的 name/room/confidence
3. **上报信号**：调用 `engine.report_signal("arcface_recognized", member_id, room, confidence)`
4. **房间映射**：MA 的房间名（如"客厅"）需要映射到管家的 room_id（如"living_room"），在 presence_config.json 中增加 `room_name_map` 配置
5. **降级**：MQTT 连接失败时不影响其他信号源，仅日志警告

### 4.5.4 配置

在 `presence_config.json` 增加：
```json
{
  "ma_presence": {
    "enabled": true,
    "topic": "ma/presence",
    "signal_type": "arcface_recognized",
    "default_weight": 1.0
  },
  "room_name_map": {
    "客厅": "living_room",
    "书房": "study",
    "主卧": "master_bedroom",
    "儿童房": "kids_room",
    "卫生间": "bathroom"
  }
}
```

### 4.5.5 验收标准

- [ ] 管家订阅 `ma/presence` 主题成功
- [ ] MA 推送在场消息后，管家定位引擎收到 arcface_recognized 信号
- [ ] 用户位置更新为 MA 报告的房间，置信度 ≥ 0.9
- [ ] 房间名映射正确（MA 的"客厅"→管家的"living_room"）
- [ ] MQTT 断开时不影响 HA 信号源，重连后自动恢复
- [ ] MA 信号丢失超过 60 秒时自动降级（HA 权重提升+阈值降低），日志告警
- [ ] MA 信号恢复后自动恢复正常权重，日志通知

### 4.5.6 MA 信号降级策略（管家侧自主实现）

**背景**：MA `ma/presence` 是定位引擎最强信号（ArcFace 权重 1.0），但 MA 宕机或 MQTT 断连时该信号丢失，定位精度会大幅下降。需要自动降级保证定位不中断。

**降级触发条件**：
- 最后一次收到 `ma/presence` 消息超过 **60 秒**
- 或 MQTT 连接断开超过 30 秒

**降级动作**（仅影响融合算法的权重配置，不改变数据结构）：
| 参数 | 正常值 | 降级值 | 说明 |
|---|---|---|---|
| occupancy_sensor 权重 | 0.3 | 0.5 | 人在传感器权重提升 |
| person_home 权重 | 0.4 | 0.6 | 人员在家状态权重提升 |
| confidence_threshold | 0.6 | 0.45 | 置信度阈值降低，避免用户位置变未知 |

**恢复条件**：
- 收到新的 `ma/presence` 消息 → 立即恢复正常权重
- 日志：`"MA presence signal restored, normal mode"`

**实现位置**：`butler/presence/fusion.py` 的 `FusionEngine` 中增加 `degraded_mode` 标志，`MaPresenceSource` 跟踪最后消息时间，轮询循环检查并切换。

## 四点六、P0-5 记忆统一入库（source=butler + 专属 app_token）（1天）

### 4.6.1 背景

memory-agent v0.5 已实现记忆统一入库：`agent_memories` 表新增 `source` 字段（ma/butler/vision/manual），复用 `trust` 字段作为 confidence。v0.6 支持多 app_token + 按 token 派生来源（防止伪造）。

管家当前写入记忆时**没有标记 source**，会被当成 MA 原生记忆（source=ma），无法隔离低置信 LLM 摘要。需要：
1. 在 MA 创建专属 app_token（source=butler）
2. 管家写入记忆时走该 token，落库 source=butler
3. 检索时可按 source 过滤

### 4.6.2 实现方案

**步骤 1：在 MA 创建专属 app_token**
- 调用 MA 的 `POST /api/config/app-tokens`，创建 name="butler-core", source="butler" 的令牌
- 保存令牌到管家配置（`data/ma_config.json` 或环境变量）
- 该令牌只允许访问 `/api/insights/query` 和 `/api/agent/memories`（v0.6 APP_ENDPOINTS 已放开）

**步骤 2：管家记忆写入改用 app_token**
- 找到管家当前写入记忆的代码（`butler/integrations/memory_agent.py` 或类似）
- 将 Authorization 头从 JWT/butler_token 改为 `Bearer <butler_app_token>`
- v0.6 会强制 source=butler（令牌派生覆盖调用方自报），即使 body 谎报 source=其他也会被覆盖

**步骤 3：检索支持 source 过滤**
- 管家检索记忆时，可传 `source="ma"` 只召回 MA 原生高置信事实
- 或 `source="butler"` 单独看管家摘要
- 默认不限制（混合检索）

### 4.6.3 低置信隔离机制

MA 已实现的隔离（管家无需额外开发）：
1. 管家写入的记忆 source=butler，可被检索按来源过滤
2. 写入默认 state=staging，永不自动进 live，需 promote/sweep 晋升
3. 晋升需满足"高置信佐证 insight"或"跨 ≥N 天观测"——管家低置信摘要很难自动升级
4. 检索侧可 `retrieve(question, source="ma")` 只召高置信事实

### 4.6.4 验收标准

- [ ] MA 中存在 source=butler 的专属 app_token
- [ ] 管家写入记忆时使用该 token
- [ ] MA 中新增的记忆 source=butler（非 ma）
- [ ] 即使 body 谎报 source=其他，落库仍为 butler（令牌派生覆盖）
- [ ] 管家检索时可按 source=ma/butler 过滤
- [ ] 管家写入的记忆默认 state=staging，不自动进 live

## 八、风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| HA WebSocket 连接不稳定 | 定位更新延迟 | 降级为 10 秒轮询；WebSocket 断线自动重连 |
| ArcFace 事件上报格式不统一 | 定位引擎无法解析 | 定义统一事件格式，交接单通知 TP |
| ESP32 蓝牙扫描功耗高 | ESP32 续航下降 | 低功耗扫描（每 30 秒扫描 5 秒） |
| 人在传感器误报 | 定位不准确 | 多源融合降低单传感器权重；连续 3 次触发才确认 |
| 手表定位延迟高 | 实时性不足 | 手表作为辅助信号，主要靠人在传感器+ArcFace |
