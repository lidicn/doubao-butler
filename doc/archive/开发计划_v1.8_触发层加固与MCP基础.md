# 开发计划 v1.8 — 触发层加固 + 推送风控层 + MCP Server 基础

> 创建：2026-09-10
> 基准：v1.7 P0 完成（晨起场景/时序数据/异常检测）
> 核心理念：借鉴 Node-RED TTS 队列 v3 的工业级风控思想，建立统一推送风控层；加固触发层解决静默失败；启动 MCP Server 基础框架让外部 agent 安全只读访问

---

## 版本目标

1. **推送风控层（PushGuard）**：统一管理所有主动推送（Bark/TTS），杜绝"异常检测疯狂推送"这类灾难
2. **触发层加固**：统一注册中心 + 执行审计 + 健康监控，解决"定时任务静默失败"问题
3. **MCP Server 基础**：stdio + HTTP 双传输 + Token 鉴权 + 只读能力暴露，为外部 agent（opencode/豆包工作）接入打基础

### P0-1 推送风控层 PushGuard ✅ 已完成部署

**模块**：`butler/guard/push_guard.py`、`butler/guard/api.py`、`butler/guard/__init__.py`

**设计要点**（借鉴 NR TTS 队列 v3，针对管家优化）：

| 机制 | NR 做法 | 管家 PushGuard |
|---|---|---|
| 状态持久化 | global 变量（重启丢失） | SQLite（重启恢复） |
| 熔断粒度 | 全局 | 按 group+priority 多维度 |
| critical 穿透 | 穿透但清空所有熔断 | 穿透但不影响其他维度 |
| 过载通知 | 走 TTS（TTS坏了播不出） | 走 Bark（独立通道） |
| 可观测性 | 只有 debug 节点 | REST API + 审计日志 |

**五层防护**：
1. L1 模式感知：睡眠/观影模式自动降级（调用方在调用前检查模式）
2. L2 多维度熔断：按 (group, priority) 分别计数，5/60s 触发，冷却 120s
3. L3 全局过载：15/60s 触发，暂停 300s；Bark 合并摘要，TTS 队列+暂停
4. L4 TTL 过期：critical 不过期，warning 30min，info 5min
5. L5 队列上限：TTS 队列 10 条，超过丢弃最旧非 critical

**优先级体系**：
- critical：音量 80，可穿透熔断，不过期，TTS 插队队首+释放锁
- warning：音量 60，不可穿透，TTL 30min，TTS 插队到 critical 之后
- info：音量 30，不可穿透，TTL 5min，TTS 队尾

**API**：
- `GET /api/guard/status`：风控状态（熔断维度/队列长度/最近审计）
- `POST /api/guard/reset`：重置风控状态（可指定 channel）
- `GET /api/guard/audit`：查询审计日志（limit/group/action 过滤）

**SQLite**：`/app/data/push_guard.db`，表 `push_audit`（所有推送决策审计）

**验证结果**（2026-09-10）：
- 连续 5 条 info 通过，第 6 条触发熔断 ✅
- 熔断后第 7 条被丢弃（120s 冷却）✅

- 状态 API 正确显示熔断维度和冷却时间 ✅
- 审计日志完整记录所有决策 ✅

### P0-5 触发层统一注册中心 ✅ 已完成部署

**模块**：`butler/triggers/registry.py`（新建）

**背景**：v1.7 验证时发现 4 个定时任务全部报 `RuntimeError: no running event loop`，根因是 APScheduler 的 job 在独立线程执行，`asyncio.create_task` 需要运行中的事件循环。这类静默失败很难发现，需要统一注册中心监控所有触发源的健康状态。

**设计**：
```python
@dataclass
class TriggerSource:
    id: str              # 唯一 ID，如 "sched:anomaly_detector"
    type: str            # "scheduler" / "rule" / "mqtt" / "polling"
    name: str            # 可读名称
    status: str          # "running" / "paused" / "error" / "unknown"
    last_run_at: float   # 最后执行时间
    last_result: str     # 最后执行结果（"success" / "error: xxx"）
    last_duration_ms: int
    success_count: int
    fail_count: int
    enabled: bool
```

**功能**：
1. 注册：所有触发源（APScheduler 定时任务/Trigger 规则层/MQTT 订阅/后台轮询）启动时注册到中心
2. 心跳：每次执行开始/结束时更新状态
3. 健康检查：API 查询所有触发源状态，异常源（超过预期周期未执行/连续失败）标红
4. 统一管理：API 可暂停/恢复/手动触发指定触发源

**集成点**：
- app.py 中所有 APScheduler job 注册时同时注册到 TriggerRegistry
- TriggerEngine 执行规则时更新注册中心
- MQTT 订阅回调更新注册中心

**API**：
- `GET /api/triggers/health`：列出所有触发源健康状态
- `POST /api/triggers/{id}/pause`：暂停指定触发源
- `POST /api/triggers/{id}/resume`：恢复指定触发源
- `POST /api/triggers/{id}/trigger`：手动触发指定触发源（测试用）

**预估**：2 天

### P0-7 薄 MCP 适配层 ✅ 已完成部署

**模块**：`butler/mcp/`（新建）

**定位**：做薄做窄，只服务于"外部 agent（opencode/豆包工作/千问工作）编写管家实时决策触发规则"这个核心需求。不搞大而全的 MCP Server。

**与 autoflow 的分工**：
- **管家 MCP**：负责管家实时决策触发规则（涉及对话上下文/MA行为信号/管家技能执行，autoflow 表达不了）
- **autoflow MCP**：负责持久化家庭自动化规则（提案闸→验证链→NR执行）
- 管家通过 `autoflow_propose` 技能把持久化规则委托给 autoflow

**MCP 设计原则（薄 MCP 适配层）**：
1. **做薄做窄**：v1.8 只暴露 6 个 Tools（触发规则 CRUD + run_skill + send_bark）+ 3 个只读 Resources
2. **Schema 自动生成**：从 `core/tools.py` 的 OpenAI function-calling 格式自动生成 MCP Tool Schema，不手写第二套
3. **鉴权复用**：MCP Token = 管家现有 API Token，不另建 Token 体系；Token 权限等级（readonly/readwrite/admin）复用现有配置
4. **审计复用**：MCP 调用记录到管家现有审计日志（跟 push_audit/trigger_audit 统一管理），不另建审计表
5. **分离领域逻辑与 MCP 适配层**：`adapters/` 目录只做参数转换和结果包装，不包含业务逻辑；核心逻辑不动
6. **高风险操作 Server 侧硬编码授权**：外部 agent 绕过不了；高风险操作需 `confirm=true` 参数
7. **走 PushGuard 风控**：send_bark 等推送类 Tool 自动经过 PushGuard 风控检查

**文件结构**：
```
butler/mcp/
├── __init__.py          # 模块入口
├── server.py            # MCP Server 核心（JSON-RPC 处理+能力分发）
├── transport_http.py    # Streamable HTTP 传输（SSE）
├── transport_stdio.py   # stdio 传输（可选，本地调试用）
├── auth.py              # Token 鉴权（复用管家 API Token 体系）
├── schema_gen.py        # Schema 自动生成（从 core/tools.py 定义生成 MCP Tool Schema）
├── adapters/            # 领域逻辑→MCP 适配层（只做参数转换，不含业务逻辑）
│   ├── triggers.py      # 触发规则 CRUD 适配
│   ├── skills.py        # 技能执行适配
│   └── bark.py          # Bark 推送适配
└── audit.py             # MCP 调用审计（复用管家现有审计体系）
```

**传输**：
- **HTTP（主）**：`POST /api/mcp` 承载客户端请求，SSE 推送流式消息；每个请求携带版本与能力元数据
- **stdio（可选）**：本地调试用，stdout 只传协议，日志走 stderr

**鉴权**：
- 复用管家现有 API Token（`BUTLER_WEB_PASSWORD` / Bearer Token 体系）
- 3 个权限等级：`readonly`（只读）、`readwrite`（读写）、`admin`（全权限）
- Token 存在配置文件，不硬编码
- 不另建 Token 体系，不做 OAuth（家庭场景 Token 足够）

**能力发现**：
- `initialize`：协议版本握手 + 双方身份
- `tools/list`：列出所有 Tools（含 name/description/inputSchema，Schema 自动生成）
- `resources/list`：列出所有 Resources（含 uri/name/description）
- `prompts/list`：v1.9 实现（v1.8 不暴露 Prompts）

**v1.8 暴露的能力**（薄 MCP，只服务于"外部 agent 编写触发规则"）：

| 类型 | 名称 | 风险等级 | 权限 | confirm | 说明 |
|---|---|---|---|---|---|
| Tool | `create_trigger` | 中/高风险 | readwrite | 中风险否/高风险是 | 创建管家实时决策触发规则 |
| Tool | `list_triggers` | 只读 | readonly | - | 列出触发规则 |
| Tool | `update_trigger` | 中/高风险 | readwrite | 高风险是 | 更新触发规则 |
| Tool | `delete_trigger` | 高风险 | readwrite | 是 | 删除触发规则 |
| Tool | `run_skill` | 中风险 | readwrite | 危险技能是 | 执行白名单内管家技能 |
| Tool | `send_bark` | 低风险 | readwrite | 否 | 发送 Bark（走 PushGuard 风控） |
| Resource | `butler://triggers` | 只读 | readonly | - | 触发规则列表 |
| Resource | `butler://skills` | 只读 | readonly | - | 可用技能列表（白名单内） |
| Resource | `butler://guard/status` | 只读 | readonly | - | 推送风控状态 |

**错误模型**：
- 区分协议错误（JSON-RPC error）和业务失败（Tool result 中的 error 字段）
- 错误要能定位、重试或降级
- 不用一段自然语言包住所有状态

**工程规范**：
- 分离领域逻辑与 MCP 适配层：adapters/ 目录只做参数转换和结果包装，不包含业务逻辑
- Schema 自动生成：不手写第二套 Schema，从 `core/tools.py` 的 OpenAI function-calling 定义自动转换
- stdout 只传协议，日志走 stderr
- 异步、配置和依赖注入可测试

**预估**：2 天

### P1-2 MCP Tools 暴露（触发规则管理+技能执行） ⏳ 待开发

实现 6 个 Tools 的适配层（Schema 从现有工具定义自动生成，不手写第二套）：

1. **`create_trigger(trigger_json, confirm)`**：
   - 调用 TriggerEngine 创建触发规则
   - 输入 Schema：trigger_json（object, required，触发规则定义）、confirm（bool, default false，高风险规则需 confirm=true）
   - 风险判定：规则动作只含只读/通知类→低风险直接生效；含设备控制/模式切换→高风险需 confirm=true
   - 输出：`{created: bool, trigger_id: str, risk_level: str, need_confirm: bool}`
   - 描述："创建管家实时决策触发规则。何时调用：用户要求创建长期触发规则时。何时不要调用：会话内临时提醒（<1h）用 set_reminder；持久化家庭自动化规则（如每晚十点半熄灯）用 autoflow_propose 技能委托 autoflow"

2. **`list_triggers(filters)`**：
   - 列出触发规则，支持按 event/enabled/risk_level 过滤
   - 只读，无副作用

3. **`update_trigger(trigger_id, trigger_json, confirm)`**：
   - 更新触发规则，高风险更新需 confirm=true
   - 保留版本历史（v1.9 完善版本管理，v1.8 先记录更新日志）

4. **`delete_trigger(trigger_id, confirm)`**：
   - 删除触发规则，必须 confirm=true（高风险操作，Server 侧硬编码）
   - 输出：`{deleted: bool, trigger_id: str}`

5. **`run_skill(skill_id, params, confirm)`**：
   - 执行白名单内技能（白名单：查询类/分析类/通知类，不包含直接控制设备类）
   - 危险技能不在白名单内，调用返回错误
   - 输入 Schema：skill_id（str, required）、params（object, optional）、confirm（bool, default false）
   - 输出：技能执行结果（结构化）

6. **`send_bark(title, body, priority, group)`**：
   - 调用 `rt.bark.push()`（自动走 PushGuard 风控）
   - 输入 Schema：title（str, required）、body（str, required）、priority（enum: critical/warning/info, default info）、group（str, optional）
   - 输出：`{sent: bool, decision: str, reason: str}`
   - 描述："发送 Bark 推送到用户手机。何时调用：需要通知用户时。何时不要调用：频繁推送（会被风控熔断）"

每个 Tool 有：
- 明确的 name（snake_case）
- description（何时调用/何时不要调用/副作用说明）
- inputSchema（JSON Schema，从现有工具定义自动生成，限制参数边界）
- 结构化输出（不用自然语言包住状态）
- 错误模型（区分参数错误/业务失败/依赖不可用）

### P1-3 autoflow_propose 技能 + 触发边界路由 ✅ 已完成部署

**背景**：触发层"切一刀"——实时决策触发留管家，持久化家庭自动化规则委托 autoflow（提案闸→编译闸→vhass孪生自证→人审→NR执行）。autoflow 有七轮验证链，管家自研持久化规则等于重新踩坑。

**新增技能**：`autoflow_propose`

**功能**：
- 用户说"以后每当X就Y"且 X/Y 都是 HA 设备域事件/状态时，调用 autoflow 提案闸
- 调用方式：`POST /api/arena/propose` 或 MCP `autoflow_propose_dsl`（autoflow 已实现）
- 把用户描述转为 autoflow DSL 提案，提交到 autoflow 竞技场
- 回执里的 `knowledge_feedback`（验证链反馈：编译结果/重放结果/断言结果/风险提示）直接透给用户
- 用户在 autoflow WebUI 场景提案面板人审批准后，规则才部署到 NR

**触发边界路由判定准则**（写进技能说明和管家 skills 路由）：

```
用户说了一句"以后每当X就Y"：
├─ X/Y 都是 HA 设备域事件/状态 ──────────→ autoflow_propose（DSL 可表达，走验证链）
├─ X 涉及 MA 行为/位置/视觉信号 ─────────→ 两种：
│    ├─ 管家能订阅 ma/# 信号实现 ────────→ autoflow_propose（触发源挂 MQTT 事件）
│    └─ 需要实时融合判断才成立 ──────────→ 管家引擎（这是决策不是自动化，create_trigger）
├─ Y 是 DeskPilot/TVPilot 设备动作 ──────→ 管家技能（ReAct 工具，本来就归管家，create_trigger）
├─ 会话内临时（<1h，如"等会儿提醒我"）──→ 管家引擎 + PushGuard（set_reminder，不持久化）
└─ 拿不准 ──────────────────────────────→ 问用户要不要"长期生效"，要 → autoflow_propose
```

**与 v1.8 触发层加固的配合**：

### 触发层加固
- 所有定时任务在注册中心可见，状态正确
- 定时任务执行失败时，注册中心标记 error，WebUI 标红
- 触发执行审计可查询，包含执行结果和耗时
- 手动暂停/恢复/触发指定触发源正常工作

### 薄 MCP 适配层
- HTTP 模式：`POST /api/mcp` 能处理 initialize/tools/list/resources/list/call
- stdio 模式（可选）：MCP Inspector 能发现 3 个 Resources + 6 个 Tools
- Token 鉴权：readonly Token 不能调用 create_trigger/run_skill（返回 403）
- Schema 自动生成：tools/list 返回的 inputSchema 与 core/tools.py 定义一致（不手写第二套）
- 只读 Resource 读取返回正确数据（triggers/skills/guard/status）
- create_trigger 调用：低风险规则直接生效，高风险规则 confirm=false 时返回 need_confirm
- delete_trigger 调用：confirm=false 时被拒绝（Server 侧硬编码）
- send_bark Tool 调用后手机收到 Bark（走 PushGuard 风控）
- run_skill 调用：白名单内技能正常执行，危险技能返回错误
- 坏参数返回明确错误（不崩溃）
- MCP 调用审计可查询（复用管家现有审计体系）
- autoflow_propose 技能：用户说"每晚十点半熄灯"→ 调用 autoflow 提案闸 → 返回 knowledge_feedback
- 触发边界路由：HA设备域规则走 autoflow_propose，MA行为信号实时融合规则走 create_trigger
