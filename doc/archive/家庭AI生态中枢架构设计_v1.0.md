# 家庭AI生态中枢架构设计

> 版本：v1.0  
> 日期：2026-09-07  
> 状态：待评审  
> 作者：豆包管家架构组

---

## 一、背景与问题

当前家庭AI生态由6个核心项目组成，各自独立发展，存在以下问题：

1. **LLM 调用分散**：butler 24处 + ma 18处 = 42处独立调用，无统一调度
2. **记忆分散**：对话记忆在 butler（SQLite），视觉记忆在 ma（ChromaDB），无关联
3. **重复建设**：两套 skills 系统、两套 insights 逻辑、两套 MCP/ACP Server
4. **职责模糊**：autoflow 和 butler 都在做编排，ma 和 TV_CAM 都在做视觉
5. **限流冲突**：butler 和 ma 独立抢 new-api 配额，容易互相 429

## 三、四方案横向对比

### 方案A：butler + ma 合并为中枢

- **优点**：统一LLM调用、统一记忆、单点管理
- **缺点**：
  - 38k行单体，职责混乱（对话+视觉混在一起）
  - 视觉CPU密集型挤占对话响应
  - 单点故障：视觉模块bug导致全屋对话瘫痪
  - 内存~400MB，部署复杂
- **改造成本**：极高
- **风险**：高

### 方案B：以 memory-agent 为核心

- **优点**：ma 已有 MCP/ACP/ChromaDB/insights，基础设施完善
- **缺点**：
  - ma 天生没有对话引擎、多角色、触发器编排、手机app同步
  - 感知层硬做中枢，职责错位
  - 需要给 ma 重写整个 butler 的对话层
- **改造成本**：极高
- **风险**：高

### 方案C：另起新中枢项目

- **优点**：最干净，从零设计，可吸取经验
- **缺点**：
  - 从零开始，预计3-6个月
  - 期间三个项目并行维护
  - 现有功能全部要迁移，有功能断裂期
- **改造成本**：最高
- **风险**：极高

### 方案D（推荐）：butler 为中枢 + ma 为感知层 + 执行层纯执行

- **优点**：
  - butler 已是事实上的中枢，改造成本低
  - 故障隔离：ma 挂了不影响对话
  - 资源隔离：视觉CPU不挤占对话
  - 职责清晰：中枢vs感知vs执行
  - 扩展性好：能力层可独立扩展
- **缺点**：
  - 需维护两个项目（butler + ma）
  - 需建立统一LLM网关和通讯协议
- **改造成本**：低
- **风险**：低

## 四、推荐架构：中枢集中 Agent，能力层保留 LLM 开关

### 4.1 核心理念

**不强制剥离 LLM，而是提供开关。** 每个能力层项目内置 `LLM_ENABLED` 开关：

- **开关关闭（默认）**：不调用本地 LLM，通过统一通讯协议向中枢请求 LLM 服务
- **开关打开**：保留独立 LLM 调用能力，用于离线/降级/特殊场景

这样既实现了"中枢集中调度"，又保留了各项目的独立性和降级能力。

### 4.2 架构分层

```
┌─────────────────────────────────────────────────────────┐
│                    👑 中枢层：doubao-butler                │
│  对话LLM · 决策Agent · 技能Agent · 多角色 · 触发器编排      │
│  MCP Server · ACP Server · 手机app同步 · 统一LLM网关       │
│  事件总线 · 能力注册 · 记忆关联                            │
└──────────────────────┬──────────────────────────────────┘
                       │ HTTP / ACP / MCP / 事件总线
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
┌──────────────┐ ┌──────────────┐ ┌──────────────┐
│  👁 感知层     │ │  ⚡ 执行层     │ │  🖥 设备端     │
│ memory-agent │ │ autoflow     │ │ zap-tv       │
│ 视觉LLM(开关) │ │ 纯执行无LLM   │ │ 纯执行无LLM   │
│ 人脸识别      │ │ HA设备控制    │ │ DeskPilot    │
│ 向量记忆      │ │              │ │ 电脑操作      │
│ 在场检测      │ │              │ │              │
└──────────────┘ └──────────────┘ └──────────────┘
```

### 4.3 各项目角色定义

| 项目 | 角色 | LLM开关 | 核心职责 | 禁止做的事 |
|------|------|---------|---------|-----------|
| **doubao-butler** | 中枢Agent | 始终开启 | 对话、决策、编排、技能、用户交互、统一LLM网关 | 不直接做视觉识别、不直接做设备ADB |
| **memory-agent** | 感知Agent | 默认关闭（可开启） | 视觉、人脸识别、在场、向量记忆、图片分析 | 不做对话、不做编排、不做决策 |
| **autoflow** | 执行Agent | 关闭 | 被butler调用执行复杂自动化流程 | 不做独立编排、不做对话 |
| **zap-tv** | 设备端Agent | 关闭 | 电视ADB控制、换台、点播 | 不做对话、不做编排 |
| **DeskPilot** | 设备端Agent | 可开启（本地推理） | 电脑操作、桌面监控、文档处理 | 不做全屋决策 |
| **TV_CAM** | 合并到ma | - | 电视端摄像头数据采集 | 不独立存在 |

### 4.4 memory-agent 的 LLM 开关策略

ma 的功能分为两类：

| 功能 | 是否需要LLM | 开关关闭时 | 开关开启时 |
|------|------------|-----------|-----------|
| 人脸识别（是谁） | ❌ 不需要 | ArcFace 纯算法，正常工作 | 正常工作 |
| 在场检测 | ❌ 不需要 | 正常工作 | 正常工作 |
| 图片描述（看到了什么） | ✅ 需要 | 通过中枢网关调用LLM | 本地调用LLM |
| 场景理解（在做什么） | ✅ 需要 | 通过中枢网关调用LLM | 本地调用LLM |
| 食物热量分析 | ✅ 需要 | 通过中枢网关调用LLM | 本地调用LLM |
| 作息洞察/规律总结 | ✅ 需要 | 移到 butler 决策层 | 本地调用（不推荐） |
| 信号学习/习惯发现 | ✅ 需要 | 移到 butler 决策层 | 本地调用（不推荐） |

**默认开关关闭**：ma 的视觉 LLM 调用通过 butler 统一网关代理，所有调用经过 butler 记录，形成统一记忆链路。

## 五、统一通讯协议

### 5.1 三层通讯方式

| 场景 | 协议 | 方向 |
|------|------|------|
| 能力注册/发现 | ACP（Agent Communication Protocol） | 能力层 → 中枢 |
| 工具调用/技能调用 | MCP（Model Context Protocol） | 中枢 → 能力层 |
| 事件通知/状态同步 | 事件总线（MQTT） | 双向 |
| LLM 代理调用 | HTTP REST | 能力层 → 中枢 |

### 5.2 统一 LLM 网关 API

中枢提供统一 LLM 代理接口，能力层项目通过此接口调用 LLM：

```
POST /api/llm/chat
Headers: X-Service-Name: memory-agent
Body: {
  "messages": [...],
  "model": "butler-chat",
  "purpose": "vision_analysis",  // 调用目的，用于记忆分类
  "context": {"skill_id": "...", "room": "..."}  // 上下文
}
Response: {
  "content": "...",
  "usage": {"prompt_tokens": 100, "completion_tokens": 50},
  "memory_id": "..."  // 中枢记录的记忆ID
}
```

**关键设计**：
- 所有 LLM 调用经过中枢，自动记录到统一记忆
- 按 `purpose` 分类记忆（对话/视觉/决策/技能）
- 按 `context` 关联记忆（哪个技能、哪个房间、哪个成员）
- 统一限流和配额管理，避免项目间互抢

### 5.3 能力注册协议

每个能力层项目启动时向中枢注册自己的能力：

```
POST /api/capabilities/register
Body: {
  "service": "memory-agent",
  "version": "1.0",
  "capabilities": [
    {"name": "face_recognize", "type": "perception", "llm_required": false},
    {"name": "image_analyze", "type": "perception", "llm_required": true},
    {"name": "presence_detect", "type": "perception", "llm_required": false}
  ],
  "llm_enabled": false,  // LLM开关状态
  "endpoints": {"mcp": "http://ma:8000/mcp", "http": "http://ma:8000"}
}
```

中枢动态发现可用能力，Agent 调用时自动路由到对应服务。

## 六、实施路径（三步走）

### 第一步：建立统一 LLM 网关（1-2周）

- butler 增加 `/api/llm/chat` 代理接口
- butler 增加能力注册 `/api/capabilities/register`
- ma 增加 `LLM_ENABLED` 开关（默认关闭）
- ma 的视觉 LLM 调用改为通过中枢网关代理
- 所有 LLM 调用自动记录到中枢记忆

**验收标准**：ma 的图片分析调用经过 butler 网关，butler 日志可看到调用记录，记忆可查询。

### 第二步：ma 决策类 LLM 迁移到 butler（2-3周）

- ma 的作息洞察、信号学习、习惯发现逻辑迁移到 butler 决策层
- ma 只保留感知类 LLM（图片描述、场景理解、食物分析）
- ma 的 MCP/ACP Server 降级为 Client，butler 成为唯一 Server
- TV_CAM 视觉能力合并到 ma

**验收标准**：ma 不再独立做决策，所有洞察/习惯由 butler 决策层产出。

### 第三步：执行层纯执行化（1周）

- autoflow/zap-tv/DeskPilot 确认无独立 LLM/Agent
- 执行层只接受 butler 指令，不做独立判断
- 建立事件总线，统一状态同步

**验收标准**：执行层项目无独立 LLM 调用，所有智能决策来自 butler。

## 七、Token 消耗分析

### 建立中枢后能省 token 吗？

**能省，但主要不是靠"集中调用"，而是靠以下机制：**

| 省token机制 | 原理 | 预计节省 |
|-----------|------|---------|
| **统一限流调度** | 避免 butler 和 ma 互抢配额导致重试（重试=重复消耗token） | 15-20% |
| **记忆关联去重** | 同一场景的视觉分析和对话共享上下文，避免重复描述 | 10-15% |
| **决策类LLM迁移** | ma 的作息洞察/信号学习移到 butler，复用 butler 已有上下文 | 10-15% |
| **消除重复建设** | 两套 skills/insights 合并为一套，避免重复的 system prompt | 5-10% |
| **模型路由优化** | 中枢根据任务复杂度自动选择模型（简单任务用flash，复杂用强模型） | 10-20% |

**合计预计节省：30-50% 的 token 消耗。**

**但有一个反效果**：统一网关会增加少量的系统提示词开销（记录调用目的、上下文关联），约增加 2-5%。净节省仍然显著。

### 关键洞察

省 token 的核心不是"把 LLM 放在一个容器里"，而是：
1. **统一调度**：避免重试和配额冲突
2. **上下文共享**：视觉分析结果直接注入对话，不需要重新描述
3. **模型路由**：简单任务不用强模型
4. **记忆复用**：已分析过的场景不重复分析

## 八、风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 中枢单点故障 | 全屋智能瘫痪 | 能力层保留 LLM 开关，中枢故障时可降级为本地调用 |
| 网关延迟增加 | 视觉分析变慢 | 网关只做代理和记录，不做额外处理；ma 可开启本地LLM降级 |
| 迁移期间功能断裂 | 用户体验下降 | 灰度迁移，先网关代理，再逻辑迁移，每步验证 |
| ma 代码量大迁移复杂 | 工期延长 | 只迁移决策类，感知类保留在 ma，降低迁移范围 |

---

## 九、总结

**推荐方案D优化版**：

1. **doubao-butler 为中枢**：集中所有 Agent/MCP/ACP/决策/编排，提供统一 LLM 网关
2. **memory-agent 为感知层**：保留视觉 LLM 开关（默认关闭，通过网关调用），只做感知不做决策
3. **执行层纯执行**：autoflow/zap-tv/DeskPilot 无独立 LLM，只接受中枢指令
4. **不强制剥离 LLM**：每个项目内置开关，可切换中枢调用/本地调用，保留降级能力
5. **预计节省 30-50% token**：主要靠统一调度、上下文共享、模型路由

**核心原则**：集中的是"调度和记忆"，不是"代码和容器"。通过统一网关和通讯协议实现逻辑集中，同时保留物理隔离和故障降级能力。
