## 0. 一句话结论

> **新建独立容器 `doubao-butler`（Docker Compose），只做「对话决策大脑」；
> 感知、记忆、事件总线、发声设备全部复用现有资产，不重复造轮子。**
> 记忆采用**分库策略**：语义记忆交 memory-agent，对话流水自建 SQLite。
> Node-RED 降级为「事件总线 + 设备适配层」，不做对话主体。

## 2. 四个候选方案评估

| 方案 | 评估 | 结论 |
|------|------|------|
| **A. Docker Compose 独立容器** | 有状态长生命周期服务（对话状态机、冷却计时、APScheduler）需要进程常驻；独立部署可单独重启、单独灰度，不影响 memory-agent/NR 稳定性；NAS 规范允许 | ✅ **推荐** |
| **B. Node-RED flow 实现** | NR 无原生对话状态机；`function` 节点堆到 311 个已难维护；对话上下文/冷却/多轮状态用 flow context 表达会迅速失控；NR 当前已 unhealthy | ❌ **不作为主体**，但**保留为事件总线 + 设备适配层** |
| **C. memory-agent 插件形式** | memory-agent **没有插件系统**（`skills.py` 只是提示词模板，不是扩展机制），需从零开发；且会污染"家庭行为记忆中枢"的单一职责，把对话状态塞进 331MB 的家庭事实库不合理 | ❌ **不为它开发插件系统**；改为**深度复用其现有 API** |
| **D. 自建数据库 vs 用 memory-agent 库** | 见 §3，**分库**最优 | ✅ **混合策略** |

## 3. 推荐架构

### 3.1 分层与职责边界

```
┌─ 感知层（全部已有，零开发） ────────────────────────────────┐
│  TV Arcface 人脸  │  memory-agent VLM  │  HA 传感器  │  go2rtc │
└────────┬──────────────────┬─────────────────┬──────────────┘
         │ /api/scan/latest │ /api/vision/*   │ REST/WebSocket
         ▼                  ▼                 ▼
┌─ 事件总线层（已有 Node-RED） ───────────────────────────────┐
│  汇聚 / 去重 / 路由 → 统一 POST doubao-butler /api/event    │
└────────────────────────────┬───────────────────────────────┘
                             ▼
┌─ 大脑层（新建 doubao-butler，唯一需要开发的容器） ──────────┐
│  WakeupEngine（冷却/免打扰/场景判断）                       │
│  DialogManager（状态机 / 上下文 / 人格）                    │
│  MemorySystem（本地对话流水 + 远程语义记忆代理）            │
│  TTS 编排（edge-tts → 音频文件 → 分发）                     │
└──────┬───────────────────┬──────────────────┬──────────────┘
       ▼                   ▼                  ▼
┌─ 记忆层 ───────┐ ┌─ 表达层（已有） ────────────────────────┐
│ memory-agent   │ │ TV /api/tts/play │ 小爱(HA tts.speak) │
│ agent_memories │ │ Bark 18273       │                    │
│ + Chroma       │ └────────────────────────────────────────┘
└────────────────┘
```

### 3.2 只开发「对话决策」，其余全部复用

| 能力 | 归属 | 依据 |
|------|------|------|
| 谁在客厅 | TV Arcface（已有） | `/api/scan/latest`、`/api/scan` + callback |
| 客厅发生了什么 | memory-agent（已有） | `/api/vision/analyze`、`/api/behaviors` |
| 用户偏好 / 家庭事实 / 长期记忆 | **memory-agent agent_memory** | 已有完整的去重、矛盾检测、晋升、TTL、信任度 |
| 人格与称呼 | **doubao-butler 本地配置** | 可复用 `/api/members` 的档案，人格 prompt 属管家私有资产 |
| 对话流水 / 防重复 / 冷却状态 | **doubao-butler 本地 SQLite** | 见 §3.3 |
| LLM 生成 | doubao2api（已有） | `/v1/chat/completions` |
| TTS 合成 | **doubao-butler 内置 edge-tts** | 见 §4.2 |
| 事件汇聚 / 设备 IO | Node-RED（已有） | 小爱、HA、Bark 链路都在里面 |

### 3.3 数据归属决策（为什么分库）

| 数据 | 存哪 | 理由 |
|------|------|------|
| 对话历史（30 天滚动） | **本地 SQLite** | 高频短周期写入；塞进 331MB 的家庭事实库不合理 |
| 防重复指纹（7 天） | **本地 SQLite** | 需要毫秒级同步查询，不能走网络 |
| 冷却 / 状态机 / 会话 | **本地 SQLite + 内存** | 强一致，重启可恢复 |
| 用户偏好 / 重要事件 / 沉淀事实 | **memory-agent agent_memory** | 复用其向量检索、去重、晋升、TTL |
| 成员档案 | **memory-agent members**（只读同步） | 避免两处维护 |

**关键约束提醒**：memory-agent 的 `add_semantic_memory` **强制要求 `source_refs`**（必须是 `event:` / `insight:` / `activity:` 前缀，防幻觉设计）。
⇒ 闲聊沉淀的"Kevin 周日有篮球课"这类事实，需溯源到一条 behavior event 或 insight；
**纯对话流水不要往里塞**，否则会触发 422。这正是分库的硬性理由。

### 3.4 防重复：不引入向量库

doubao-butler **不装 ChromaDB、不跑 embedding 模型**，改用：
- 本地 SQLite 存 `bigram 集合`
- 查重 = Jaccard 相似度，7 天内同成员 > 0.6 判重复
- 纯 Python、毫秒级、零依赖

语义级去重的活儿交给 memory-agent 的 `conflict_scan`（写回时自动做）。
⇒ 容器依赖极轻：`fastapi / uvicorn / httpx / apscheduler / edge-tts / pydantic-settings`，内存占用 < 150MB，几乎不 churn。

```yaml

      - LLM_API_KEY=<redacted>
      - HA_URL=http://192.168.2.200:8123
      - HA_TOKEN=<ha_token>
      - NR_WEBHOOK=http://192.168.2.200:1880/butler/event
      - BARK_URL=http://192.168.2.200:18273
      - TTS_PROVIDER=edge-tts
      - TTS_VOICE=zh-CN-XiaoxiaoNeural
      - PUBLIC_BASE=http://192.168.2.200:8095
      - TZ=Asia/Shanghai
    # 规范 §2.7：容器崩溃 churn 是 NAS 死机的直接触发路径，必须严防
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8000/api/health"]
      interval: 60s
      timeout: 5s
      retries: 3
      start_period: 30s
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"
```

**稳定性硬要求（来自规范 §0 的血泪教训）**：
- 全局异常捕获，**绝不让进程崩**（崩溃→重建的 veth/挂载 churn 会触发飞牛 trim 模块死锁 → 整机冻结）
- 所有外部调用（LLM/TTS/HA/memory-agent）必须设超时 + try/except
- 健康检查端点不得因下游不可用而失败

## 7. 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| **容器崩溃触发 NAS 死机** | 整机冻结 3.5h（已发生 2 次） | 全局异常捕获 + healthcheck + 日志持久化 + 看门狗自动断电重启 |
| doubao2api 会话失效 | LLM 不可用 | 降级到 memory-agent `/api/llm/ask`（已有缓存与确定性路径） |
| memory-agent 视觉未启用 | 场景上下文缺失 | 退化为 TV 人脸 + HA 传感器，不影响主线 |
| TV 端离线/息屏 | 播放失败 | `/api/scan` 返回 503 时降级：小爱 → Bark |
| edge-tts 需联网 | 断网时无语音 | 预生成高频话术音频缓存；核心提醒降级为 Bark 文字 |
| 主动对话打扰家人 | 体验反感 | 冷却 10min + 免打扰时段 + 电视播放中不打断 + 每成员可调频 |
