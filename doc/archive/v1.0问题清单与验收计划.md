## 二、待修复问题（v1.0 攻坚）

### P0 — 阻断核心体验

#### P0-1 小爱音箱打断（全屋）
- **现象**：对任意小爱说"贾维斯/豆包管家 + 问题"，小爱先用内置 TTS 播报自己的回复，butler 回复在小爱播完后才出来（或中途出来但叠音）。
- **根因**：小爱内置 TTS 优先级极高，`notify.send_message`（文本指令）和 `media_player.media_stop` 均被排队；唯一有效通道是 `player_play_music`（音乐模式，REPLACE_ALL）。
- **修复**：统一打断方案——所有音箱均用 player_play_music 播"叮"提示音抢占通道（不再区分 X08A/其他）；去掉 dialog.py 里 X08A 专用的 pre-ding（ear 已播过叮）。
- **验收标准**：对任意房间小爱说唤醒词+问题，小爱播报不超过 2 秒即被打断，随后 butler 回复清晰播出。
- **状态**：🔧 已部署，待用户现场验收

#### P0-2 单音箱回复（哪个音箱问哪个音箱答）
- **现象**：在客厅左小爱说"豆包管家今天天气怎么样"，客厅左和客厅右两个小爱同时播报 butler 回复。
- **根因**：butler 角色的 output_devices 包含多个设备，dialog.speak_as_role 按房间过滤但可能匹配到多个同房间设备。
- **修复**：xiaomi_ear 触发时把触发设备 ID（source_device）传给 on_wakeup，speak_as_role 优先用触发设备，不用 output_devices 全量广播。
- **验收标准**：在 A 音箱唤醒，仅 A 音箱播报 butler 回复；同房间多设备时仅触发设备回复。
- **状态**：🔧 已部署，待用户现场验收

#### P0-3 LLM 回复质量（胡编乱造+时间错误）
- **现象**：butler 回复内容胡编乱造，下午 14 点还说是"早上"。
- **根因**：①agnes-2.5-flash 是推理模型，max_tokens=800 不够（思考占满后答案为空）；②system prompt 里没有注入当前时间；③temperature=0.6 对推理模型偏高。
- **修复**：①max_tokens 800→2000；②temperature 0.6→0.3；③system prompt 注入当前日期时间；④system prompt 要求"直接回答不要思考过程"。
- **自动化验收**：✅ 8/8 时间感知正确，0 次空回复。
- **状态**：✅ 已修复（自动化验收通过）

#### P0-4 LLM 调用不稳定（"卡住了"）
- **现象**：经常回复"嗯，我刚才有点卡住了，能再说一遍吗？"
- **根因**：①agnes 推理模型 max_tokens=800 不够导致空回复；②chat_with_tools 无重试机制。
- **修复**：①max_tokens 800→2000；②agent.run 加 1 次重试（失败后等 1 秒重试）；③空 content 时打 warning 日志。
- **自动化验收**：✅ 8/8 连续调用成功，0 次"卡住了"。
- **状态**：✅ 已修复（自动化验收通过）

### P1 — 影响体验但不阻断

#### P1-1 memory-agent 工具调用超时
- **现象**：ask_memory 失败时空转 20 秒，导致 butler 回复延迟巨大。
- **根因**：tools.py 里 ask_memory 没有超时限制。
- **修复方向**：所有 tool 调用加 5 秒超时，失败降级。

#### P1-2 角色路由准确性
- **现象**：在书房说"豆包管家"可能路由到贾维斯，或在客厅说"贾维斯"路由到 butler。
- **根因**：match_role_by_text 按唤醒词匹配，但私人助理的 scope_private 校验可能有边界问题。
- **验收标准**：每个角色的唤醒词在正确房间正确路由，越界拒绝并提示。

#### P1-3 X08A 提示音格式
- **现象**：player_play_music 播短 mp3 时 X08A 报"播放服务遇到问题"。
- **根因**：X08A 对 mp3 采样率/比特率敏感，44100Hz 不支持，24kHz 需验证。
- **修复方向**：用 edge-tts 合成的有效 mp3 作为提示音，或用更长的音频文件。

#### P1-4 回声抑制
- **现象**：butler 在小爱播报的内容可能被对话传感器再次识别，触发二次唤醒。
- **当前状态**：dialog.py 有 suppress_echo，但窗口可能不够。
- **验收标准**：butler 播报不会触发自我唤醒。

### P2 — 优化项

#### P2-1 唤醒响应速度
- **目标**：从用户说完到 butler 开始播报 < 3 秒。
- **当前**：LLM 1-2s + TTS 1-2s + 打断 0.5s ≈ 3-5s。
- **优化**：①LLM streaming 首字输出；②TTS 预合成常用回复；③打断与 LLM 并行。

#### P2-2 全屋耳朵覆盖
- **当前**：8 个 conversation 传感器已订阅。
- **待确认**：主卧室浴室/卫生间的小爱是否需要耳朵（可能误触发）。

#### P2-3 角色对话持久化
- **当前**：role_state.json 存 conversation_id，但多轮上下文在内存里（重启丢失）。
- **优化**：上下文持久化到数据库。

## 五、关键技术决策记录

1. **打断方案**：小爱音箱内置 TTS 无法被 notify/media_stop 打断，唯一有效通道是 player_play_music（音乐模式）。全屋统一用此方案，X08A 需特殊音频格式。
2. **单音箱回复**：触发设备 ID 必须贯穿 on_wakeup → speak_as_role，不能用 output_devices 全量广播。
3. **LLM 模型**：agnes-2.5-flash 免费但能力有限，需评估是否换回 deepseek-v4-flash。
4. **时间感知**：system prompt 必须注入当前日期时间（Asia/Shanghai），不能依赖模型自身知识。
5. **工具超时**：所有 tool 调用必须有超时，失败降级为纯对话，不能阻塞主流程。
