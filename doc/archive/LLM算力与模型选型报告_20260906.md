# 豆包管家 LLM 算力与模型选型报告

> 生成时间：2026-09-06 | 基于 v0.9 部署后真实运行数据 + 代码静态分析

## 一、当前 LLM 调用架构

豆包管家使用**双后端**，职责分离：

```
┌─────────────────────────────────────────────────────────┐
│                    豆包管家容器 (:8095)                    │
│                                                          │
│  推理/工具循环层          对话展示/多模态层                │
│  ┌──────────────┐        ┌──────────────────┐           │
│  │ new-api      │        │ doubao2api (:9090)│           │
│  │ deepseek-v4  │        │ 豆包网页端逆向     │           │
│  │ -flash       │        │ - 文本对话         │           │
│  │ (原生 FC)     │        │ - 视觉多模态       │           │
│  └──────┬───────┘        │ - 图片/音乐生成    │           │
│         │                └────────┬─────────┘           │
│         │                         │                     │
│  调用点：                     调用点：                    │
│  - 对话唤醒 agent.run        - notifier.push            │
│  - 决策心跳 decision.tick    - camera_vlm 视觉分析       │
│  - trigger LLM 动作          - food-calorie 食物热量     │
│  - 技能引擎推理              - face_greet 人脸分析        │
└─────────────────────────────────────────────────────────┘
```

**关键事实**：
- new-api（3001）走 deepseek-v4-flash，承担**推理+工具调用**，是核心算力依赖
- doubao2api（9090）走豆包网页端逆向，承担**视觉多模态+对话展示**，免费但稳定性依赖逆向
- 两者均为 OpenAI 兼容接口，`butler/integrations/llm.py` 和 `butler/integrations/doubao.py` 分别封装

## 三、并发与算力需求

### 3.1 峰值并发估算

按家庭场景最坏情况（周末晚上全家活跃）：

```
决策心跳      : 1 并发（每10分钟一次，串行）
耳朵对话      : 3 并发（3个房间同时唤醒）
视觉分析      : 2 并发（2个摄像头同时分析）
主动推送      : 1 并发（决策结果推送）
─────────────────────────────────────
new-api 峰值  : ≈ 4-5 并发
doubao2api 峰值: ≈ 3-4 并发
```

### 3.2 Token 量估算

| 场景 | 输入 token | 输出 token | 日均次数 | 日均 token |
|------|-----------|-----------|---------|-----------|
| 决策心跳 | 800-1500（摘要+system） | 100-300 | 144 | 13万-26万 |
| 对话唤醒 | 500-2000（含历史12轮） | 100-500 | 100 | 6万-25万 |
| 视觉分析 | 1500-3000（含图片base64≈1000） | 200-800 | 50 | 8万-19万 |
| **合计** | | | | **≈ 30万-70万 token/天** |

### 3.3 算力需求结论

| 指标 | 最低需求 | 推荐配置 |
|------|---------|---------|
| new-api QPS | 2 | **5** |
| new-api 并发连接 | 3 | **8** |
| 日均 token | 30万 | **70万（留 2x 余量）** |
| doubao2api QPS | 1 | **3** |
| 单次请求超时 | 30s | 60s（视觉） |

**NAS 容器资源**：butler 容器本身不跑模型，只是 API 客户端，CPU/内存需求极低（<100m CPU，<200MB 内存）。算力全部在外部 API 服务。

## 四、模型选型建议

### 4.1 是否维持 deepseek-v4-flash？

**结论：决策层维持 flash，对话层升级。**

| 场景 | 当前模型 | 建议模型 | 理由 |
|------|---------|---------|------|
| 决策心跳推理 | deepseek-v4-flash | **deepseek-v4-flash**（维持） | 轻量分类/行动选择，flash 足够；关键是配额不是模型能力 |
| 耳朵对话 | deepseek-v4-flash | **deepseek-v4**（非flash）或 doubao-pro | 多轮对话需要更强语义理解和长上下文 |
| 工具调用（function calling） | deepseek-v4-flash | **deepseek-v4** | flash 的 FC 可靠性低于标准版 |
| 视觉多模态 | doubao2api（豆包网页端） | **维持 doubao2api** | 豆包多模态能力强且免费，暂无更优替代 |
| 食物热量 | doubao2api | **维持 doubao2api** | 同上 |

**关键判断**：当前 429 不是模型能力问题，是 **new-api 上 deepseek-v4-flash 的渠道配额/限流**问题。换模型不解决根本，需要：
1. 在 new-api 上为豆包管家配置**专属渠道/专属模型名**，独立配额
2. 或升级到 deepseek-v4（配额可能更充裕）
3. 加客户端退避重试（当前 429 直接失败，无重试）

### 4.2 new-api 专属模型配置建议

在 new-api（192.168.2.200:3001）上为豆包管家创建**专属模型映射**：

```
模型名: doubao-butler-chat
映射到: deepseek-v4（或 deepseek-v4-flash，取决于配额）
渠道: 独立渠道（不与其他项目共享配额）
限速: 5 QPS / 8 并发
上下文: 8K（对话）/ 4K（决策）
```

**配置步骤**（new-api WebUI）：
1. 渠道 → 添加渠道 → 选择 deepseek 上游 → 填入 API Key
2. 模型 → 添加模型 → 模型名 `doubao-butler-chat` → 绑定上述渠道
3. 令牌 → 创建专属令牌 → 绑定模型 `doubao-butler-chat` → 设置限速 5 QPS
4. butler 容器环境变量 `NEW_API_MODEL=doubao-butler-chat`，`NEW_API_KEY=<专属令牌>`

**好处**：
- 与其他项目（memory-agent、doubao2api 等）隔离配额，互不影响
- 可独立监控调用量和配额
- 后续可平滑切换上游（deepseek → 通义 → 豆包官方）而不改 butler 代码

### 4.3 客户端加固建议

当前 `llm.py` 的 `_raw` 方法遇到 429 直接抛异常，无重试。建议：

```python
# 建议增加：指数退避重试（429/5xx 重试 3 次，间隔 2s/4s/8s）
# 建议增加：降级后端——new-api 失败时自动降级到 doubao2api 文本对话
```

这是小修改，可在 butler 内完成，不需要交接单。

## 五、doubao2api 侧注意事项

doubao2api 是逆向服务，**无 SLA 保障**：
- 视觉多模态当前稳定，但豆包网页端接口变更可能随时失效
- keep_conversation（持久对话线程）可靠性待验证（见"角色对话收敛"问题）
- 建议：视觉分析结果缓存到 butler 本地，避免重复调用；关键路径（决策心跳）不依赖 doubao2api
