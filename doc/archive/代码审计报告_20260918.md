#### [P0-12] ✅ 技能创建确认分支先于取消分支，且肯定表含多字动词 → 否定句被当成确认

- **位置**：`butler/core/dialog.py:265-276`（NAS 与本地 md5 相同 `8d8371eb…`，**线上生效**）
- **证据**：
  ```python
  :265  if any(w in text_lower for w in ["确认","好的","可以","没问题","创建","生效","启用"]):
  :266      result = creator.confirm(role_id)          # 先判肯定
  :273  if any(w in text_lower for w in ["取消","不要","算了","放弃","不用"]):
  :274      result = creator.cancel(role_id)           # 后判否定
  ```
  肯定表里是**多字动词**（创建/生效/启用）而非单字，所以它不会犯 AutoForge 那种「要」⊂「不要」的错；但两个分支是**独立的 `if`（不是 `if/elif`）**，且肯定分支先 return，于是「否定词 + 被问动词」共现时判反：
  - 「不要创建」含「创建」→ `creator.confirm()` → **技能被创建并生效**（静态推演，未运行）
  - 「不可以」含「可以」→ 同上
  - 「先别启用」含「启用」→ 同上
  反之「不要」「取消」「不用了」在三字表下判对——**所以 butler 与 AutoForge 的爆炸半径不重叠，两家的正确用例互不通用。**
- **第三个问题**：`:278-280` 把「两句都不命中」当成修改意图，直接 `creator.cancel()` 销毁草稿。一句听不清的话会丢掉用户刚生成的草稿，且无任何提示。
- **影响面**：这是「技能草稿转正」的闸门，不是直接 HA 写操作；但转正后的技能会在后续事件里执行，属于**把用户的拒绝编译成一条常驻自动化**。
- **修复方向**：删掉这两张内联表，改用 `homesdk.consent`（不变式：子串只否决、不放行；`unknown` 既不建也不删，保持 pending 并重问）。**本仓已就此开工单：`E:\NAS\AgentOps\workorders\doubao-butler\WO-BUT-001-homesdk-consent-adopt.md`**（含 `llm_decide/ask.py:170-190` 那条 LLM 判定门的前置化要求，以及「动手前先给本仓一张 git 回滚网」的前置项——本仓目前不是 git 仓库）。
- **同源项**：AutoForge `af_executor.py:53-66` 是同一族缺陷的另一形态，见 `02-审计-AutoForge.md` P0-1 与 `WO-AF-001`。

## 一、P0：启动即崩与整条功能链失效

### [P0-1] ✅ TTS 模块导入即 `ModuleNotFoundError`，拖垮整个应用启动

- **位置**：`butler/tts/manager.py:18`；触发点 `butler/app.py:85`
- **证据**：`from butler.tts.nowvoice_tts import NowVoiceTTS`，但 `butler/tts/` 目录实际只有 `__init__.py / base.py / edge_tts.py / edge_tts_patch.py / kokoro.py / manager.py`，**不存在** `nowvoice_tts.py`。该 import 在模块顶层、无条件执行，`app.py:85` 又无条件构造 runtime 的 tts manager。
- **失败场景**：任何一次进程启动（含 Docker 重启、systemd 拉起、`uvicorn butler.app:app`）都在 import 阶段抛异常退出。也就是说除非法外加载，**整个管家当前起不来**，而 `doc/NowVoice_TTS_API.md` 说明这是一次「换引擎没换引用」的半途重构。
- **修复方向**：① 立即把该 import 改回现存引擎或补齐模块；② 引擎选择走配置 + 注册表（`{"edge": EdgeTTS, "kokoro": Kokoro}`），未知 key 直接 fail-fast 并打印可用值；③ 加一条 `python -c "import butler.app"` 的启动冒烟检查（见 §八 无 CI）。

### [P0-2] ✅ `tts.speak()` 方法不存在，四处调用点被 `except` 吞掉 → 主动播报永远沉默

- **位置**：定义侧 `butler/tts/manager.py:63`（只暴露 `synthesize()`）；调用侧 `butler/proactive/engine.py:178`、`butler/morning/routine.py:207`、`butler/timeseries/anomaly.py:371`、`butler/af_bridge.py:121`
- **证据**：四处均为 `await self.rt.tts.speak(...)`，且都包在 `except Exception: logger.warning(...)` 里。
- **失败场景**：晨报、主动提醒、异常告警、AF 询问转播报——所有「设备响起来」的路径永远不响，日志里只留一行 warning。这是 P0-1 的同类病：**接口重命名后调用方未同步，而异常处理策略把契约违反降级为噪音**。
- **修复方向**：在 manager 上补 `async def speak(text, device=None)`（`synthesize` + 推送到指定 entity），或统一改调用方；同时把这类 `AttributeError` 从 `except Exception` 里排除（`except (httpx.HTTPError, asyncio.TimeoutError)`），让编程错误可见。

### [P0-3] `vibe_routes` 引用不存在的模块 → 相关 API 全 404

- **位置**：`butler/app.py:37`、`butler/app.py:192`
- **证据**：`from butler.api import vibe_routes` / `include_router(vibe_routes.router)`，`butler/api/` 下无该文件。
- **失败场景**：与 P0-1 同因（半途重构）。若被 try/except 包住则静默丢路由，前端对应页面永久 404。
- **修复方向**：补文件或删引用；路由注册改为「显式列表 + 启动时逐个 import 断言」。

### [P0-4] `fact_set_role` 缺 `get_conn` 局部导入 → 该端点 100% 返回 500

- **位置**：`butler/api/memory_routes.py:310`；对照同文件 `:71/:174/:195` 都有 `from butler.store.db import get_conn`
- **证据**：函数体内直接 `c = get_conn()`，模块级无该名字。
- **失败场景**：任何写角色事实的请求固定 500，且因为别的端点正常，容易被误判为「数据库坏了」。
- **修复方向**：把 `get_conn` 提到模块级 import（该文件其它三处也在做局部导入，说明是复制粘贴惯例，建议一并收敛）。

### [P0-5] `init_from_store()` 早于 `rt.scheduler` 赋值 → 重启后定时任务不恢复

- **位置**：`butler/app.py:318-320`（调用）vs `butler/app.py:662`（`rt.scheduler = ...`）
- **证据**：恢复逻辑内部依赖 `rt.scheduler`，属性在其之后才建立。
- **失败场景**：容器重启 = cron/定时触发全部丢失，直到下一次手工创建任务。用户侧表现为「提醒莫名其妙不响了」。
- **修复方向**：调整顺序，或让 `init_from_store` 返回待注册列表由 app 在 scheduler 建好后统一注册。

### [P0-6] 推送过载锁死后无法解锁：TTS 队列没有任何消费者

- **位置**：`butler/guard/push_guard.py:242-340`
- **证据**：实现了 `tts_pop()`，全仓无调用者；队列满 10 条即进入 overload 判定。
- **失败场景**：通知高峰期（早晨多源并发）把 guard 打入过载态，之后所有推送被判定「已限流」而丢弃，且因不消费故永不恢复，**只能重启进程**。
- **修复方向**：要么补消费者，要么删掉这条死路径（保留一半的限流器比没有更危险）。

### [P0-7] 模式闸门 `can_tts/can_bark/can_run_skill` 定义了但无人调用

- **位置**：`butler/modes/engine.py:243-275`
- **证据**：全仓无调用点。
- **影响**：夜间/会议/静音模式的「能不能发声、能不能跑技能」形同虚设——静默模式仍会响，睡眠模式仍会执行技能。这是安全/体验类设计缺陷：用户以为存在约束，实际不存在。
- **修复方向**：在所有输出与执行入口接上闸门（与 P0-2 一起改，避免再次漏）。

## 二、P0：鉴权绕过与会话/凭据暴露

### [P0-8] 会话密钥默认随机 + 会话表仅存内存 → 重启全员掉线，多进程互不认账；主口令可直接当 Bearer 用 ✅（逻辑逐行确认）

- **位置**：`butler/api/deps.py:14`、`:41-48`
- **证据**：
  - `_SESSION_SECRET = os.environ.get("BUTLER_SESSION_SECRET") or secrets.token_hex(16)`：未配环境变量时每次启动换密钥。
  - `_active_sessions: set[str]` 为进程内集合：无持久化、无过期回收（只增不减），且 `uvicorn --workers>1` 时各 worker 互不可见。
  - `if tok and tok == get_settings().web_password: return True`：**主密码本身就是长效 Bearer**，无需登录流程，也不参与任何限流/审计。
- **失败场景**：① 重启后旧 token 全部失效但 `web_password` 仍有效，用户被训练成「用主密码当 token」；② `_active_sessions` 单调增长是内存泄漏；③ 前端硬编码 `"Authorization": "Bearer <redacted>"`（`butler/static/js/app.js:129,147,157`、`pages/commands.js`、`pages/skills.js`），意味着**只要 `web_password` 为空或被设为 `"admin"` 即完全无鉴权**，且任意访问者都能从 JS 源码里读到这个凭据字面量。
- **修复方向**：会话落库（含 `expires_at`）、密钥缺失时 fail-fast 而非随机生成、禁止「主口令 == 有效 token」这条捷径（口令只用于换取短时效 session token）、前端不再自带凭据、补 `/api/auth/logout`（当前**无登出端点**，凭据一旦泄露只能改全局口令）。

### [P0-9] 无鉴权 webhook 可驱动设备、调用 Agent、并落盘同源 HTML（存储型 XSS）

- **位置**：`butler/api/doubao_webhook.py:765-779`（`_webhook_handler` / `routes()`），及其下游 `execute_device_command`、`rt.dialog.agent.run`、`save_user_page`
- **证据**：该组路由不在 `guard()` 覆盖范围内（与其余 per-route `guard()` 手写作法不一致，本身就是漏 guard 的结构性原因）；`【调用LLM：…】` 指令直接把外部输入喂进 Agent；`save_user_page` 仅在内容含 `<head>` 时注入 CSP，`static/user_pages/` 与主站同源。
- **失败场景**：能访问该端口的任意主体可：让管家执行设备指令（开锁/开阀级别）、以管家身份驱动 LLM 工具链、在同源目录落一段可执行 HTML → 拿到管理员浏览器会话。
- **修复方向**：webhook 纳入统一鉴权（独立签名 + 时间戳 + 重放缓存）；`save_user_page` 一律加 CSP `sandbox`、改为 `Content-Disposition` + 独立子域，或干脆只渲染纯文本/markdown；`【调用LLM：…】` 协议需白名单化指令来源。

### [P0-10] ✅ MA 对接令牌以字面量硬编码，绕开已有配置项

- **位置**：`butler/core/agent.py:99`（另 `butler/core/tools.py:1017` 重复一份）；配置侧 `butler/config.py:131 memory_agent_butler_token`、`:223` 从 `MEMORY_AGENT_BUTLER_TOKEN` 读取
- **证据**：`MA_TOKEN = "<32+ 位字面量>"`（本报告不复述其值），随后请求 `http://192.168.2.200:8086/api/vision/presence?...`。配置项存在且已接通环境变量，但代码不走它。
- **失败场景**：① 凭据进入源码/镜像层/Docker 构建上下文（无 `.dockerignore`，见 §八），任何能读仓库的人即持有 MA 有效令牌；② 轮换令牌需改代码重新部署，运维必然改不完；③ 值与 MA 侧 `BUTLER_TOKEN` 分叉后表现为「在场查询一直 401」，而异常被 `try/except` 吞掉（该处注释自己写了 `best-effort`），排查方向被误导。
- **修复方向**：改为 `get_settings().memory_agent_butler_token`，缺失时降级为「不在场」并明确记日志；**立即在 MA 侧吊销该硬编码令牌并换发**；URL 同样从配置来（`go2rtc_base_url`/MA base 已有先例）。

### [P0-11] 面匹配/口令类端点用字符串相等比较 Bearer

- **位置**：`butler/api/face_routes.py:26`、`butler/api/vision_routes.py:24-29`
- **证据**：`auth == f"Bearer {token}"`，非 `hmac.compare_digest`。
- **影响**：理论上存在时序侧信道；更现实的问题是「`Bearer ` 前缀大小写/多余空格即不等」造成脆弱鉴权，以及风格不统一（同仓 `deps.py` 又是另一套判定）。
- **修复方向**：抽 `require_bearer(token)` 工具函数，内部 `compare_digest`，全项目 router 统一使用。

## 三、P1：并发、事件循环阻塞与资源泄漏

### [P1-1] ✅ 单例可变状态跨请求串话：`last_trace_id` / `_last_user_text`

- **位置**：`butler/core/agent.py:38,76,119,125`；读取方 `butler/api/agent_routes.py:38`、`butler/core/tools.py:1059`
- **证据**：Agent 是单例，`last_trace_id`、`_last_user_text` 作为实例属性被每个请求覆写，另有模块读取它们做「别名学习」。
- **失败场景**：两个用户/两个前端会话并发时，A 的 trace 或文本被记到 B 头上；别名学习会把错误的「实体别名 ← 用户话术」对写入持久库（**别名污染**，之后所有解析都可能命中错设备）。
- **修复方向**：用 `contextvars` 或显式把 `trace_id`/`user_text` 作为参数传递；别名学习的输入必须来自同一请求的局部变量。

### [P1-2] ✅ 整轮重试会重放已执行过的工具副作用，并产生重复 trace 行

- **位置**：`butler/core/agent.py:190-210`；配合 `integrations/llm.py:148-168`
- **证据**：`for attempt in range(2)` 用**同一份 `messages`（已含 tool 结果）和同一个 `tracer`** 重新调用 `chat_with_tools(...)`。工具在上一 attempt 中已经真实执行过（HA 写、提醒创建）。
- **失败场景**：LLM 第二次调用超时/报错后重试 → 设备被二次操作；`tracer` 复用 → `agent_traces` 出现两行同 `trace_id`，而查询侧 `get_trace()` 用 `fetchone()`，前端只能看到其中任意一条，诊断时结论随机。
- **修复方向**：重试仅重试「尚未产生副作用的首次 LLM 请求」；或把 attempt 计数下沉到 llm 层并在 tracer 上记 `attempt`；trace 表加 `(trace_id, attempt)` 唯一键。
- **相关**：`integrations/llm.py:148-168` 的 `time_budget` 只在每轮迭代开始检查，单次 LLM 调用超时无上限 → 120s 预算实际可被拖成数分钟。

### [P1-3] 同步 IO 与阻塞调用散落在 async 路径上

- **位置（子审计汇总）**：`butler/core/tools.py:41`（`urllib.request.urlopen(timeout=25)` 于 async 工具内）、`butler/audiobook/manager.py:88-103,409-425`（`rglob` 全盘扫描在事件循环上）、`butler/core/event_stream.py:240-247`（循环内同步 `commit`）
- **失败场景**：一次 25s 的网络读或一次大目录遍历会**冻结整个事件循环**——所有聊天、所有 webhook、SSE 全停。管家是单进程 asyncio 服务，这是最常见的「卡住了」根因。
- **修复方向**：统一 `httpx.AsyncClient`（连接池 + 明确超时）；文件遍历走 `asyncio.to_thread` 或改为增量索引；DB 写走 `to_thread` 或 `aiosqlite`。
- **注意**：`app.py:504` 已存在正确范式 `run_coroutine_threadsafe(coro, _main_loop)`，说明作者知道该模式，问题是**没有一致执行**。

### [P1-4] 四处独立共享 SQLite 连接，无 `busy_timeout`、主键用 `COUNT+1`

- **位置**：`butler/core/decision_store.py:19-31,67-74`、`butler/notification_store.py:25`、`butler/pwa_chat_store.py:22`、`butler/user_location.py:32`
- **证据**：模式一致——模块级共享连接 + `COUNT(*)+1` 生成 id + 读-判-写非原子。
- **失败场景**：① `COUNT+1` 是典型 check-then-act，并发插入直接主键冲突或覆盖；② 无 `busy_timeout` 时并发写抛 `database is locked` 并被上层 `except Exception` 吞掉 → 决策/通知记录静默丢失；③ 读-判-写投票逻辑（读旧值判断后再写）在并发下产生丢失更新。
- **修复方向**：`INTEGER PRIMARY KEY` + `INSERT RETURNING`；连接层统一 `PRAGMA busy_timeout=5000; journal_mode=WAL; synchronous=NORMAL`；判断逻辑写进单条 SQL 或用 `BEGIN IMMEDIATE`。

### [P1-5] 每 15 分钟重建 `SecurityMonitor`，冷却状态归零

- **位置**：`butler/app.py:646-657`；`butler/core/security_monitor.py:20-24`（`self._last_alert`、`_alert_cooldown = 3600`）、`:90-96`
- **证据**：✅ 冷却表是实例属性，注释明确「1小时冷却」；但 monitor 每个周期用 `SecurityMonitor(rt)` 新建。
- **失败场景**：**冷却完全失效** → 门窗夜间未关、无人开空调这类告警每小时应报 1 次，实际每 15 分钟就报 1 次（4 倍噪音），Bark/推送侧被打爆，用户开始忽略告警（告警系统的经典失效模式）。
- **修复方向**：monitor 作为 runtime 单例，或把 `_last_alert` 落库/落 `rt`；实例复用即可修复。
- **附带逻辑错误**：✅ `:90-96` 判定「无人时空调在开」用 `"climate" in eid.lower() and evt["state"] == "on"`，而 HA 的 `climate.*` 状态是 `heat/cool/auto/off`，**几乎永不为 `"on"`** → 该规则实际从不告警（静默失效）；门窗侧 `"door" in eid` 会把 `sensor.doorbell`、`binary_sensor.front_door_sensor` 一并纳入（误报）。

### [P1-6] 无界增长与无保留策略

- **位置**：`butler/core/event_stream.py:240-247`（`home_events`、`agent_traces` 无 TTL/归档）、`butler/integrations/ha.py` 的 `_media_stop_tasks: dict = {}`（**类属性**，且重复定义 `def schedule_media_stop` 于 `:124` 与 `:395`，后者覆盖前者）
- **失败场景**：NAS 上长跑 SQLite 表无上限增长，最终拖慢所有查询；类属性 dict 被所有实例共享（虽然本仓单例，但测试/多实例时相互污染）；重复同名函数定义说明文件已失控，读代码者会以为 `:124` 生效。
- **修复方向**：事件表按天分表或定期裁剪；删重复定义；`_media_stop_tasks` 移到 `__init__`。

## 四、P1：契约失真——「返回字符串/返回 True」代替失败传播

这是本项目最根因化的一类设计缺陷：**失败被编码成正常返回值**，于是上层永远看不到失败。

### [P1-7] `HA.call_service` 把 HTTP 失败当成功结果返回字符串

- **位置**：`butler/integrations/ha.py:73-89`
- **证据**：`return "http 404: ..." / return "error: ..."` 而非抛异常。
- **失败场景**：调用方（含 LLM 工具层）无法用统一方式判定成败；错误串会被当成「工具输出文本」再喂给 LLM，LLM 于是对用户说「已经帮您打开了」——**假成功直达用户**。同时 `404` 说明 entity 已不存在，这类信息本该触发一次自愈（重扫描/提示重命名），现在被丢弃。
- **修复方向**：抛类型化异常（`HAEntityNotFound`/`HAUnauthorized`/`HATimeout`），在工具边界一次性转成人类可读文本；LLM 侧的 `observe_fn` 只接收结构化 `ok/err`。

### [P1-8] `schedule_media_stop` 重复定义 + 类属性任务表

见 P1-6，属于同一类「静默不生效」。

### [P1-9] 自进化写操作确认门槛与实际默认模式不匹配

- **位置**：`butler/self_evolution.py:42`（默认 mode `"semi"`）、`:302-303`（写操作确认条件 `self.mode == "active"`）、`:89`
- **证据**：确认逻辑只在 `"active"` 生效，而默认是 `"semi"` → 需要确认的写操作路径实际不经过确认；`:89` 拿 `success_rate` 与 `skill_failure_rate` 直接比较（一个是成功率、一个是失败率，量纲互补不可比）。
- **失败场景**：技能自进化在无人复核的情况下改配置/改技能（与 P1-11 的注入面叠加即为「模型自我授权」）；阈值判断恒偏向一侧，进化方向错误。
- **修复方向**：把「是否需要人工确认」做成显式的动作风险表（与 AutoForge 的分级思路对齐，见跨系统建议），阈值比较统一为同侧指标。

### [P1-10] `dry_run` 参数全链路无人消费

- **位置**：`butler/skills/sandbox.py:33,96-138`、各 skill 执行器；`ctx.dry_run`
- **证据**：`ctx.dry_run` 被设置并透传，但**没有任何执行引擎读取它**；`RISKY_OUTPUTS` 校验的键已在 `schema.py:103-105` 被移除，即校验对象恒不存在（自我满足的检查）。
- **失败场景**：技能「试运行」实际会真实写设备。安全演练给出绿色结论，用户据此放开自动执行。
- **修复方向**：`dry_run` 必须在最终副作用边界（HA 调用、文件写、网络 POST）被判定；`RISKY_OUTPUTS` 改为对**入站**参数或原始输出做检查，而非已被过滤后的结构。

### [P1-11] 技能创建/存储存在路径穿越与竞态

- **位置**：`butler/skills/store.py:146-160`、`butler/roles/store.py:148-191`、`butler/skills/creator.py:123,175-187`、`butler/skills/quarantine.py:40-45`、`butler/skills/templates.py:295-308`
- **证据**：
  - `store.py`：`path = d / f"{sid}.json"`，`sid` 未过滤，`../` 可写目录外；`roles/store.py` 同样直接 `(self.dir / f"{role.id}.json").write_text(...)` / `.unlink()`。对照 `butler/triggers/schema.py:30` 已有 `_ID_RE` 白名单正则——**同一仓库内一半模块做了校验，另一半没做**。
  - `creator.py`：`draft_id = f"draft_{int(time.time())}"` 秒级碰撞；`confirm()` 按 role 弹出而非按 id → 并发草稿会错确认。
  - `quarantine.py`：危险词用子串匹配，`"format"` ⊂ `"information"`、`"reset"` ⊂ `"password_reset"` → 误杀正常技能，同时反向绕过（`"del""ete"` 分词不命中）。
  - `templates.py:295-308`：JSON 用字符串插值拼装，值内含 `"` 或 `\n` 即产出非法 JSON 或被注入额外键。
- **失败场景**：LLM 生成的 skill id 直接决定落盘路径 → 配合 prompt injection（P0-9 的 webhook 可达 Agent）可越界覆盖配置文件；草稿竞态会把 A 的草稿内容确认给 B。
- **修复方向**：所有 id 过 `_ID_RE`（复用 triggers 的实现）+ `Path.resolve()` 后断言在预期目录内；模板改用 `json.dumps`；隔离判定改为分词/正则边界；草稿用 `secrets.token_urlsafe` + 按 id 确认。

## 五、P1：Agent 工具面缺乏校验（可被提示注入放大）

### [P1-12] `control_device` 接受模型给出的 `domain/service/data`，且从不查白名单

- **位置**：`butler/core/tools.py:1030-1052`；对照 `ha_tools/whitelist.is_allowed` 存在但未被调用
- **失败场景**：模型输出（可被设备名、网页正文、webhook 内容注入）→ 任意 HA 服务调用 + 任意 `data` 载荷。白名单模块是**装饰品**。
- **修复方向**：工具入口强制 `is_allowed(domain, service)`；`data` 按服务做 schema 校验；对 L2/L3 域（锁、阀、`shell_command`、`hassio`）要求一次性人工确认令牌。

### [P1-13] `system_run` 直接执行模型给的 path + args

- **位置**：`butler/core/tools.py:1575`（`dpk.system_run(args.get("path"), args.get("args"))`）
- **影响**：等价于给 LLM 一个宿主进程执行原语（对端是 NAS 上的容器/进程）。即使 `dpk` 内部另有限制，工具层的入参处理也已是「未校验即转发」。
- **修复方向**：改为注册表 `{"播放曲库A": 预定义命令}`，参数只能是枚举值；默认关闭该工具，开启需显式配置 + 每次确认 + 审计留痕。

### [P1-14] 快速路由把用户文本切片直接当 `entity_id`

- **位置**：`butler/core/fast_routes.py:104-120`，经 `butler/core/agent.py:48-66`
- **证据**：命中关键词后 `dispatch_tool("control_device", {"entity_id": <用户原文片段>})`，**跳过 LLM、跳过 schema、跳过 P1-12 的（本来也没有的）白名单**。
- **失败场景**：任意含关键词的话术即产生设备写；文本切片可能拼出意料之外的 entity（语音助手场景下电视/环境音里的内容也能触发）。
- **修复方向**：快速路由只能命中**预注册别名表中的 id**，未命中即回退完整链路；输出前二次确认 `entity_id` 在库中存在。

### [P1-15] 提醒/定时类工具在 APScheduler 线程里用 `asyncio.create_task`

- **位置**：`butler/core/tools.py:1226-1231`
- **证据**：`time.localtime` 计算时间 + `asyncio.create_task(...)` 运行在 APScheduler 的线程池（非主循环）。
- **失败场景**：worker 线程内 `get_running_loop()` 是 APScheduler 自建循环或无循环 → `RuntimeError`（被吞）或任务被创建后循环立刻关闭，**提醒永不触发**。这正是摘要中「静默永不运行」类缺陷。
- **修复方向**：统一 `asyncio.run_coroutine_threadsafe(coro, _main_loop)`（`app.py:504` 已有正确写法）；时间用 UTC + 显式 tz，见 §六。

## 六、P1：时间、幂等与调度语义

### [P1-16] 容器 UTC / 代码硬编码 `Asia/Shanghai` / naive-local 与 aware-UTC 混写

- **位置**：`butler/app.py:503`（`AsyncIOScheduler(timezone="Asia/Shanghai")`）、`core/tools.py:1226`（`time.localtime`）、各 store 的时间戳列
- **失败场景**：TEXT 列里同时存在 `2026-09-18T08:00:00+08:00` 与 `2026-09-18 08:00:00` 两种格式，**字符串比较时 `T`(0x54) > 空格(0x20)**，于是「取最近 N 条」的排序跨格式错乱；容器重启到 UTC 后，晨报时间偏移 8 小时。
- **修复方向**：进程内只允许 `datetime.now(tz=ZoneInfo(...))` 一种来源；落库统一 ISO-8601 UTC + 展示层转本地；一次性数据修复脚本 + 列上加 CHECK 或改存 INTEGER（epoch）。

### [P1-17] 冷却写墙钟、判据读单调钟（反之亦然）

- **位置**：`butler/triggers/engine.py:114`、`:299`
- **失败场景**：NTP 校时/夏令时（本仓无 DST 但跨时区部署有）跳变会使触发器冷却一次归零（重复触发）或冻结数小时。
- **修复方向**：所有间隔/冷却用 `time.monotonic()`，所有「什么时候」用 wall clock；两种时钟不写进同一列。

### [P1-18] `sched.modify_job(job_id, next_run_time=None)` 是「永久移除任务」

- **位置**：`butler/triggers/registry.py:222-241`、`butler/health_api.py:112`
- **证据**：APScheduler 中 `next_run_time=None` 表示暂停，但若任务同时被 `remove()`/重启后按「已暂停」跳过恢复，语义上等价删除；这里代码意图是「暂停/取消」，实际让任务再也不会被调度，界面上仍显示存在。
- **失败场景**：健康检查 API 想「重置」一个坏任务，结果把它变成僵尸——用户看到任务在列表里、永不执行、也没有错误。
- **修复方向**：明确 `pause` 与 `remove` 两个 API；`init_from_store` 恢复时校验暂停原因（并修 P0-5 才能恢复）。

### [P1-19] 5 字段 cron 原样交给 `add_job`，校验器从不检查 URL/写路径

- **位置**：`butler/core/cron_task.py:661-688`（`register_api` 持久化调用方 URL，`{secret:xxx}` 直接替换进 URL；`:116-131,198-209` `validate_api_url` 存在但**在写入与执行路径上都没被调用**）；`butler/cron_validator.py:25-34,130-153`（`validate()` 不查 URL；域检查被跳过；`_PRIVATE_NETS` 缺 `::1`、`fc00::/7`、`100.64.0.0/10`）
- **失败场景**：① 注册方给一个外网 URL + `secret` 占位符，之后每次 cron 触发都把含密钥的 URL 发到外部主机（**密钥外泄**）；② `100.64.0.0/10` 未列入私网，而 Tailscale 地址正落在这个段（`192.168.2.200` 之外的 `100.x`）→ SSRF 校验对自家网络失效或被误杀；③ cron 表达式解析错误只在手工校验时报告，注册路径不校验 → 运行时才炸。
- **修复方向**：`validate_api_url` 在 **写入时** 与 **执行时** 各查一次（DNS 重绑定需在执行时复验并锁定 IP）；密钥走请求头而非 URL query；补齐 IPv6 与 CGNAT 段；`add_job` 前强制 `cron_validator`。

### [P1-20] `notifier.push_image` 未校验 URL → SSRF

- **位置**：`butler/notifier.py:118-124`
- **失败场景**：与 P1-19 同源，服务端代拉任意图址，可探内网端口/读云元数据（NAS 环境里主要是内网横向）。
- **修复方向**：白名单域 + 私网拒绝 + 大小/超时上限。

## 七、P2：一致性、可观测性与配置

### [P2-1] ✅ `_env_bool` 忽略自身 `default`，未设置即为 False

- **位置**：`butler/config.py:32-38`
- **证据**：`if v in ("0","false","no","off",""): return False if v == "" else False` —— 空串（即未设置）直接 False，`default` 参数在这两个分支里永不被使用。
- **失败场景**：`tts_cache_enabled` 等所有默认 True 的开关，在没显式配环境变量时**都是关的**；用户改代码里的默认值无效，容易误判为「配置不生效」而去硬编码，进一步腐化。
- **修复方向**：`if raw is None: return default`，并把这一函数纳入单测（True/False/未设置/乱值四种）。

### [P2-2] ✅ 日志脱敏形同虚设，另有脚本直接打印令牌前缀

- **位置**：`butler/logging_setup.py:17-24`（`MaskingFilter` 只处理 `record.msg`，不处理 `record.args`）、`butler/integrations/llm.py:218-219`（工具入参原样 `logger.info`）、`butler/check_token.py:2-4`
- **证据**：`logger.info("%s", secret)` 走 `args`，filter 改不到；`check_token.py` 打印令牌前缀（本报告不复述值）。
- **失败场景**：令牌、成员姓名/住址、聊天原文进日志文件（且日志常比数据库更宽权限），排障时贴日志即泄露。
- **修复方向**：filter 内 `record.msg = fmt % record.args` 后置空 args，或改用结构化日志 + 显式 `redact()`；删除 `check_token.py` 或改为只输出 `sha256[:8]`。

### [P2-3] 别名匹配器 `match()` 定义了但无人调用

- **位置**：`butler/core/aliases.py:13,31-33,66-75`
- **影响**：设备别名解析走了另一条更弱的字符串包含路径（配合 P1-14 的切片），别名库成为只写不读的表。
- **修复方向**：把别名解析收敛到唯一入口 `aliases.match()`，其他路径删除。

### [P2-4] 在场事实第三方写入者 + 未确认即标记已投喂

- **位置**：`butler/memory/feeder.py:43-71,86-96`（与 `roles/store.py`、`agent` 侧共同构成 `role_state.json` 的**第三个写入者**）
- **失败场景**：三个写入者无锁 read-modify-write 同一个 JSON 文件 → 丢更新；500 条事实一次性推送后立即标记 fed，若 MA 侧部分失败则**永久丢失**。

## 八、跨项目设计根因（本项目侧）

1. **半途重构 + `except Exception` = 静默死链**：P0-1/2/3/4、P1-8、P1-5 附带逻辑，全部是「改名/删码后调用方未同步」，而宽异常把编译期就该暴露的问题变成运行时噪音。
2. **失败被编码为成功值**：P1-7、P1-9、P1-10（`dry_run` 无人消费）、P2-5（健康检查恒绿）。系统缺少 `Result/异常` 纪律，导致上层（含 LLM）只能靠读字符串猜测世界状态，进而产出「假成功回复给用户」。
3. **安全能力存在但不接**：`ha_tools/whitelist.is_allowed`、`triggers/schema.py` 的 `_ID_RE`、`cron_validator.validate_api_url`、`modes/engine.py` 的 `can_*`、`push_guard.tts_pop`、`core/aliases.match`——**六个已实现的防护件在全仓无人调用**。这比"没做安全"更危险，因为它让评审者误以为已覆盖。
4. **无 CI、无冒烟测试**：`.github` 下没有 workflow（AutoForge/memory-agent 同样如此）。上述 P0 全部可被「import 一次 + `client.get('/docs')`」的 30 秒冒烟挡掉。
5. **配置层与实际行为脱钩**：P2-1 让默认值失效，P0-10 让配置项被硬编码绕过，P1-10 让 `dry_run` 成为装饰参数。配置系统的可信度已受损，建议做一次「每个配置项 → 唯一读取点」的映射表并删除无读取点项。
