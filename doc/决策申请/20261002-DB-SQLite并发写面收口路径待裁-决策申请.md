## 一、大白话：报告说什么、我为什么⛔ 照它的方子抓药

报告说：全站共用一条 SQLite 连接，MQTT 回调线程、调度线程、事件循环都在往里写 ⇒ 会 `database is locked`。它给的方子有三味：**线程本地连接**（每线程一条）、**`isolation_level=None`**（每条语句自己提交）、**带重试的 `write()` 封装**。

前两味我判定与已经量过的根因**方向相反**：

- 根因不是"两个线程抢着写"，是**一条连接把事务悬住了**（`in-flight` 的隐式事务不 commit，写锁一直握着；`doc/写面复摆取证-20261001.md:144` 的持锁 pid 那一格是终局一票）。把 1 条连接变成 N 条＝**可能悬住的事务从 1 个变成 N 个**，锁面变大不是变小。
- `isolation_level=None` 会把**跨语句原子性**拆掉：现读有 **33 个函数是"多条写共用一次 commit"**（见下表），逐语句自动提交后，中途抛错就是**半提交**状态——这正是本仓第 17 批刚修完的那一族（整份 JSON 就地截断写）的 SQL 版。
- `write()` 重试是把 `locked` 咽下去：`busy_timeout` 已经在做同一件事（现值 5000），再加一层退避只是让"永远等不到释放"看起来像"偶尔慢"。

所以本件请 DCD 裁的是**收口路径**，⛔ 是"要不要修"——修要修，但修哪一层要先定。
