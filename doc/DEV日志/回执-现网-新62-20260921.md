## 一、代码事实（先读码，再发请求；顺序不能反）

### 1. 登录成功后后端到底发了什么 cookie

部署树 `butler/app.py:127-140`（逐行为 `sed -n '126,140p'` 原样读出，行号为部署树口径）：

```python
127  async def _login(request: Request):
129      body = await request.json()
135      tok = login(str(body.get("user", "")), str(body.get("password", "")), client_ip=client_ip)
136      if not tok:
137          return err("用户名或密码错误", 401)
139      r.set_cookie("butler_auth", tok, httponly=True, max_age=60 * 60 * 24 * 7)
```

⇒ **名 = `butler_auth`**；属性只有 `HttpOnly` + `Max-Age=604800`（7 天）。**代码里没有 `secure=True`、没有显式 `samesite=`**（Starlette 默认 `lax`）。令牌由 `deps.py:79-81 make_session()` 生成：`secrets.token_urlsafe(32)` ⇒ **长度必为 43 字符**（这条给了下面读数的自校验点：实测 `token_len=43` 与代码同值，说明我打到的是这份码，不是别的分支）。会话只存 `sha256(tok) → 过期时刻`（`deps.py:83`），落盘 `deps.py:34 _SESSIONS_FILE = /app/data/sessions.json`，TTL `deps.py:33 = 7 天`。登出：`app.py:154 r.delete_cookie("butler_auth")` + `deps.py:306-309 logout()` → `deps.py:104 revoke_session(tok)`，只撤销请求里那一枚令牌。

### 2. 中间件/闸门接受哪些凭据来源（顺序即优先级）

`check_auth` 在部署树 `deps.py:237`，逐支原文行位：

| 顺序 | 行 | 分支 | 放行条件 |
|---|---|---|---|
| 0 | `:228 auth_enabled()` | 未配 `BUTLER_WEB_USER` 时 | `:232 auth_disabled_allowed()` 显式开调试开关才 `return True`（`:242`），否则 **默认拒绝**（`:245 return False`，注释自陈「原行为是静默放行，属 fail-open」已被 WO-ME-204 改掉） |
| 1 | `:247-249` | **cookie `butler_auth`** | `session_alive(tok)`（查 sha256 表 + 过期） |
| 2 | `:251-255` | `Authorization: Bearer …` | 前缀不对直接 `return False` |
| 3 | `:256` | `bearer_locked(request)` | 60 秒窗口内失败 ≥20 次先刹车（`:39-40`） |
| 4 | `:259-262` | `_SERVICE_TOKENS` | 来自 env `BUTLER_SERVICE_TOKENS`；**实测该 env 未设置**（`set=False`）⇒ 这一支今天是空的 |
| 5 | `:267-270` | **把登录口令本身当 Bearer** | `ALLOW_PASSWORD_AS_BEARER` 默认 `"true"` ⇒ `hmac.compare_digest(tok, web_password)` 通过即放行 |
| 6 | `:271` | 记一次 Bearer 失败 | `note_bearer_failure(request)` |

⇒ 结论性的两句：**cookie 会话与 Bearer 是并列的两条合法路径**（谁先匹配谁放行，cookie 在前）；「Bearer 用的就是登录口令」这条不是猜测，是 `:267` 的默认值。

## 三、结论（派单三选一，我选 (a)）

> **(a) cookie 腿是通的，DP 的形状/凭据不对 ⇒ 明早窗口不必为鉴权去动前端。**

支撑与边界，一并写清：

1. **通**：两条送法（显式 `-H Cookie` 与 DP 原样 `-c/-b` jar）各自 200×3，覆盖 `/api/status`、`/api/config`、`/v1/models` 三个不同挂载模块，不是只对一个 handler 有效。
2. **DP 的 T4 为什么会 401**：`回执-DP-20260921-B0.md:19` 自己列了两种可能——「Set-Cookie 属性导致 jar 未回传」或「登录本身返回非 200」。**前者已被 §2.3 逐字复刻证伪**；剩下后者与今天现网状态（新账号名/新口令未生效、活的是 `admin`+旧值）相容。
   ⛔ **但我不能替 DP 断案**：他的 `user`/`password` 两个值全文 REDACTED，我无凭据核对他当时填的是哪一对。所以本件只写到「**属性说已排除，登录失败说是唯一存活解释，且与现网凭据现状相容**」，不写「DP 用错了值」。**要坐实这一条，只有一条合法路径：让 DP 把他那次 `POST /api/login` 的状态码贴出来**（非 200 即结案，与口令值无关，不涉及脱敏）。
3. **不选 (b)**：Bearer 确活（`T-bearerOLD 200 200 200`），但它活**不妨碍** cookie 活；两者是并列路径（`deps.py:247` 与 `:251/:267`），不是二选一。
4. **不选 (c)**：登录没坏，`login_http=200` 两条独立会话各成一次。⇒ **无 P0。**

### 派给窗口的一句话

前端**不需要**为「鉴权形态」改任何东西：网页本来就是 cookie 会话在跑（`authed: true` 那条 `butler_auth`）。真正决定要不要动前端的，是**口令值**那条线（`Bearer` 默认仍把登录口令当 API key，`deps.py:267`；部署树 `deps.py:147` 已留一句「第二步（`ALLOW_PASSWORD_AS_BEARER=false`）要等本单记账名单清零才允许出」）——那是策略问题，不是形态问题，且我不动。

### 对 B-0 悬案（MT 的 APK 重装 / DP-004 ①②③ 挂起中）的影响

- **B-0 的第一问「后端是否仍认 `Bearer <网页口令>`」现在有了我这侧的独立读数：认**（`T-bearerOLD` 200×3，`10:55:44Z` 窗口，与 DP 的 09:35Z 窗口是两个时点、同一答案）。⇒ **换钥对设备是有作用的**，那次 ADB 开机不是白开；挂起的两单可以按「Bearer 存活」排。
- 但**必须提醒时序**：设备里硬编码的是**旧值**（小甜菜 `DecisionActivity.kt` / `GuardianMonitor.kt`、DeskPilot `butler.py:40` 与 `llm_client.py:23`），而口令线是**值变形态不变**。所以 B-0 之后新出现的 401，第一嫌疑是「值已换、设备还在发旧值」，不是「Bearer 形态废弃了」。这条区分对明早很重要，写在这。
