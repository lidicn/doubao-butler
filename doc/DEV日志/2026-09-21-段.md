## 三、本段唯一的新技术发现：Arcface 的「1 秒去重」是一扇永远打不开的门

原先我以为电视端的问题只是「按帧发布」。量出来更糟：

```
MqttManager.java:62   FACE_PUBLISH_INTERVAL_MS = 1000;      ← 意图：最快 1 秒一次
MqttManager.java:502  json.put("ts", System.currentTimeMillis());   ← 把每次都变的毫秒戳放进「待比较串」
MqttManager.java:504-509  rect.put(left/top/right/bottom)            ← 逐帧抖动的坐标也放进去了
MqttManager.java:515  if (payload.equals(lastFacePayload) && … ) return;   ← 左半边恒 false ⇒ return 从未执行
```
AND 条件的左边（整串全等）在正常情况下永远不成立，所以那 1000ms 的门**一次都没拦过**。画面里只要有一张稳定的脸，发布频率 = 相机帧率。

对端后果（butler 侧，`dialog.py:78-81 → :124 → wakeup.py:68 → repo.py:85`）：每收一条 `/face` 就 `INSERT INTO wakeup_log` + `commit()`，**且 `decide()` 四个分支无条件落到那一行，被冷却挡掉的也写**。

活体读数（NAS 容器内只读 SQL，23:31Z）：
```
total 163505   max_ts 2026-09-20 17:14:25Z
by_trigger [('face', 163505)]     ← 整张表 100% 只有 face，没有一行是真正的「唤醒」
last7d 68612   per_day_7d 9802    ← 日均 9,802 行（我此前口头说的 9,033 偏低，以本读数为准）
```
⇒ 一张名叫 `wakeup_log` 的审计表，实际是「同一个人坐在沙发前的重复帧流水」，**它对「今天谁真的被打扰了几次」这个问题回答能力 = 0**，只贡献体积和 NAS 磁盘 commit。

**两头都要修，且不合并成一单**：电视端改去重键（代理对话在做），butler 端改「不许每事件必落库」（`WO-ME-225`）。
