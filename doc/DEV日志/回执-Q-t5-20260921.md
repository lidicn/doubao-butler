## 二、配置键设计（default-off，且不误伤"缺即崩"那三把）

```
butler/config.py
  +    db_retention_days: int = 0                      ← dataclass 字段，默认 0
  +            db_retention_days=_env_int("DB_RETENTION_DAYS", 0),   ← load() 里的 kwarg
```

为什么用 `_env_int` 而不是 PM 提醒的那个 `_env`：

- `_env(key, default)` 是 `.strip()` 的字符串通道，**缺键与空值都变空串** ⇒ 对布尔/整数开关是陷阱（`int("")` 会炸，或更坏：把空串当假值悄悄改语义）。
- `_env_int(key, default)` 内部 `int(os.environ.get(key, str(default)))` 带 `except (TypeError, ValueError) → default`
  ⇒ 缺键 / 空值 / `30d` 这类非法值**全部落回 0＝关**。这条我用 P1 量了，不是推断：

```
P1  DB_RETENTION_DAYS 缺键  -> _env_int(...,0) = 0
    DB_RETENTION_DAYS 空值  -> _env_int(...,0) = 0     （实测喂的是三个空格）
    DB_RETENTION_DAYS 非法值 -> _env_int(...,0) = 0     （实测喂 "30d"）
    DB_RETENTION_DAYS 0/30  -> 0 / 30
    Settings().db_retention_days（不读环境） = 0
```

- **没有碰"缺键即 RuntimeError"那一族**：`config.py:268-287` 的三道闸（`DOUBAO_API_KEY`、`DESKPILOT_API_TOKEN`、
  `TASK_REPORT_TOKEN`、`BUTLER_WEB_PASSWORD`）我一个字没动，也**没给我的新键加必选校验**——
  它是开关，不是凭据；必选校验会把"缺键"从"关"变成"启动即崩"，那正好是 `up -d` 重读 `.env` 时最坏的形状。
- 加字段会不会改到别的回显？E 镜像 188 个 `.py` 里枚举 `Settings` 顶层字段的落点 = 0
  （`api/config_routes.py:42`、`api/system_routes.py:35` 枚举的是 `s.persona.members`，`mask_secrets()` 是 0 调用点孤儿）。
  ⚠ 分母边界：我只跑了 E 镜像 188 个 + 部署树快照 16 个 `.py`，**部署树全量 238 个我没语料** ⇒ 这一格标"未穷尽-无全量语料"。

## 四、补丁自检：四条 rc 全录

尺子与被知的坑（`patch` 不带 `--binary` 会把全 LF 的干净 diff 判红）——**这次我撞到了它的另一面：CRLF 文件**。
在同一台机器、同一份基底上跑：

| # | 命令 | rc | 说明 |
|---|---|---|---|
| 1 | `patch -p1 --dry-run -i <patch>`（**不带** `--binary`） | **1** | `config.py` 两个 hunk 报 `FAILED (different line endings)`；`repo.py`/`app.py` 检查通过 |
| 2 | `patch -p1 --dry-run -s --binary -i <patch>` | **0** | 形状合格 |
| 3 | `patch -p1 -s --binary -i <patch>`（真套到 `_scratch/…/f1`） | **0** | 三文件与 `cand/` **逐字节相同**（`cmp` 三个 BYTE-IDENTICAL） |
| 4 | `git apply --check <patch>`（本机默认 `core.autocrlf=true`） | **0** | 走 git 通道形状也过；头部那 44 行 `#` 注释 git 不拒 |
| 5 | `git -c core.autocrlf=false apply <patch>`（真套到 `t4`） | **0** | 产物 md5 与第 3 行同值（`aa0fef65`/`442e93a3`/`e5ed7fc9`）⇒ 两条通道等价 |
| 6 | `git apply <patch>`（**默认 autocrlf=true**，套到 `t3`） | **0** | ⚠ rc 是 0 但**产物字节不同**：`app.py` md5 → `4b403d0b…`、`repo.py` → `e09810c4…`（LF 整文件翻 CRLF）⇒ §五 那条"别在 Windows 上 git apply"的出处 |

⇒ 第 1 条的 rc=1 **是尺子坏，不是补丁坏**：同一份 patch 在 `--binary` 下 rc=0，且套出来逐字节 == 我的候选。
根因：`butler/config.py` 在部署树里是**整文件 CRLF**（363/363），另两只文件是整文件 LF ⇒ 默认模式对 CRLF 文件必然判"行尾不同"。
第 6 行是更阴的一种：**rc=0 不等于产物对**（工具全对时也要成立那条规矩，我这回是拿 md5 而不是 rc 收的账）。

**逐文件血统（P3，两侧各报 LF/CRLF 两个数，不报单侧）**：

## 五、这张补丁要生效：`restart` 还是 `up -d`

**机制**：`butler/` 整目录是 bind mount ⇒ 盘上 `.py` 换了、活进程仍跑旧模块；`docker restart` 会让进程重新 import 新 `.py`，
但它**不重读 `.env`**（`.env` 由 compose 在创建容器时注入）。所以：

| 要达到的效果 | 需要的动作 |
|---|---|
| **只是把补丁落进盘上代码**（开关仍关死，行为不变） | 落文件 → `docker restart doubao-butler` 即生效。**不需 `--build`、不需 `up -d`**（registry 不可达） |
| **把开关打开**（`DB_RETENTION_DAYS=30`） | 改 `.env` ⇒ 那一次**必须** `docker compose up -d`（不加 `--build`），`restart` 无效 |
| 只落 app.py+repo.py、不合 config.py | `restart` 就够，但**开关永远点不亮**（`getattr(…,0)` 兜底为关），等于今天 |

⇒ 建议的窗口切法：**这一批只落代码 + `restart`**（观察一次启动无异常即算落库完成），
`up -d` + 开键放到**下一次**单独动作，两件事不要塞同一分钟——`up -d` 会重读 `.env` 并可能动可写层（《三个骗人机制》那条账），
把它和"合新代码"绑一起做，出问题就分不清是谁带的。

**落盘前置闸（必须做，别拿"能套上"当"套对了树"）**：
我实测把这张 patch 套到 **E 盘那份已漂移的旧镜像**上，`patch --dry-run --binary` 同样 **rc=0**。
原因是我的 4 个 hunk 的上下文（`sched.add_job(_fp_cleanup_job…)`、`dnd_windows…`、`recent_wakeups`）在两侧完全相同，
漂移发生在别的区（BaiduTTS 块、fail-closed 键）。⇒ **上下文不区分两棵树，只有 md5 区分**。
所以窗口里必须：套之前比 §下表"应用前 md5"三行，套之后比"应用后 md5"三行；任一格不等就停手报 PM，不要 `-f`、不要 fuzzy。

## 九、自报失误（两条，都当场改掉并留了读数）

1. **我的第一条换行读数就是假的。** 我一开始用 `grep -c $'\r' <file>` 量换行，读数报出 `butler/store/repo.py crlf=480`、
   `app.py crlf=963` —— 而字节级复量（python `count(b"\r\n")`）是 **repo.py CRLF=0、app.py CRLF=0**，那两只文件是纯 LF。
   这台 Git Bash 里 `$'\r'` 到 grep 手里退化成空模式 ⇒ `grep -c` 变成"数行数"，**每只文件都会报"全是 CRLF"**。
   后果：我按这个假读数把构建器写成"整文件 CRLF 写回"，被构建器自己的血统闸拦下一次（`ABORT store/repo.py 基底是混装血统`），
   才发现是尺子错。**⇒ 规矩补一条（进台账）**：换行计数只用字节级读数（python `count`）或 `file`/`od`，
   **在这个 shell 里 `grep -c $'\r'` 一律不可用**，它和"数行数"同值。
2. **首版候选按"三文件统一 CRLF"生成**（同上一条的错误读数带出来的），若真交付会把 LF 文件整文件翻成 CRLF——
   正是 `回执-Q-dev` §十二-bis 自报过的那个坑，我在没读到那条之前差点重犯。
   修法：构建器改成**逐文件取血统**（`CRLF if crlf else LF`），并对"基底混装行尾"直接 `ABORT` 不猜。
   现 §四 P3 的两侧 LF/CRLF 并列读数即这件事的闸（**只报新文件那一侧等于没闸**，这是 Q-dev 立的，我照做）。
