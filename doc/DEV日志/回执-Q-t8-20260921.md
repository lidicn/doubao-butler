## B-2 · 现网的真答案：一个**先于 sock 存在**的 bug——docker 工具今天根本没碰 CLI

`_dispatch_docker`（`tools.py:1751 def`，**同步**）在 `:1760/1762/1764/1766` 调 `dk.ps()/restart()/logs()/compose_up()`，而这些都是 `async def`。**全仓没有一处 await 它们**（B-0 尺子 3 = 0 命中）。⇒ `r = dk.ps(...)` 拿到的是一个 **coroutine 对象**，随即 `return _json.dumps(r,…)`（:1776）序列化协程 → `TypeError` → 被本函数自己的 `except Exception`（:1777）接住 → 返回：

```
{"ok": false, "error": "internal_error", "message": "Object of type coroutine is not JSON serializable"}
```

**我用真对象跑出来的原始读数**（本地 python 3.13.2，`import` 成功、吃到被测对象、`sys.path` 挂仓根）：

```
using real DockerClient: True
DockerClient.ps is coroutine function: True
  type(r) = coroutine
dispatch output: {"ok": false, "error": "internal_error", "message": "Object of type coroutine is not JSON serializable"}
never-awaited warning: ["coroutine 'DockerClient.ps' was never awaited"]
```

⇒ **结论对 PM 之问的直接回答**：
1. **不是静默成功**。拔 sock 之后（乃至拔之前），`docker_*` 工具链一律返回 `ok:False`。B 担心的"假绿 = 拔掉却回 `{ok:true}`"**在 butler 这条路径上找不到实证**：底层 `_run_sync` 永不抛、把 rc≠0 如实转成 `ok:False`；外层 dispatcher 的兜底 except 也只会转成 `ok:False`。没有任何分支在失败时写 `ok:True`。
2. **但有一个反向陷阱**（比假绿更值得记）：**当前代码里 sock 根本不会被 butler 打开**——因为 await 缺失，`docker` CLI 从没被 spawn。所以"拔掉 sock 后现象变不变"这个测量本身会**假阴**：拔前 `ok:False(coroutine)`、拔后仍 `ok:False(coroutine)`，看起来"拔 sock 无影响"，实则是**功能早已整条坏掉**（连 §八 说的"改 new-api 后要 restart 生效"那个耦合也从没真正执行过）。**要判断"sock 拔掉会不会静默成功"，必须先把 `_dispatch_docker` 改成 async 并 await（或 `asyncio.run`），否则测的是那个 bug，不是 sock。**
