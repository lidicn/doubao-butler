## 四、最难处理的问题（Top 10）

### 1. 电视播放时语音唤醒率低
- **现象**：客厅电视播放视频时，唤醒词需要很大声才能触发
- **根因**：单麦克风远场拾音，无回声消除（AEC），电视声音被麦克风拾取
- **难点**：需要硬件级 AEC 或多麦克风阵列；软件降噪效果有限
- **当前状态**：DeskPilot 用讯飞 SDK 验证了唤醒，但电视场景未解决
- **可能方向**：Porcupine + 音频预处理；或 TV 端 HDMI 音频回采做 AEC

### 2. LLM 在技能场景中不能正确调用工具
- **现象**：单独用简单工具层可以开电视，但放在 morning_lidicn 场景中 LLM 不调用
- **根因**：function-calling 不稳定 + ReAct 循环 + 两轮 system prompt 矛盾
- **难点**：LLM 行为不可控，prompt 补丁治标不治本
- **当前方案**：Sentinel 模式（表达归 LLM、决策归确定性代码），但复杂场景仍需验证
- **可能方向**：更小的专用模型做意图分类；或完全确定性的状态机

### 3. 记忆系统提取不生效
- **现象**：立即提取显示成功，但待审区域看不到新内容；LLM 读取的是旧内容
- **根因**：提取链路多处断点（API 投喂闸门、自信度阈值、数据库写入）
- **难点**：异步链路长，每一步都可能静默失败
- **当前状态**：增加了投喂闸门和日志，但端到端成功率仍低
- **可能方向**：同步提取 + 即时反馈；或简化为用户手动标记

### 4. TTS 多通道冲突
- **现象**：小爱音箱 TTS、edgetts、nowvoice、讯飞 TTS 多条链路，经常冲突或重复
- **根因**：没有统一的 TTS 调度层，各模块各自调用
- **难点**：不同 TTS 引擎延迟差异大（nowvoice 1-3s，讯飞 <500ms，edgetts 不稳定）
- **当前状态**：有播放队列但只覆盖部分链路
- **可能方向**：统一 TTS 父类 + 优先级队列 + 设备独占锁

### 5. 小爱音箱指令后胡言乱语
- **现象**：对小爱说"关闭空调"后，小爱用 edgetts 播报无关内容
- **根因**：HA 事件触发了某个技能的 TTS 动作，或回声自触发
- **难点**：触发链路长，难以定位是哪个技能/规则触发的
- **当前状态**：未定位根因
- **可能方向**：全链路 TTS 调用日志（哪个技能、哪个触发器、哪条规则）

### 6. one-api.db 读写挂载无法消除
- **现象**：set_model_allocation 需要直写 SQLite，new-api 无等价 HTTP API
- **根因**：new-api 的 abilities 表（含 weight/priority）不通过管理 API 暴露
- **难点**：需要 new-api 侧开发，跨项目协调
- **当前状态**：交接单已发 OP，等待交付
- **可能方向**：自写一个轻量管理 API sidecar；或接受读写挂载 + 白名单限制

### 7. 技能触发器窗口互斥
- **现象**：同一时间段多个 TV 端技能可能同时触发，体验混乱
- **根因**：触发器之间没有资源锁（TV 端是独占资源）
- **难点**：需要跨技能的资源调度器，当前技能引擎是独立执行的
- **当前状态**：有设备锁但只覆盖单设备操作，不覆盖"TV 端注意力"
- **可能方向**：资源抽象层（TV 屏幕 / 音箱 / 灯光都是可占用资源）

### 8. 容器非 root 后 one-api.db 权限
- **现象**：butler 运行在 uid 10001，one-api.db 属主是 new-api 的用户
- **根因**：两个容器用户不同，共享 SQLite 文件需要权限协调
- **难点**：SQLite 写入需要文件级写权限，只读挂载不行
- **当前状态**：one-api.db 仍为读写挂载，权限问题待 phase 2 解决
- **可能方向**：同 UID 运行；或 HTTP API 替代文件共享

### 9. WebUI 功能不完整
- **现象**：缺少登出（已修）、注册、密码修改、角色管理、技能调试等
- **根因**：WebUI 是后补的，很多管理功能只有 API 没有页面
- **难点**：前端工作量大，且需要与后端 API 同步
- **当前状态**：基础面板可用，管理功能缺失
- **可能方向**：优先补技能管理 + 角色管理 + 系统日志页面

### 10. 跨项目协调成本高
- **现象**：ADM 三仓（DB/AF/MA）+ 外部项目（TVPilot/DeskPilot/new-api），接口经常变
- **根因**：没有统一的接口契约测试，变更靠人工同步
- **难点**：每个项目独立开发，接口变更不通知下游
- **当前状态**：有三仓通讯协议标准，但执行靠自觉
- **可能方向**：接口契约测试（CI 中验证跨仓接口）；或共享 schema 包

## 六、需要 DCD（关键决策部）辅助决策的内容

### 架构决策

1. **技能引擎演进方向**：继续 JSON 定义 + 动作链，还是转向 LLM 原生编排（类似 AutoForge IR）？当前技能引擎在复杂场景下表达力不足，但 LLM 编排又有稳定性问题。
2. **TTS 架构**：统一 TTS 父类 + 多引擎继承，还是单一引擎 + 降级链？当前 4 个 TTS 引擎（nowvoice/edgetts/讯飞/小爱）各自为政。
3. **记忆系统归属**：记忆功能应该完全交给 MA，还是管家保留本地缓存？当前双写导致不一致。
4. **设备控制层**：继续通过 HA 间接控制，还是直接对接米家本地 API？HA 有延迟和稳定性问题。

### 技术选型

5. **语音唤醒方案**：Porcupine（离线、准确、需付费）vs 讯飞（在线、免费、有延迟）vs 开源方案（snowboy 已停更）。电视场景的 AEC 怎么做？
6. **多模态识别**：用 doubao2api 的多模态（免费、有延迟）还是本地模型（fast、需 GPU）？NAS 无 GPU。
7. **数据库**：SQLite（当前）是否够用？未来并发量上来后是否需要 PostgreSQL？
8. **前端框架**：当前原生 JS + 静态页面，是否需要引入 Vue/React？管理功能越来越多。

### 产品决策

9. **核心定位**：豆包管家是"家庭语音助手"还是"全屋智能中枢"？前者聚焦对话+TTS，后者需要设备抽象+场景自动化。
10. **角色系统**：7 个角色（butler/jarvis/caesar/gu_anheng 等）是否过多？每个角色绑定房间+音色+人设，维护成本高。
11. **主动服务边界**：主动问询（"要不要开电视"）的频率和场景如何控制？当前无限触发导致体验差。
12. **隐私边界**：摄像头画面、语音数据、家庭成员信息的存储和使用范围。

### 跨项目决策

13. **ADM 三仓分工**：DB（管家）/ AF（自动化）/ MA（记忆）的边界在哪里？当前有功能重叠（如 ask 节点 AF 和 DB 都有实现）。
14. **TVPilot/DeskPilot 归属**：是独立项目还是并入管家？合并风险高（god class），分离协调成本高。
15. **new-api 管理 API**：是等 OP 交付，还是自写 sidecar？影响 one-api.db 只读化进度。
