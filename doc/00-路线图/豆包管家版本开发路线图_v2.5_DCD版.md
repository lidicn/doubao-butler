## 〇、与 v2.4 路线图的关键差异

1. **v2.4 自我描述与代码事实有三处出入**，已核实修正：TTS"没有统一调度层"不准确（TTSManager 已存在，问题是 nowvoice 崩溃 + 未全链路接入）；"统一通知路由层 notifier/router.py"不存在（通知 API 分散 3 处）；技能"没有资源锁"不准确（runner 有 Semaphore/Lock，缺的是"TV 注意力"这类抽象资源）。
2. **新增裁定 0**：本地副本与部署树漂移，开工前先对齐权威树——否则可能在修已经修过的东西。
3. **新发现 P0**：`nowvoice_client.py` 缺失导致 TTS manager 导入即崩，可能正是"多通道冲突/乱播"的部分根因。
4. **v2.5 技能引擎 v2 整体推翻重排**：LLM 原生编排被裁定否决（决策 1），技能工厂/调试面板保留，"技能市场"删除（单用户场景无市场对象）。
5. **v2.8 记忆整合提前到 v2.6**：核实发现召回环节根本不存在（依赖豆包 APP 黑盒），这是日常体验问题，不是中长期价值。
6. **全部版本挂决策门**：路线图是假设不是承诺。

## 十、贯穿纪律

1. **权威树唯一**：本地副本对齐后，要么建 git 仓要么明确只读镜像，禁止再次双向漂移（裁定 0 的固化）。
2. **修复必须带定位证据**：每个 bug 修复 PR 附 trace_id 或日志证据，"修好了"不算证据，"日志显示触发链是 X"才算。
3. **发声调用点零旁路**：v2.5 后任何新增发声必须过 TTSManager，code review 检查项。
4. **版本交付记录修正**：v1.5 的"统一通知路由层"记录与实际不符，在 v2.4 路线图归档时加注——记录失真比代码缺陷更腐蚀决策。

## 十一、一页总结

- **先止血再建设**：v2.4.1 的 5 项全是现网痛点（TTS 崩溃可能是乱播根因），2-3 天；权威树对齐是第 0 步。
- **15 项决策全部有源码依据**：最重要三条——技能引擎不走 LLM 编排（治理层已 B+，别折腾）；记忆召回根本不存在（不是慢，是没有）；v3.0 中枢复用 AF 而非重建。
- **原 v2.5-v2.8 规划重排**：记忆从 v2.8 提前到 v2.6（它是日常体验不是长期价值）；技能市场删除（单用户无市场）；多模态/唤醒挂双评估门。
- **被低估的资产**：decision/ Sentinel 模式（A-）和 triggers 四闸门（B+）是这个项目最健康的两个模块，后续设计应围绕它们扩展而非绕开。

## 十三、ADM 联动篇（DCD 2026-09-29 增补）

> 依据：`decisions/20260929-ADM三仓联动七问-裁定.md` + `20260929-ADM协议选型MCP与ACP-裁定.md`
> DB 角色：**交互中枢（体验入口）**——用户/设备经 DB 进入生态，DB 编排"感知→决策→表达"，把活分给 MA（记忆/感知）和 AF（自动化）。

### 13.1 DB 的联动现状（实测）

- DB→AF：每 5s 轮询 `/api/asks/pending` + 回写 answer（唯一通道）；
- DB→MA：**四路 token、MCP+REST 混用**（MCP Bearer / vision Basic / butler_token / app_token）——全场最乱接入样本；
- DB 自身也是 MCP server（11 工具）；
- DB 订阅 MA 的 `ma/presence`、`ma/device-health`（MQTT）。

### 13.2 DB 的联动档位

| 档 | 联动功能 | 就绪门槛 | 说明 |
|----|---------|---------|------|
| 一（加固） | **DB→MA 通道收敛**：四路 token 收敛为 MCP 主通道，REST 仅留 vision 实时例外 | DB v2.6 | 本轮最大收益点；需 MA 侧 token 合并设计配合 |
| 一（加固） | homesdk http/auth 接入（DB 是 homesdk 首个真实消费方） | DB v2.6 | 完成 homesdk 首验 |
| 一（加固） | MA 记忆召回接入（DB v2.6 既有计划） | MA vMA-1.2.2 完成后 | 前置硬条件不变 |
| 二（价值） | **DB 通过 MCP 查 MA 业务数据**（例："昨天书房空调开机时长"） | MA vMA-1.2.2 后 | MCP 工具调用，确定性 |
| 二（价值） | **DB 通过 MCP 在 AF 建自动化** | AF v2.3.0 后 | ask 通道升级 |
| 三（挂门） | 语义委派走 ACP（建议/叙事类，四条件+四禁止） | 联动稳定后 | 见协议选型裁定 §三 |

### 13.3 表达归 DB（分工铁律）

凡"对人说话"（TTS/通知/电视上屏）一律 DB 出口。MA 出洞察、AF 做设备动作、**DB 负责说**。例：MA 发现"昨日书房工作超时"→ AF 可建"提醒"自动化 → 播报由 DB 完成。

### 13.4 MQTT 规范 + 公共收件箱（DCD 2026-09-29 修订）

**基础能力下放 MQTT**：DB 开设公共收件箱 `butler/inbox/{speak,notify,tv}`，任何仓投递、DB 订阅、DB 过 Sentinel 闸门（夜间/冷却/角色/每日预算）。护栏：Broker ACL（仅注册主体）、载荷 schema fail-closed（超长/缺字段丢弃+审计）、每来源限流、trace_id 必填。

**在线探测**：发布 retained `adm/doubao-butler/status`（LWT 保离线）+ `adm/doubao-caps` 能力摘要；订阅 `adm/memory-agent/status`、`adm/autoforge/status`。

**分工铁律不变**：MA 出洞察、AF 做设备动作、DB 负责说。但表达通道从"MA 同步调 DB"改为"投递收件箱，DB 异步闸门后播出"——**三方不持调用链，只对事件反应**。详见 homesdk 联动篇 §L2。
