## v0.1 — Trigger 规则层基础（P0，约 3.5 天）

**目标**：把硬编码的 `on_face` 打招呼抽象成可配置 trigger 规则，验证 trigger 引擎闭环。

**完成内容**：
1. 新建 `butler/triggers/` 模块（与 `butler/skills/` 平级）：
   - `schema.py`：trigger JSON 校验与规范化
   - `store.py`：`data/triggers/*.json` 存储 + 热加载（参考 SkillStore）
   - `engine.py`：TriggerEngine（事件匹配 + 条件 + 冷却 + 执行）
   - `defaults.py`：默认 trigger 播种
2. trigger JSON schema：`{id, name, event, conditions{time_range,member,room}, role, actions[{skill,params}], cooldown_sec, priority, enabled}`
3. 事件类型：`face_detected`（v0.1 只实现这一个，其他预留）
4. 条件匹配：`time_range`、`member`、`room`
5. 动作执行：单技能 `runner.run()`（多技能动作链 v0.3 实现）
6. 重构 `dialog.on_face`：从硬编码打招呼改为发布 `face_detected` 事件到 TriggerEngine
7. 默认 trigger：`morning_greet`（人脸→打招呼技能，替代原 on_face 逻辑）
8. `app.py` 集成：初始化 TriggerStore + TriggerEngine，挂载到 runtime

**交付物**：
- `butler/triggers/` 模块（4 个文件）
- `data/triggers/morning_greet.json`
- `dialog.py` on_face 重构

**部署记录（2026-09-06）**：
- `butler/decision/` 模块（config/aggregator/engine/action_router）、`butler/skills/engines/decision/`、`butler/api/decision_routes.py`（/api/decision/status · /api/decision/tick · /api/decision/runs）
- `decision_runs` 表 + repo 读写；`decision_heartbeat` trigger（event=heartbeat）+ `decision` 技能（trigger.entry=heartbeat，schema 白名单已扩展）
- APScheduler interval job 每 10 分钟 → `_heartbeat_tick` → trigger 引擎 heartbeat 事件
- runner `_apply_outputs` 支持 `meta.suppress_output`（决策层自管输出，避免重复播报）
- 数据聚合用北京时间（容器跑 UTC，原实现时间错位导致夜间规则失效，已修）
- 新 API：GET /api/decision/status、POST /api/decision/tick（body 可带 mock/now_hour 测试注入）、GET /api/decision/runs
- 单元冒烟测试 `tests/test_decision_engine.py`（9 项：no_action/白名单外/低置信度/speak执行/冷却/notify/异常JSON/suggest/夜间规则/落库）

**真实运行确认**：
- 心跳自动触发：02:12/02:15 两轮真实心跳正常跑（scheduler）
- 02:14 真实数据推理"凌晨无人但书房电脑+空调开着"→ notify 推送到豆包app butler 对话成功
- mock 验证"周一 07:10 客厅灯关+主卧空调开+lidicn 在主卧+要赶高铁"→ LLM 推理"可能睡过头"→ speak 主卧室小爱播报叫醒（confidence 0.95）
- 冷却验证：同场景 1 分钟内二次触发 → "同类行动 speak 在 1 分钟前执行过（冷却 30 分钟）"拦截

**验证标准**：
- TV 人脸事件 → trigger 匹配 → greet 技能 → 小爱播报（与原 on_face 行为一致）
- 时间窗口外不触发
- 冷却期内不重复触发
- 容器重启后 trigger 规则不丢

**已知约束**：v0.1 只支持单技能动作，多技能链 v0.3；参数模板 `{{event.xxx}}` v0.3 实现。

**实际落地记录（2026-09-05）**：

- 技能 4 个：`tv_turn_on`（media_player.turn_on）、`tv_switch_channel`（media_player.select_source，channel→data.source）、`daily_dev_summary`、`today_schedule`
- `data/config.json`：家庭成员配置（lidicn→大佬、Kevin→小凯、Emily→小艾），persona 称呼生效
- **LLM 坑**：deepseek-v4-flash 为推理模型，`max_tokens=256` 预算几乎全被 `reasoning_content` 占用导致正式 content 被截断为空；llm_text 引擎 max_tokens 提到 1024 修复

- **待真实环境确认**：客厅电视 HA 实体 `media_player.xiaomi_rmh1_6103_play_control` 的 turn_on/select_source 是否生效（trigger 参数可覆盖 entity）；真实人脸事件触发链全链路需在 07-08 点窗口实测

## v0.5 — 多角色豆包app对话（通知展示层）（P0，约 2 天）

**目标**：每个角色在豆包app里有一个独立对话；butler 主动消息（提醒、打招呼、决策层行动）推送到对应角色对话，用户在手机豆包app可见。

**关键前提（已验证）**：
- doubao2api `keep_conversation=True` 纯文本对话可用：创建→返回 conversation_id，复用→上下文保留（真机验证："你叫测试用户"跨轮记住）
- doubao2api `tools` 可用（`DOUBAO_CODE_EXECUTOR=on` 已开启，family_fallback 支持中文意图推断）

**完成内容**：
1. 修复 camera_vlm 重复对话 bug：`ctx.role` 为 None 时 `keep_conversation=False` 导致每次新建对话；修复后每角色视觉分析复用同一 conversation_id

4. 主动推送通道：butler 的提醒/打招呼/技能输出，除小爱播报外，可选择同步推送到豆包app对应角色对话
5. 所有角色初始化 conversation_id（butler/xiaoyue/agent_lidicn/agent_kevin/agent_emily/gu_anheng）
6. 对话持久化完善：`dialog_turns` 表加 `role_id` 列，正常对话路径同时存 user+assistant 消息

**交付物**：
- `butler/integrations/doubao.py` 纯文本 chat 方法
- `butler/roles/state.py` 扩展（主动推送）
- camera_vlm 重复对话修复
- 对话持久化完善（role_id + user 消息存储）

**验证标准**：
