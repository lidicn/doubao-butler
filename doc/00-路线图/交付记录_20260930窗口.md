## 4. v2.6#3 死腿：trigger_runs 8 天没写一行（本窗发现并修复）

- 现象：`trigger_runs` 110 行，`max(ts)` = 2026-09-22 07:48:37Z；同期触发器一直在跑（重启后 2 次心跳都记到
  `completed ok`，表里 0 行）。
- 取证手段：把 `triggers/engine.py` 落库处的 `except Exception: pass` 改成带异常类型的 warning。下一次心跳
  （05:08:04Z）就报出真因：`ValueError: Invalid format specifier '.1fs' for object of type 'int'` ——
  `f"elapsed={elapsed:.1fs}"` 把字面量 `s` 吞进了格式说明符，整条 `error=` 表达式在函数被调用**之前**就抛了。
- 归因：坏串来自 `11dd96f`（2026-09-22 16:05:51 +0800 trigger gates…），与表里最后一行是同一天的下午；
  我 `ef53c53` 在那一行尾部只加了 `trace_id=`，没看见同一行这个洞。
- 修复：`{elapsed:.1fs}` → `{elapsed:.1f}s`，并把静默吞异常改为 `logger.warning`（假绿通道闭合）。
- 独立尺：把每个 f-string 的 format_spec 真拿去格式化 float/str/int，扫 `/app/butler` 252 个 .py，
  改前 `INVALID_FORMAT_SPEC=1`，改后 `=0`。
- 生效证据：`trigger_runs` 落新行 `ts=1790744884.69 / decision_heartbeat / heartbeat / ok /
  trace_id=beca39ca339d4e3f`，与同刻日志行尾 `trace=beca39ca339d4e3f` 同号，且无 persist failed 告警。

> 教训（写给自己）：`/api/triggers/logs` 这类"数据接口"如果底下那张表早就停更，接口本身跑得再绿也是假绿。

## 6. G3 门（v2.6 trace 数据能否支撑调试面板）：够反查与回放，不够"单步执行"

`agent_traces` 1,595 行、`trace_id` 填充率 100%，来源分布 `xiaoai 1094 / active 322 / webui 84 / api 60 / tv_wake 29 / wechat 6`；
抽最完整的一条（56 步）逐步看字段：`tool 56/56`、`args` 在每个 action 步、`result` 在每个 observation 步、
`cost_ms 34/56`、`error_code 19/56`。结论分三条：

- **能做**：触发链时间线、逐步变量查看（args/observation 截断 500/800 字符）、耗时与错误码、按 trace 反查
  "这句话是谁触发播的"。这部分数据是够的。
- **不能做**：单步执行。`AgentTracer._persist()` 只在 `finish()` 落库 ⇒ 运行中的 trace 在库里不存在，
  面板无法边跑边看；要做单步必须先在引擎侧加增量落库或断点接口。另有 89 行 `steps_json` 为空的 trace（0 步）。
- **有洞**：`skill_runs` 594 行里 `trace_id` 只填了 6 行（且都是今天 v2.6 上线后的 trigger 跑），
  与 `agent_traces` 的联链命中 0 次；HTTP 入口至今没有 ASGI 中间件铸造 trace（`X-Trace-Id` 也没有），
  webui/api 的链是从 `Agent.run` 内部才开始的。

⇒ 建议面板先做"触发链反查 + trace 时间线 + 变量查看"三件，把"单步执行"从 v2.7 摘出去；
补 HTTP 入口 trace 与 `skill_runs.trace_id` 覆盖面是面板开工前的两张小工单。**这条建议要不要采纳由出资人裁**，
