# 豆包管家生态开发规范 v1.0

> 适用范围：TVPilot、DeskPilot 及未来豆包管家下属所有子项目
> 制定：豆包管家 PM（兼任 DEV）| 日期：2026-09-08
> 原则：工具层不决策、标准化接口、可观察、可复用、少崩稳跑

---

## 一、工具层规范（强制）

所有子项目对外提供的工具接口必须遵循以下规范，豆包管家 ReAct 依赖这些约定做错误恢复和观察验证。

### 1.1 统一响应包络

```json
{
  "ok": true,
  "tool": "tool_name",
  "result": { },
  "cost_ms": 123,
  "error": null
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `ok` | bool | 操作是否成功 |
| `tool` | string | 工具名（与请求一致） |
| `result` | object/null | 成功时返回结构化结果，失败时为 null |
| `cost_ms` | int | 操作耗时（毫秒），用于性能监控和超时判断 |
| `error` | string/null | 失败时的错误码（见 1.2），成功时为 null |
| `message` | string | 可选，人类可读的错误描述或补充信息 |

**禁止**：直接返回裸数据（如 `{"level": 40}`）、返回 HTML、返回非 JSON。

### 1.2 标准化错误码

所有子项目必须使用以下统一错误码，禁止自造错误码。豆包管家 ReAct 根据错误码做重试/换路径/报错决策。

| 错误码 | 含义 | 重试策略 | HTTP 状态 |
|--------|------|---------|----------|
| `invalid_parameter` | 参数错误（缺失/类型错/越界） | 不重试，直接报错 | 400 |
| `unauthorized` | 鉴权失败（Token 无效/缺失） | 不重试 | 401 |
| `forbidden` | 权限不足（白名单外/角色限制） | 不重试 | 403 |
| `not_found` | 资源不存在（窗口/渠道/容器） | 不重试 | 404 |
| `session_required` | 需要先建立会话（SSH/连接） | 先调 connect 再重试 | 409 |
| `confirmation_required` | 危险操作需二次确认 | 向用户确认后带 confirm=true 重试 | 409 |
| `app_not_running` | 目标应用未运行（LX Music/mytv） | 提示用户启动，不自动重试 | 200(ok=false) |
| `operation_timeout` | 操作超时 | 重试 1 次（指数退避） | 504 |
| `unavailable` | 服务不可达（网络错/连接拒绝/503） | 重试 1 次（指数退避） | 503 |
| `not_implemented` | 工具未实现 | 不重试 | 501 |
| `internal_error` | 服务内部错误（异常/崩溃） | 不重试，记录日志 | 500 |

### 1.3 API 路径规范

- 统一前缀：`/api/v1/`（TVPilot 历史原因保留 `/api/`，新项目必须 `/api/v1/`）
- 工具名用小写蛇形：`desktop_screenshot`、`volume_set`、`windows_activate`
- GET 用于查询类（无副作用），POST 用于操作类（有副作用）
- 健康检查：`GET /health`（免鉴权），返回 `{"status":"ok","service":"xxx","version":"x.y.z"}`
- Swagger 文档：`GET /docs`（FastAPI 项目必须启用）

### 1.4 鉴权规范

- 所有 `/api/v1/*` 端点必须 Bearer Token 鉴权（`/health` 除外）
- Token 通过环境变量配置，禁止硬编码
- 开发期默认 Token 必须在文档中标注"开发默认值，生产需更换"
- 生产 Token 由豆包管家统一签发，子项目不自行管理用户体系

## 二、代码规范（强制）

### 2.1 语言与框架

- 后端：Python 3.11+，FastAPI（新项目）/ BaseHTTPRequestHandler（TVPilot 历史遗留，v1.0 前迁移）
- 前端：Vue3 + Vite（DeskPilot）/ 原生 HTML+JS（TVPilot PWA，无构建依赖）
- 禁止：在工具层引入 agent 框架（LangChain/AutoGen 等），运行时 Agent 统一由豆包管家承担

### 2.2 异常处理

- 所有工具入口必须 try/except 捕获异常，返回 `internal_error` 包络，禁止异常冒泡导致 500
- 异常必须写日志（含 traceback），但禁止在响应中返回 traceback（安全风险）
- 超时必须有明确的 timeout 参数，禁止无限等待
- 资源必须释放（文件句柄/数据库连接/SSH 会话）

### 2.3 日志规范

- 使用统一日志库（Python logging），禁止 print
- 日志级别：DEBUG（开发调试）/ INFO（正常操作）/ WARNING（可恢复异常）/ ERROR（不可恢复异常）
- 操作审计日志：所有有副作用的操作（点击/输入/删除/重启/部署）必须记录到 ops.jsonl，格式：
  ```json
  {"ts":"2026-09-08T10:00:00","tool":"desktop_click","params":{"x":100,"y":200},"ok":true,"cost_ms":45,"source":"llm"}
  ```
- 日志禁止包含敏感信息（Token/密码/密钥），必须脱敏

### 2.4 测试规范

- 单元测试覆盖率 ≥ 70%（核心模块 ≥ 80%）
- 工具层测试必须 Mock 外部依赖（ADB/SSH/桌面），禁止测试触碰真实设备
- API 层测试必须验证响应包络格式和错误码
- 全量测试必须在部署前通过，禁止测试失败部署
- 测试命令必须在文档中写明（含环境变量设置）

## 三、部署规范（强制，NAS 环境）

### 3.1 Docker 容器化

- 所有服务必须 Docker 化，docker-compose 编排
- 基础镜像：python:3.11-slim（Python 服务）/ alpine:3.19（轻量服务）
- 镜像必须多阶段构建（如有编译依赖），减小镜像体积
- 容器必须非 root 运行（如可行），最小权限原则

### 3.2 端口绑定

- **必须绑定局域网 IP**：`192.168.2.200:PORT:PORT`，**禁止 `0.0.0.0`**
- 端口分配表（已占用）：
  | 端口 | 服务 |
  |------|------|
  | 8090 | TVPilot |
  | 8095 | 豆包管家 |
  | 8765 | DeskPilot |
  | 3001 | new-api |
  | 1883 | MQTT |
  | 8123 | HomeAssistant |
- 新服务端口必须在开发规范中登记，禁止冲突

### 3.3 健康检查与重启

- 容器必须配置 healthcheck（HTTP 端点或命令）
- 重启策略：`unless-stopped`
- 应用层必须做好异常捕获，**禁止崩溃循环触发 NAS 死锁**
- 重启退避：连续崩溃 3 次后暂停 60s 再重启

### 3.4 数据持久化

- 所有需要持久化的数据（数据库/配置/日志/操作存档）必须挂载 volume
- 数据库文件挂载必须考虑备份策略（写前备份或定期备份）
- 敏感配置（Token/密钥）必须通过环境变量传入，禁止写入镜像

### 3.5 部署流程

1. 本地开发测试通过（全量测试绿）
2. scp/rsync 同步代码到 NAS（禁止实时同步，避免半文件状态）
3. `docker compose up -d --build` 部署
4. 等待健康检查通过（最多 60s）
5. 冒烟测试：调用 health + 1 个核心工具
6. 记录部署版本和时间

## 四、安全规范（强制）

### 4.1 危险操作确认闸

以下操作必须实现 `confirmation_required` 机制：
- 桌面点击命中危险区域（回收站/系统托盘/关闭按钮）
- SSH 执行写操作命令（删除/修改/重启/部署）
- Docker 操作（compose down / restart / rm）
- 系统操作（shutdown / restart / sleep / lock）
- new-api 数据库写操作（修改模型分配/渠道配置）

**确认机制**：
1. 首次调用不传 `confirm` → 返回 409 `confirmation_required`，`message` 说明危险原因
2. 豆包管家向用户确认后，带 `confirm=true` 重试
3. 确认后操作必须执行，且记录审计日志（含 confirm=true）

### 4.2 审计日志

- 所有危险操作和有副作用操作必须记录审计日志（ops.jsonl）
- 审计日志必须包含：时间戳/工具名/参数/结果/耗时/操作来源（llm/manual）/是否确认
- 审计日志保留 ≥ 30 天
- 审计日志禁止包含敏感信息（密码/Token/密钥内容）

### 4.3 最小权限原则

- 容器只挂载必要的 volume 和设备
- SSH 工具必须有主机白名单（P2 启用时）
- 数据库操作必须有备份机制，禁止直接 DROP/TRUNCATE
- Token 必须最小权限（只读 Token 不能做写操作）

## 五、文档规范（强制）

### 5.1 必备文档

每个子项目必须维护以下文档，放在项目 `doc/` 或 `docs/` 目录：

| 文档 | 用途 | 更新频率 |
|------|------|---------|
| `路线图_*.md` | 版本路线图（定位/原则/版本规划/风险） | 每次版本变更 |
| `开发计划_*.md` | 详细开发计划（里程碑/任务分解/验收标准/排期） | 每周同步 |
| `架构_*.md` | 技术架构（模块划分/接口设计/数据流） | 架构变更时 |
| `M*_阶段交付报告.md` | 每个里程碑完成后的交付报告（交付内容/测试结果/待办） | 里程碑完成时 |
| `联调验收_*.md` | 与豆包管家联调的验收报告（场景/结果/问题） | 联调完成时 |

### 5.2 交接单规范

跨项目协作必须使用交接单，格式见 `board/templates/handoff_template.md`。

交接单类型：
- **需求交接单**：豆包管家需要子项目提供什么能力
- **变更交接单**：路线变更/接口变更/决策变更
- **问题交接单**：阻塞/bug/风险
- **联调交接单**：联调计划/验收标准/时间窗口

交接单必须：
- 编号：`YYYYMMDD_NNN_项目_主题`
- 明确发起方/接收方
- 具体需求可执行、可验收
- 标注优先级（P0/P1/P2）和建议截止时间
- 状态跟踪：`待回复` → `进行中` → `已完成` / `已关闭` / `已拒绝`

### 5.3 回复单规范

接收方必须回复交接单，格式见 `board/templates/reply_template.md`。

回复单必须：
- 对应交接单编号
- 明确结论（接受/部分接受/拒绝+原因）
- 具体计划/排期
- 预计完成时间
- 实际完成后更新验收结果

## 六、联调规范（强制）

### 6.1 联调前置条件

子项目工具接入豆包管家联调前必须满足：
1. 工具层规范达标（统一包络/错误码/鉴权）
2. 全量测试通过
3. 健康检查正常
4. 提供工具清单（名称/参数/返回示例/错误码）
5. 危险操作确认闸已实现（如适用）

### 6.2 联调流程

1. 子项目完成工具开发 → 发联调交接单给豆包管家
2. 豆包管家接入工具（DeskPilotClient/TVPilotClient + tools.py 注册 + 观察验证器）
3. 豆包管家部署 NAS → 冒烟测试（health + 1 个核心工具）
4. 联调验收场景（至少 3 个：正常路径/错误恢复/观察验证）
5. 输出联调验收报告
6. 问题反馈 → 交接单跟踪 → 修复 → 回归验证

### 6.3 联调验收标准

- 正常场景端到端通过（用户自然语言 → 工具调用 → 观察验证 → 完成）
- 错误场景正确处理（工具失败 → 错误码 → ReAct 重试/换路径/报错）
- 观察验证生效（操作后自动验证结果，回灌 ReAct）
- 操作存档可对账（管家 agent_traces + 子项目 ops.jsonl）
- 响应时间可接受（单工具 < 5s，组合操作 < 30s）

## 七、版本管理规范（强制）

### 7.1 版本号

- 格式：`v主版本.次版本.修订号`（如 v0.3.1）
- 主版本：架构级变更（不兼容）
- 次版本：功能新增（兼容）
- 修订号：bug 修复/优化（兼容）
- 开发中版本标注 `🔄 进行中`，完成后标注 `✅ 已完成`

### 7.2 里程碑

- 每个版本必须拆分为里程碑（M0/M1/M2...）
- 每个里程碑必须有：目标/任务分解/验收标准/预计工期/依赖
- 里程碑完成必须输出交付报告
- 里程碑延期必须发交接单说明原因和新计划

### 7.3 变更管理

- 路线变更/接口变更/决策变更必须发变更交接单
- 变更必须说明：变更原因/变更内容/影响范围/迁移方案/回滚方案
- 接口变更必须保持向后兼容（至少 1 个版本过渡期）
- 废弃接口必须标注 `@deprecated` 和替代方案

## 八、SSH 与运维能力分级（强制）

### 8.1 分级策略

| 级别 | 能力 | 安全要求 | 适用阶段 |
|------|------|---------|---------|
| **L0 固定脚本** | 封装好的 Python 工具（new-api/docker 等），参数化调用，无任意命令 | 工具内部验证+备份+确认闸 | 当前（默认） |
| **L1 受限脚本** | 限定工作目录的脚本执行（如只允许 `/vol1/1000/docker/` 下的 git pull） | 工作目录白名单+命令白名单+确认闸 | 按需扩展 |
| **L2 受限 SSH** | SSH 执行命令，但主机白名单+命令过滤+只读默认+确认闸+审计 | 5 道约束（见 DeskPilot 路线图 §六-补） | P2，L1 不够用时 |
| **L3 通用 SSH** | 任意 SSH 命令执行 | 不推荐，仅特殊场景临时开启 | 远期，需专项审批 |

### 8.2 当前策略

- **豆包管家**：L0（new-api 直接 SQLite + docker 通过 docker.sock），不提供通用 SSH
- **DeskPilot SSH**：已从 LLM 工具移除，P2 启用时必须达到 L2 标准（5 道约束）
- **新增运维场景**：优先封装为 L0 固定脚本，不轻易升级到 L1/L2

## 九、违规处理

- 违反本规范的代码不得合并/部署
- 违反规范导致的问题必须发问题交接单，限期修复
- 重复违反规范的项目需接受架构评审
- 规范本身需要变更时，发变更交接单，PM 评审后更新
