# 项目管理总纲 v1.0

> 制定：2026-09-09 | 适用：豆包管家 / DeskPilot / TVPilot
> 管理模式：各自按路线图全力推进 → 指定里程碑联调 → PM 负责无需用户在场的验收

---

## 一、组织架构

```
用户（决策者/联调配合）
    │
    └── 豆包管家 PM（调度+验收+文档）
         ├── 豆包管家 DEV（PM 兼任，管家自身代码迭代）
         ├── DeskPilot DP（桌面端工具+代理）
         ├── TVPilot TP（电视端工具+Arcface）
         └── 小甜菜（已交接豆包工作，跟踪进度）
```

---

## 二、工作模式

### 2.1 推进模式
- **各自推进**：DP/TP/管家按各自路线图独立开发，不等待
- **里程碑联调**：到达指定里程碑时，PM 组织联调
- **PM 验收**：不需要用户在场的验收，PM 直接完成
- **用户联调**：必须用户在场的场景，提前预约时间

### 2.2 阻塞处理
- 遇到依赖其他项目的阻塞时，**先绕开**（用 mock/降级方案），不等待
- 无法绕开的，在看板标注"阻塞"，PM 协调
- 阻塞超过 24 小时未解决，升级到用户决策

### 2.3 通信渠道
| 场景 | 渠道 |
|------|------|
| PM→DP/TP 任务下发 | 工单（看板 API）+ 豆包对话消息（DeskPilot PM 管道） |
| DP/TP→PM 状态上报 | 看板 API（accept/complete/fail） |
| DP/TP→PM 紧急问题 | 豆包对话消息 + Bark 推送 |
| 用户→PM | 豆包对话 / PWA 消息 |
| PM→用户 | 豆包对话 / Bark / 小爱 TTS |

## 三、验收分工

### 3.1 PM 可独立验收（无需用户在场）

| 类别 | 具体项 | 验证方式 |
|------|--------|---------|
| 代码质量 | 编译通过 / 单元测试通过 / lint 无错 | 命令行执行 |
| API 接口 | 端点可用 / 请求响应正确 / 错误码规范 | curl / Python 脚本 |
| 容器部署 | 启动成功 / 健康检查通过 / 日志无 ERROR | docker ps + logs |
| 静态页面 | 页面加载 / 元素渲染 / 基础交互 | HTTP 请求 + 代码检查 |
| 数据持久化 | 增删改查 / 重启不丢 | API 测试 + 容器重启 |
| 文档完整性 | 路线图/开发计划/交接单齐全 | 文件检查 |
| 性能基线 | 响应时间 / 内存占用 / 无泄漏 | 压测脚本 + 监控 |

### 3.2 必须用户在场

| 类别 | 具体项 | 原因 |
|------|--------|------|
| 电视真机 | 换台/搜索播放/回桌面/中文输入 | 需要电视开机+遥控器操作+观察画面 |
| 桌面真机 | 点击/输入/拖拽/窗口操作 | 需要电脑解锁+观察实际效果 |
| 语音交互 | 唤醒/对话/TTS 播报 | 需要说话+听结果 |
| 人脸识别 | FaceID 登录/成员识别 | 需要人站在摄像头前 |
| 多设备联动 | 全屋找人/多音箱播报/TV+HA 联动 | 需要多个设备同时在线 |
| 用户体验 | 界面易用性/交互流畅度/视觉效果 | 需要用户主观判断 |
| 锁屏/息屏 | 息屏状态下操作/唤醒 | 需要真实锁屏环境 |

### 3.3 联调节点预约制
- 路线图中每个里程碑标注**验收方式**（PM 验收 / 用户联调）
- 需用户在场的里程碑，PM 提前 24 小时在看板标注"待用户联调"，并通过 Bark/小爱通知用户
- 用户确认时间后，PM 组织联调，联调结果记录到看板

## 四、文档规范

### 4.1 每个项目 doc 目录只保留
- `路线图_v{版本}.md` — 唯一权威路线图
- `开发计划_v{版本}.md` — 当前里程碑开发计划
- `架构_v{版本}.md` — 架构文档（大版本更新时）
- `项目交接文档_{日期}.md` — 最新交接文档
- 当前有效交接单/回执
- `archive/` — 历史文档归档（不删除）

### 4.2 路线图统一格式
```
# {项目名} 版本路线图 v{主.次}
> 版本 | 日期 | 状态
## 版本完成状态表（版本/名称/状态/完成日期/备注）
## 版本详情（每个版本：目标/核心内容/交付物/验收方式/是否需用户在场）
## 依赖关系
## 风险与待决
```

### 4.3 开发计划统一格式
```
# {项目名} 开发计划 v{版本}_{里程碑名}
> 对应路线图版本 | 预计工期 | 负责方
## 目标
## 任务分解表（ID/任务/优先级/负责方/依赖/状态/验收方式）
## 每日进度记录
## 风险与阻塞
```

### 4.4 交接单规范
- 文件名：`交接单_{日期}_{编号}_{标题}.md`
- 必须包含：背景/任务描述/验收标准/依赖/截止时间/PM 签字
- 完成后 DP/TP 写回复单：`reply_{日期}_{编号}_{标题}.md`
- 状态跟踪在 board/handoffs/ 和 board/status.md

## 五、版本号规范

- 格式：`v{主版本}.{次版本}.{修订号}`
- 主版本：架构级变更（如 v1.0 稳定版、v2.0 工具层收敛）
- 次版本：功能里程碑（如 v1.2 DeskPilot 接入、v2.7 SoM 精确定位）
- 修订号：bug 修复/小优化
- 三个项目**各自独立编号**，不强制同步，但格式统一

## 七、风险登记

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| new-api 额度耗尽 | 所有 LLM 调用中断 | 精简 prompt / 降级方案 / 提前扩容 |
| 用户联调时间不足 | 需用户在场的里程碑延期 | 提前预约 / 集中联调 / PM 尽量多验收 |
| 项目间依赖阻塞 | 某项目等待另一项目 API | 先 mock 绕开 / 降级方案 / PM 协调 |
| 文档不同步 | 路线图/开发计划与实际进度脱节 | 每个里程碑完成后立即更新 / PM 每周检查 |
| OC/外部工具不稳定 | 依赖 OC 的任务中断 | 核心功能不依赖 OC / 备用方案 |
